# 协议规范

本文件定义这个仓库是什么、应该怎么用，以及其中每一份手册都必须遵守的规则。参与贡献之前，或开始按本仓库学习之前，请先读完本文。

---

## 1. 目的

把一张高层级的技能图谱，变成一套真正可以学习的手册。图谱回答的是**该学什么**；本协议规定的是**每一份手册必须怎么写**，最终结果要同时做到好上手与技术可信。

它要避免两种失败：

- **太空**——复述原文。五封信合计约 3,000 词，复述一遍不产生任何增量。每份手册都必须从一手来源补充真实的深度。
- **太硬**——直接堆一手文献而不做引导。没有上手坡道的深度是学不进去的。

## 2. 范围

**应该写进来：** 概念、技术、原理、已知的坑，以及确立它们的来源。

**不应该写进来：** 个人项目细节、雇主相关信息、未公开的内部数据，以及任何经不起所引来源作者审视的内容。这是公开仓库，只写可以公开的内容。

## 3. 工作单元

一个子技能一份手册。共 20 个子技能，因此共 20 份手册（每份两个语言版本）。一份手册不得覆盖两个子技能，一个子技能也不得拆到两份手册里。

## 4. 模板规范

每份手册固定包含以下六段，顺序不变。

### 4.1 概述
**目的：** 上手坡道。没有背景的读者读完这一段，应该知道这个技能是什么、为什么重要。
**写什么：** 一句话定义；这个技能解决什么问题；不掌握它会出什么问题。
**不写什么：** 术语、缩写、引用。必须出现的术语就地解释。
**篇幅：** 一到两个短段落。

### 4.2 图谱中的定位
**目的：** 把手册锚定到来源上，防止整理过程中偏离图谱原本的主张。
**写什么：** 忠实转述原文对这一子技能的说法；**至少包含一句原文的直接引用**；附原文链接。引用原文是硬性要求——它把手册锚定在原文实际的主张上，也让读者能够核查。
**不写什么：** 长段引用。见 §5.3。
**篇幅：** 一到两段转述，加一到两句引用。

### 4.3 核心概念
**目的：** 工作性知识——真正动手时需要知道的菜单。
**写什么：** 概念、分类，以及选择的判据，通常用表格或短清单呈现。凡是概念背后带着决策的（"当……时用 X"），把决策规则明确写出来。
**不写什么：** 历史脉络；不改变读者行为的背景铺垫。
**篇幅：** 手册结构的主体，篇幅随子技能而定。

### 4.4 深入原理
**目的：** 底层原理、机制，以及反直觉的发现。手册的可信度由这一段挣得。
**写什么：** 为什么是这样；有测量结果的地方给出具体数字；有据可查的偏差及其缓解手段；与常见做法相矛盾的结论。
**不写什么：** 把推测当事实写。若某结论存在争议，或仅在特定条件下成立，明确说明。
**篇幅：** 手册中篇幅最长的一段。

### 4.5 能力检查点
**目的：** 让它可自测。这是把「文章合集」变成「协议」的关键。
**写什么：** 5–8 条陈述，每条以「我能……」开头，每条都能通过产出某个东西来验证（一段解释、一个设计决策、一份清单）。每条检查点都必须能在 §4.3 或 §4.4 中找到依据。
**不写什么：** 含糊条目（「了解 X」「熟悉 Y」）。如果你无法判断自己是否达标，就重写它。
**篇幅：** 5–8 条。

### 4.6 来源
**目的：** 可核查。
**写什么：** 正文引用过的全部来源，用表格列出类型、出处、链接。
**不写什么：** 你没真正用到的来源。
**篇幅：** 按需。

## 5. 证据规则

### 5.1 来源分层
| 层级 | 包含什么 | 用途 |
|---|---|---|
| **1. 一手** | 同行评议论文；厂商或标准组织的官方文档；作者本人的写作 | 所有实质性的**事实**主张 |
| **2. 实践者** | 具名工程师基于生产经验撰写的文章 | **方法**、工作流、取舍 |
| **3. 二手** | 综述、课程材料、摘要型博客 | 仅用于建立方向感；作为事实陈述前必须回到一手来源核实 |

### 5.2 引用规则
- 每一条非显而易见的事实主张都带来源。
- **引用原文是硬性要求。** 每份手册必须至少包含一句原文的直接引用（保留英文原句并附链接），无论其余部分用的是哪类来源。这是唯一不放宽的来源要求。
- 正文中用 Markdown 链接就地引用，同时在 §4.6 再列一次。
- 不引没读过的来源。不把二手来源当作其本身在转述的主张的依据。
- 引用数字时（准确率、一致率等），给出测量该数字的来源。
- 不设一手来源数量的硬性下限。研究型子技能应多引几个；实践型子技能（Part 4 中的多数）完全可以主要建立在二手材料上，只要明确标注即可。

### 5.3 引用与版权
原文版权归 DeepLearning.AI 所有。本仓库是非官方的，必须清晰守住这条线：
- 每份手册对每封信最多引用一到两句，且必须标注出处并附链接。
- 其余全部改写。
- 不得全文收录任何一封信，包括翻译版。翻译不构成豁免理由。
- 不得暗示获得吴恩达或 DeepLearning.AI 的背书，或与其存在隶属关系。
- 本仓库的原创正文采用 CC BY-NC-SA 4.0 许可（见 `LICENSE`）。被引用的第三方文字不在该许可范围内，保留其自身的署名归属，因此它们不能被随本仓库一起重新授权。

### 5.4 不确定性的表达
说清主张的强度。如果是合理推断，写"多半""实际上"；如果证据只来自单一场景，就说明这一点。

## 6. 术语规则

- 中英对照术语表 [`GLOSSARY.md`](GLOSSARY.md) 具有权威性。手册若需要表中没有的术语，须在同一次改动中补进术语表。
- 手册中首次出现时，使用「中文（English）」格式；此后只用中文。
- 若某个术语在中文圈没有通用译法，**不要自己造一个**。保留英文原词，并把这一决定记录在术语表中。目前的做法实例：`eval`、`grader`、`trace`。

## 7. 双语规则

- `docs/en/` 与 `docs/zh/` 严格镜像，每份手册两个版本齐全。
- 两个版本必须在语义上等价。不要求逐字直译，但任何一方都不得增加或删减实质内容。
- 两个版本的术语都必须与术语表一致。
- 改动任一语言版本，必须同步改动另一版本。

## 8. 文件命名与位置

```
docs/en/part-{n}-{part-slug}/{nn}-{english-slug}.md
docs/zh/part-{n}-{part-slug}/{nn}-{中文标题}.md
```

- `nn` 是 [`MAP.md`](MAP.md) 中的子技能编号，补零到两位，使文件按学习顺序排列。
- **英文手册**：英文小写 slug 加连字符，不得有空格或非 ASCII 字符。
- **中文手册**：用简短的中文标题，与 `MAP.zh-CN.md` 中该子技能的中文名一致。中文目录是给中文读者直接在 GitHub 上浏览的，可读的文件名比 ASCII 一致性更有价值。
- 目录名（`part-1-ai-applications` 等）两个语言树都保持英文 ASCII，以保证 URL 稳定、可分享。

示例：
- `docs/en/part-1-ai-applications/04-evaluation-driven-development.md`
- `docs/zh/part-1-ai-applications/04-评估驱动开发.md`

**改文件名必须同步更新 `MAP.md` 与 `MAP.zh-CN.md` 中的链接。** 只改名不改链接会产生死链，而且不会有任何提示。

## 9. 完成的定义

一份手册同时满足以下全部条件，才算完成：

- [ ] 六段齐全、顺序正确，中英两个版本都是
- [ ] 能力检查点 5–8 条，每条可验证
- [ ] 至少一句原文的直接引用，保留英文原句并附链接
- [ ] 来源与子技能匹配：事实主张依赖一手来源的就引一手；用二手材料的明确标注
- [ ] 每条事实主张都有来源
- [ ] 术语与 `GLOSSARY.md` 一致，新增术语已补入
- [ ] 符合 §5.3 的引用限制
- [ ] `MAP.md` 中该条目标记为已完成

## 10. 新增一份手册的流程

1. 确认该子技能已在 `MAP.md` 中列出且尚未完成。
2. 先搜集来源：子技能有研究或标准基础的，以一手为主；属于实践型的，用二手。若某条主张完全找不到来源，就不要写它。
3. 先用一种语言按模板起草。
4. 写对应的另一语言版本。
5. 新术语补进 `GLOSSARY.md`。
6. 更新 `MAP.md`。
