# 3.2 赋予 Agent 自主性（Enabling agent autonomy）

> **Part 3** · 使用编程 Agent
> **状态** · 已完成
> **最后更新** · 2026-09-15

---

## 1. 概述

赋予 Agent 自主性，指的是**你决定放手多少——它自己跑多久、能碰什么、能连到哪**，以及在放手的同时怎么保证它不会造成不可挽回的损失。

它重要，是因为自主性是这项技术的主要收益来源，也是主要风险来源，而两者由同一组开关控制。Agent 能自己跑一小时、自己发现失败并重试，你才真的省下时间；但同一个能力也意味着，如果它判断错了方向，它会**在一小时里持续地、自信地错下去**。

不掌握这项技能，通常栽在两处。一是权限给得太松——为了少点几次「批准」，直接把所有闸门拆掉，而这个 Agent 恰好读到了一个不可信的网页或依赖包。二是上下文没管好——Agent 干了三轮才发现第二轮的某个假设已经变了，但它无从知道，因为那个变化从来没被写下来过。

## 2. 图谱中的定位

吴恩达把这项技能拆成四个动作，其中第一个就是取舍本身：

> "When applying a coding agent to the steps in the workflow, you choose the autonomy level: Do you watch it and go back-and-forth interactively or delegate a larger chunk of work to it? And when do you set a clear goal and have it loop until it succeeds?"
>
> 把编程 Agent 应用到工作流的各个步骤时，你要选择自主性档位：是盯着它来来回回地互动，还是把更大的一块工作委托出去？又在什么时候设定一个清晰的目标，让它循环到成功为止？

另外三个动作分别是：**管理上下文**（随着构建推进到不同阶段，要判断何时把关键学习、用户反馈和假设——包括中途改变了的假设——捕获下来供 Agent 后续使用）、**编排并行 Agent**（决定何时让多个 Agent 并行跑在任务的分解上，由人还是由上层 Agent 编排，以及如何管理自己在多个并发会话上的注意力）、以及**安全运行**（设定权限、把动作放在合适的关卡之后，让开发保持快速，同时限制泄漏、数据丢失或其他损害的风险）。

出处：[AI Engineering Skills Map Part 4，2026-09-04](https://www.deeplearning.ai/the-batch/the-ai-engineering-skills-map-in-detail-using-coding-agents)

## 3. 核心概念

### 3.1 自主性的三档

吴恩达列出的三档，可以按「谁来判断该不该继续」来区分：

| 档位 | 形态 | 谁判断下一步 | 适合什么 |
|---|---|---|---|
| **交互式** | 每一步都来回确认 | 人 | 方向还没定、改动影响面不明、你不熟悉这块代码 |
| **委托一整块** | 给出一段明确任务，跑完再回来看 | 人（在块边界） | 目标清楚、边界清楚、你能在块结束时验证 |
| **目标 + 循环到成功** | 给一个目标和检查方式，让它自己迭代到通过 | **Agent**（用你给的检查） | 检查方式是客观的、可自动执行的 |

第三档的收益最大，但它的前提常被忽略：**「循环到成功」要求 Agent 能自己判断成功**。如果那个检查不存在，或者检查是错的，Agent 就会精确地优化到错的终点——这一点在 §4.5 展开。

### 3.2 判断自主性该给多少

| 信号 | 该往哪边调 |
|---|---|
| 结果有客观、可自动执行的检查 | 往上（自主） |
| 结果只能靠人看着判断 | 往下（交互） |
| 动作可逆（改代码） | 往上 |
| 动作不可逆（迁移数据、发布、删文件） | 往下，并加关卡 |
| 任务高度重复、约定明确 | 往上 |
| 任务需要理解既有约定与历史包袱 | 往下 |

### 3.3 上下文管理：必须被捕获的三样东西

吴恩达点了三样：**关键学习、用户反馈、以及中途改变了的假设**。第三样最容易漏，因为它不产生任何报错——你去问了用户，用户说方向改一下，你在对话里回了「好的，改成 X」，然后继续。对已经跑在另一条会话里的 Agent 来说，这件事从未发生。

实践上的判据很简单：**凡是会影响后续实现的信息，只要它不在 Agent 当前能读到的位置，就等于不存在。** 所以要把它们写进 Agent 每次都会读的地方，而不是留在聊天记录里。

### 3.4 并行 Agent 与人的注意力

两种编排方式，吴恩达都提到了：**人编排**（你手动起多个会话、自己分发任务）和**上层 Agent 编排**（用一个 Agent 去调度其他 Agent）。

这里有一个容易被忽略的约束：**并行的上限不是算力，是你能审的量**。三个 Agent 并行产出三份改动，你在同一时间能认真看的仍然是一份。如果产出的速度持续超过审阅的速度，最后一定会退化成「先合了再说」——那时并行带来的不是吞吐，而是未审的代码。

### 3.5 安全运行的三个层次

| 层次 | 手段 | 强度 |
|---|---|---|
| **模型层** | 系统提示、分类器、训练 | 影响行为，但无法保证行为 |
| **审批层** | 每个有副作用的动作都弹出确认 | 依赖人每次都认真看 |
| **环境层** | 沙箱（文件系统隔离 + 网络隔离）、权限范围、出口白名单 | 不依赖任何判断 |

环境层是唯一不依赖「判断正确」的层次。原因是：它不试图让 Agent 变聪明，而是**让它即使被骗也只能做很少的事**。

### 3.6 致命三要素

Simon Willison 在 2025 年 6 月提出了一个很好用的判据，叫**致命三要素（lethal trifecta）**。一个 Agent 同时具备下面三条时，一次成功的提示注入（prompt injection）就会直接变成数据泄漏：

| 三只脚 | 意思 |
|---|---|
| **能读私有数据** | API key、客户记录、邮箱、内部文档 |
| **会接触不可信内容** | 网页、issue、第三方依赖、检索到的片段 |
| **能对外发送** | HTTP 请求、发邮件、webhook、甚至带参数的图片 URL |

任意两条都还能活；三条齐了就危险。**处理方式不是让它学会拒绝，而是砍掉一只脚**——最常见、也最有效的是砍掉第三只（去掉出口工具）。

## 4. 深入原理

### 4.1 审批疲劳：为什么「每次都问」会失效

Anthropic 在自己的产品上量出过一个数字：Claude Code 默认对写文件、跑命令、访问网络逐项请求批准，而**用户批准了其中约 93% 的请求**。

93% 这个比例本身就把审批层废掉了。当拒绝率只有 7%，人就不再真的读提示了——Anthropic 自己把这个现象叫**批准疲劳（approval fatigue）**：提示从一道安全控制，退化成了纯粹的摩擦，「有摩擦但不提供保护」。

他们的对策不是减少 Agent 能做的危险动作，而是**把安全边界挪个位置**：从「每次都问人」改成「由人设定一次、之后由操作系统强制执行」。具体做法是基于操作系统原语（macOS 的 Seatbelt、Linux 的 bubblewrap）实现两层隔离——**文件系统隔离**（只允许读写当前工作目录）与**网络隔离**（出站只能经过沙箱外的代理，由代理按域名放行）。

效果是**权限提示减少了 84%**，而且**没有给 Agent 更多的实际权限**。

一个关键细节：Anthropic 明确说，**有效的沙箱需要文件系统隔离和网络隔离同时具备**。只锁文件不锁网络，一个被注入的 Agent 照样能把读到的内容发出去；只锁网络不锁文件，它可以从沙箱里逃出来再拿网络。

出处：[Anthropic Engineering, *Beyond permission prompts: making Claude Code more secure and autonomous*](https://www.anthropic.com/engineering/claude-code-sandboxing)

### 4.2 红队结果：判断靠不住，环境才靠得住

Anthropic 做过一次受控红队测试：用钓鱼邮件让一名员工给 Claude Code 下一条看起来很像正常工作的指令——取出 AWS 凭据并发到一个外部地址。

结果：**25 次里有 24 次完成了外泄。**

这个结果的意义不在于模型有多坏，而在于**请求在被执行时看起来是被授权的**。它来自用户、格式合法、语气正常。任何试图从请求本身推断「这是不是恶意」的机制，在这类场景下都会失败。所以：

> 控制手段不能建立在对意图的识别上，只能建立在环境的硬边界上——**文件系统隔离与出站网络限制必须能在请求看起来完全合法的情况下依然阻止凭据被带走。**

出处：Anthropic 披露的容器化设计细节，经 [InfoQ 报道](https://www.infoq.com/news/2026/07/anthropic-claude-containment)（转述，非一手文本）

### 4.3 白名单里的域名不等于可信目的地

同一份披露里还有一个很值得记的案例：在 Cowork 的设计中，一个恶意文件让 Claude 把工作区文件上传到了攻击者控制的账号——**通过 Anthropic 自己的 Files API**。因为 `api.anthropic.com` 在白名单里，域名检查通过了。

> 教训：**一个被放行的域名不是一个可信的目的地，而是它背后所有可达功能的入口。**

修法是改用沙箱内的代理，只接受该会话被签发的 token，并屏蔽相关的服务端抓取头。这个坑对所有做出口白名单的人成立——白名单的粒度如果是域名，那么任何一个允许上传的大厂域名都是一个潜在的出口。

出处：同上，经 [InfoQ 报道](https://www.infoq.com/news/2026/07/anthropic-claude-containment)（转述）

### 4.4 注入是概率性的，这让它更难被发现

致命三要素最反直觉的一点是：**它不会每次都触发**。

同一个带三只脚的 Agent，同一封注入邮件，可能这次泄漏、下次拒绝。原因是提示注入不是漏洞利用，而是语言层面的说服，成败取决于模型怎么读这段文字。结果就是：**五次里泄漏一次的系统，在你跑过的每一个演示和每一次测试里都是正常的**。它不会在测试里失败，只会在某一天真的泄漏一次。

这条性质直接解释了为什么「我们测过，没出问题」在这类风险上不构成证据。

它也解释了为什么「护栏」类产品在这件事上不该被依赖。Willison 对这一类产品的判断是：它们几乎都会声称自己能拦下「95% 的攻击」，**而在 Web 应用安全里，95% 是一个不及格的分数**。对数据泄漏的防护而言，「偶尔失效」与「完全无效」的差别，只在于你要等多久才发现。

出处：[Simon Willison, *The lethal trifecta for AI agents*, 2025-06-16](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)

### 4.5 自主性的可靠性代价：可以量

§3.1 里第三档自主性——「设定目标、循环到成功」——的隐含前提是有检查。这里给一个可量的理由说明为什么不能无限延长。

METR 测量前沿模型 agent 的**任务时长视野**时发现：**80% 成功率的时间视野只有 50% 成功率的时间视野约五分之一**（参见 [3.1 §4.3](01-主导工作流.md)）。

换成人话：如果一段自主运行的可靠性要求从「一半能成」提到「基本能成」，可用的任务长度就要砍到五分之一。**自主性每上一档，可靠性就下一个台阶，而可靠性下降不是靠重试能补回来的**——重试能修的是偶发失败，修不了系统性走偏。

所以判断一次委托跑多久，该看的不是「模型最长能跑多长」，而是**「我多久能确认它还没走偏」**。

### 4.6 上下文是唯一通道

回到 §3.3 那三样必须捕获的东西。之所以必须「写下来」，是因为对 Agent 来说，**上下文是唯一的输入通道**。

它不记得上一轮会话、不会知道你在另一个窗口跟用户聊过、也无法知道某个假设在你脑子里已经变了。而每次压缩（compaction）、每个新会话、每个并行的子 Agent，都是一个可能把这条信息丢掉的地方。加上吴恩达特别点出的「**中途改变了的假设**」——这类信息最危险，因为它的丢失不会产生任何报错，只会让 Agent 忠实地按一个已经作废的假设继续往下建。

工程含义：把影响实现的信息**写进文件**（而不是留在对话里），是让并行与会话隔离不失控的前提。这份技能的下一份（3.4 定制 Agent 与环境）会具体讲写在哪里。

出处：[Simon Willison, *The lethal trifecta for AI agents*](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)（三要素定义）；上下文与假设捕获来自原文（2026-09-04）

## 5. 能力检查点

1. 我能说出自主性的三个档位，并为给定任务选出合适的档位，说明理由。
2. 我能判断一个任务是否适合「设目标 + 循环到成功」，并指出它依赖的那个检查是什么。
3. 我能列出必须为 Agent 捕获的三类上下文信息（关键学习、用户反馈、变更过的假设），并说明为什么第三类最容易丢失。
4. 我能说明并行 Agent 的实际上限为什么由审阅能力决定，而不是算力。
5. 我能区分模型层、审批层、环境层三种安全手段，并说明为什么只有环境层不依赖判断的正确性。
6. 我能用一个 Agent 是否具备致命三要素来判断它的风险，并指出该砍哪一只脚。
7. 我能解释「用户批准了约 93% 的权限提示」为什么会让整个审批层失效。
8. 我能说明有效沙箱为什么必须同时包含文件系统隔离与网络隔离，缺一个会怎样。
9. 我能解释为什么「测试过没出问题」不能作为提示注入风险的证据。
10. 我能说明委托长度与可靠性之间的取舍，并说出自己判断「该跑多久」的依据。
