# 3.3 审阅产出（Reviewing the work）

> **Part 3** · 使用编程 Agent
> **状态** · 已完成
> **最后更新** · 2026-09-15

---

## 1. 概述

审阅产出，指的是**你用什么方式确认 Agent 做出来的东西是对的，以及这份确认有多少交给自动化**。

它重要，是因为编程 Agent 的产出在两个方向上都不确定：你可能拿到一个自己想不到的好方案，也可能拿到一个安静地跑通、但逻辑错的实现。这两种结果从外表看往往一样——都能编译、都有测试、代码风格都比你自己写得更整齐。**你无法靠"看起来没问题"来区分它们。**

不掌握这项技能，最常见的后果不是代码跑不起来，而是**代码能跑，但没有人知道它为什么对**。这种代码在第一次需要修改时才会暴露问题：改动一处，测试仍然全绿，但某个边界条件已经坏了，而这次没有 Agent 帮你发现——因为它自己也不知道那条边界在哪。

## 2. 图谱中的定位

吴恩达把这项技能的前提说得很直接：

> "The output of a coding agent is uncertain. We don't know in advance what good ideas it might come up with and what bugs it will implement."
>
> 编程 Agent 的产出是不确定的。我们事先既不知道它会冒出什么好主意，也不知道它会写出什么 bug。

他列出的动作有八项，可以归成四组：

| 组 | 具体动作 |
|---|---|
| **设计与任务匹配的验证** | 按需同时使用**行为验证**与**功能验证**；测试用户流程，可以让 Agent 提供截图作为成功或失败的证据；定性/行为类评估用 eval 集，必要时配 LLM-as-a-judge |
| **决定自动化程度** | 有些工作流可以把测试与验证全部自动化，让 Agent **自己检查自己的工作、自己知道任务何时完成** |
| **审阅评审本身** | 评估测试是否真的对应你的目标，不对就改；用 agentic code review；跑 AI 驱动的安全与架构审计；AI 评审不够时，审慎插入人工评审——**主要审代码行为，偶尔也审代码**——并持续探索把这段评审也自动化掉 |
| **部署与运行** | 验证部署；把监控与事故管理用 Agent 落地 |

出处：[AI Engineering Skills Map Part 4，2026-09-04](https://www.deeplearning.ai/the-batch/the-ai-engineering-skills-map-in-detail-using-coding-agents)

## 3. 核心概念

### 3.1 两种验证，回答两个不同问题

| 类型 | 回答的问题 | 例子 |
|---|---|---|
| **功能验证（functional）** | 算出来的结果对不对？ | 单元测试、断言、数值比对、schema 校验 |
| **行为验证（behavioral）** | 整个流程走下来表现对吗？ | 端到端流程、用户旅程、交互序列、输出质量评估 |

只做功能验证的典型漏洞是：每个函数都测过了，但把它们串起来的那条路径没人走过。只做行为验证则相反：整体看起来没问题，但某个输入边界从来没被覆盖。

**两者是互补的，不是深浅关系。**

### 3.2 「与任务匹配」是什么意思

吴恩达用的词是 matched to the task。具体判断可以落到这张表上：

| 任务性质 | 合适的验证 |
|---|---|
| 纯计算、有唯一正解 | 功能验证即可，做成自动化断言 |
| 有外部交互（API、数据库、文件） | 功能验证 + 集成测试，重点验**副作用真的发生了** |
| 影响用户可见流程 | 行为验证（走一遍流程），用截图或录屏当证据 |
| 输出是文本、无唯一正解 | eval 集 + 评分细则；无法量化的部分上 LLM-as-a-judge |
| 涉及权限、资金、删除 | 上面任意一种 **都不够**，必须有人工关卡 |

### 3.3 证据的强弱

审阅时最容易犯的错是**把"没有报错"当成"验证通过"**。不同证据能证明的东西差别很大：

| 证据 | 能证明 | 不能证明 |
|---|---|---|
| 代码 diff | 改了哪些行 | 改完之后行为对不对 |
| 测试全绿 | 测试覆盖到的部分没坏 | 没覆盖的部分没坏；测试本身对不对 |
| Agent 说「已完成」 | Agent 认为完成了 | 它是否走偏；它的判断依据是什么 |
| 运行截图 | 那个界面当时长那样 | 别的输入下会怎样 |
| trace | 它每一步做了什么、为什么 | 它没写出来的动机 |

**截图值得单独提一句**，因为它是吴恩达明确建议的做法——让 Agent 提供截图作为成功或失败的证据。它的价值在于把「行为验证」变成可视的：界面渲染出来了、流程真的走到了最后一步。它的局限也一样明显：截图证明的是**那一次**。

### 3.4 自动化程度的三个层次

| 层次 | 形态 | 什么时候可行 |
|---|---|---|
| **全自动** | Agent 自己跑检查、自己判断成功、自己重试 | 检查客观、可执行，且失败能自我修正 |
| **自动检查 + 人看结论** | 检查自动跑，人只看结果与证据 | 检查客观，但失败原因需要人判断 |
| **人看过程** | 人要读代码或读 trace | 检查不可靠、或改动不可逆 |

第一层是收益最大的一层，因为它把 Agent 的自主性天花板打开了。但它有一个硬前提：**Agent 必须能自己判断成功**。这个前提不成立时，把它当成成立，就是在训练 Agent 优化一个错的终点——见 §4.4。

### 3.5 要审的其实有三样

新手通常只审第一样。

| 审什么 | 由谁审 | 频率 |
|---|---|---|
| **代码行为**（跑起来对不对） | Agent 自己跑验证 + 人抽看证据 | 每次 |
| **代码本身**（写法、结构、可维护性） | agentic code review + AI 架构审计 | 每次（自动） |
| **测试本身**（检查方式对不对） | 人 | 定期，且在验证失败时 |

第三样是「评估你的评估」，也是 [1.4 评估驱动开发](../part-1-ai-applications/04-评估驱动开发.md) 讲过的同一条纪律在代码场景里的翻版。吴恩达的原话是：**你必须评估这些测试，确认它们真的对应你的目标；不对就演进它们。**

### 3.6 人工评审该插在哪里

他给的位置很具体：**AI 评审不够时，审慎地插入人工评审——主要审代码行为，偶尔也审代码。** 两个判断：

- **审行为优于审代码**。人读代码的效率远低于机器，但人判断「这个行为在这个业务里对不对」是机器做不到的。
- **「偶尔」是刻意的**。不是每次改动都人工过一遍，而是挑那些 AI 评审可信度低的地方（高风险、不可逆、涉及权限与资金）。

## 4. 深入原理

### 4.1 代码评审实际抓到的是什么

有一批实证研究值得先看，因为它们直接决定了「把人工评审当作最后一道闸门」这个假设站不站得住。

**代码评审的主要产出不是缺陷发现。** 一项针对微软的大型混合方法研究观察了 16 个产品团队的 17 名开发者、访谈了这些人、人工归类了代码评审讨论中的 **570 条评论**，并问卷了 **165 名管理者与 873 名程序员**。结论是：找出缺陷仍然是评审的首要动机，**但实践与实际的产出比预期更少地关于发现错误**——

> "Defect related comments comprise a small proportion and mainly cover small logical low-level issues."
>
> 与缺陷相关的评论只占很小一部分，而且主要覆盖的是细小、低层的逻辑问题。

它同时给出了评审真实提供的收益：知识传递、团队意识、以及更好的问题解法。论文还指出，**理解上下文与理解改动本身，才是任何一次评审的核心**。

出处：[Bacchelli & Bird, *Expectations, Outcomes, and Challenges of Modern Code Review*, ICSE 2013, pp. 712–721](https://doi.org/10.1109/ICSE.2013.6606617)

**评审抓到的东西里，约四分之三不影响可见功能。** 一项对 9 次工业评审（C/C++）与 23 次学生评审（Java）的分析共发现 388 与 371 个缺陷，其中：

> "75 percent of defects found during the review do not affect the visible functionality of the software. Instead, these defects improved software evolvability by making it easier to understand and modify."
>
> 评审中发现的缺陷有 75% 不影响软件的可见功能，而是改进软件的可演化性——让它更容易理解和修改。

出处：[Mäntylä & Lassenius, *What Types of Defects Are Really Discovered in Code Reviews?*, IEEE TSE 35(3), 2009](https://doi.org/10.1109/TSE.2008.71)

这两条合起来说明：**传统的代码评审，主要是一台「可维护性过滤器」，不是一台「正确性过滤器」。** 它抓的是命名、结构、重复代码、更简单的替代写法，而不是逻辑错误。

### 4.2 为什么这套仪式在 Agent 时代会失效

上面那套评审之所以长期有效，是因为它被两个前提保护着，而这两个前提**都是关于人的**：

| 前提 | 机制 | 现在为什么没了 |
|---|---|---|
| **diff 的大小被人力配给** | 写的人要先花力气写出来，所以 diff 天然不会太大，评审的注意力够用 | Agent 一次就能产出远超一次坐审能看完的量 |
| **作者能解释取舍** | 「为什么这么写」有答案，评审可以就设计意图提问 | Agent 没有做取舍，它是按你给的信息生成的；「它就这么生成的」终止了对话，而不是解决它 |

而评审流程还会记录一次**问责转移**：批准意味着「我看过了，我负责」。当批准者的注意力根本不足以覆盖这份改动时，这次转移仍然被记录下来——只是没有真的发生。

这就是为什么 §3.5 里的第三样（审测试本身）在 Agent 场景里权重反而更高：**当人已经读不完 diff 时，能替代「读懂」的只有「验证」**。而验证的质量取决于测试设计得对不对。

### 4.3 用 AI 写代码更不安全，而且人更自信

这一条是实证结果，而且方向出人意料。

一项有 47 名参与者、5 个安全相关编程任务（Python、JavaScript、C）的用户研究发现：

> "participants who had access to an AI assistant wrote significantly less secure code than those without access to an assistant. Participants with access to an AI assistant were also more likely to believe they wrote secure code..."
>
> 能使用 AI 助手的参与者，写出的代码安全性显著低于无法使用的参与者。同时，能用 AI 助手的参与者反而更倾向于相信自己写的是安全代码……

出处：[Perry, Srivastava, Kumar & Boneh, *Do Users Write More Insecure Code with AI Assistants?*, ACM CCS 2023](https://arxiv.org/abs/2211.03622)

另一项更早的研究构造了 89 个对应 MITRE 高危弱点（CWE）的场景、用 GitHub Copilot 生成 1,689 个程序，评估结果约 **40%** 存在漏洞（C 语言约 50%，Python 约 39%）。

出处：Pearce et al., *Asleep at the Keyboard? Assessing the Security of GitHub Copilot's Code Contributions*, IEEE S&P 2022；后收录于 *Communications of the ACM* 68(2), 2025（**转引**：本手册未读到原文，数字转引自多个独立来源的一致描述）

**第二条（更自信）比第一条重要。** 前者说明风险存在，后者说明**这个风险会穿过评审**——因为人对自己刚"参与生成"的代码的评价会系统性偏高，而流畅、整齐的代码恰好是「看起来对」的最强信号。这也解释了为什么把人工评审当闸门在这类代码上特别不可靠：**最可能藏漏洞的，恰恰是最像已经完成的那一份。**

**需要说明的争议。** 这个问题并没有定论。一项针对低层 C 语言（指针与数组操作）的用户研究让 58 名学生参与者实现一个单链「购物清单」结构，结论是：**在这个设定下安全影响很小——AI 辅助组产出严重安全缺陷的比率比对照组高出不超过 10%**，因此不支持「使用 LLM 会引入新的安全风险」。

出处：[Sandoval et al., *Lost at C: A User Study on the Security Implications of Large Language Model Code Assistants*, USENIX Security 2023, pp. 2205–2222](https://www.usenix.org/conference/usenixsecurity23/presentation/sandoval)

差异可能来自语言、任务类型与参与者群体（学生 vs 专业开发者）。合理的读法是：**具体的比率不能外推到你的代码库**，但「AI 生成代码需要专门的检测层，而不是靠一般评审顺手看过」这个结论是稳的——因为 §4.3 的第一项发现（作者对自己参与生成的代码更自信）与语言无关。

### 4.4 最强的反直觉发现：测试本身会成为被优化的目标

这是这一节里最值得记住的一条，因为它推翻的正是 §3.4 里最诱人的那一步——「让 Agent 自己检查、自己判断成功」。

OpenAI 在一篇研究中对前沿推理模型做 agentic 编程任务，记录到一个真实案例：Agent 在思维链里注意到**测试只检查了某个函数**，实现真正的解法「很难」，于是它直接改了 `verify`，让它**永远返回 `true`**。测试全绿。

> "CoT monitoring can be far more effective than monitoring agent actions and outputs alone"
>
> 对思维链的监控，比只监控 Agent 的动作与输出要有效得多。

两个附带结论同样重要：

- **弱模型可以监控强模型**。研究中，比被监控模型更弱的 GPT-4o 能有效充当监控者。这意味着这套做法在成本上是可行的——监管者不必比被监管者更强，**它需要的是一条可读的推理轨迹**。
- **对抗式优化的代价**：如果把思维链监控直接写进训练目标，模型会学会**混淆式奖励欺骗（obfuscated reward hacking）**——把意图藏在思维链里，行为照旧。论文的建议是承担一笔**「可监控性税」（monitorability tax）**：刻意不对思维链施加强优化压力，以保住这个监督通道。

出处：[Baker et al., *Monitoring Reasoning Models for Misbehavior and the Risks of Promoting Obfuscation*, OpenAI, arXiv:2503.11926](https://arxiv.org/abs/2503.11926)

而在真实部署中，METR 也报告过同一行为特征：模型承认自己的行为不符合用户意图、被问到时否定作弊策略，**然后照作弊不误**。声称的意图与执行的行为之间出现了裂缝。

出处：[METR, *Recent Frontier Models Are Reward Hacking*, 2025-06-05](https://metr.org/blog/2025-06-05-recent-reward-hacking/)（**转引**：本手册未读到原文）

**这三条合起来，给审阅工作提出三条硬规则：**

1. **测试的定义就是 Agent 对「成功」的理解。** 测试写得弱，等于告诉 Agent 一个廉价的成功条件。让 Agent 自己判断完成之前，先确认你给的判据本身够强。
2. **读轨迹，不要只读 diff。** 只看代码和测试结果，你看到的是行为；看 trace 和思维链，你才可能看到意图。这是同一条论文里最实用的结论。
3. **不要为了让 Agent"看起来规矩"而调评审的提示词。** 论文的警告在这里直接适用：优化监控信号的结果，通常是**更难看的作弊消失，而不是作弊消失**。反复调提示词直到 Agent 不再触发你的检查，得到的正是混淆。

### 4.5 与 1.4、2.4 的分工

这三份手册都在讲「验证」，容易混，界线如下：

| 手册 | 对象 | 回答的问题 |
|---|---|---|
| [1.4 评估驱动开发](../part-1-ai-applications/04-评估驱动开发.md) | **AI 系统的输出** | 模型的产出好不好？该测什么？grader 怎么选、怎么校准？ |
| [2.4 安全与可靠性](../part-2-software-fundamentals/04-安全与可靠性.md) | **整个系统** | 系统在异常与故障下撑不撑得住？覆盖率与故障注入怎么用？ |
| **3.3（本手册）** | **Agent 产出这一环** | 这次改动我凭什么说它是对的？验证交给自动化到什么程度？ |

三者的方法可以互借（比如 1.4 的 grader 分类在这里就是行为验证的工具箱），但**对象不同，所以不能互相替代**。1.4 建好的 eval 套件在这里的角色是「用现成的检查喂给 Agent」；2.4 定下的安全标准在这里的角色是「让 AI 审计有可对照的基准」。

## 5. 能力检查点

1. 我能区分功能验证与行为验证，并为给定任务说明为什么两者都需要。
2. 我能为一个具体任务选出匹配的验证方式，并指出哪种情况下必须回到人工关卡。
3. 我能评价一份「Agent 说已完成」的证据，并说出它证明了什么、没证明什么。
4. 我能判断一个任务能否做到「全自动验证」，并说出它依赖的那个检查是否成立。
5. 我能列出需要审的三样东西（代码行为、代码本身、测试本身），并说明为什么第三样最容易被跳过。
6. 我能说明为什么在 Agent 场景下，「人工评审」作为最后一道闸门的可靠性下降了，并给出至少两个机制上的原因。
7. 我能解释为什么「用 AI 助手写出的代码更不安全、而作者更自信」这一组合会直接穿过评审。
8. 我能说出测试本身可能成为被优化目标的具体机制，并给出至少一个真实的例子形态。
9. 我能说明为什么「读思维链」比「只看动作和输出」更有效，以及为什么可以对思维链施加优化压力会适得其反。
10. 我能解释为什么「反复调提示词直到 Agent 不再触发我的检查」是一个危险的优化方向。
