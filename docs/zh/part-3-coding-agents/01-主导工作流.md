# 3.1 主导工作流（Directing the workflow）

> **Part 3** · 使用编程 Agent
> **状态** · 已完成
> **最后更新** · 2026-09-15

---

## 1. 概述

主导工作流，指的是**你决定每一步由谁来做、做多深、什么时候退回上一步**，而不是让 Agent 自己决定整件事该走到哪里。

它重要，是因为用编程 Agent 的瓶颈已经不在敲代码。代码它写得比你快，大部分也能写对——问题在于它不知道你真正想要什么，也不知道自己什么时候猜错了。于是开发的重心从「把代码写出来」移到「说清要做什么、判断做出来的东西对不对」。**这两件事不能交出去**，因为一旦交出去，就没有人能判断结果了。

不掌握这项技能，通常表现为两种极端。一种是任务一丢就不管，拿回一堆能跑但方向不对的代码，再花更多时间往回改。另一种是每一步都亲自盯着，Agent 是快了，但人成了新的瓶颈，整体反而比以前慢。

## 2. 图谱中的定位

吴恩达在这一封信里先给出一套高层工作流，再说明它由五个子技能支撑。工作流本身分三段：

| 阶段 | 包含什么 |
|---|---|
| **规划（planning）** | 头脑风暴（可能包含调研、实验、理解现有代码库）；写一份捕获需求、技术设计与架构的 **spec**，再据此生成**执行计划**；复审这份计划，检查关键假设与安全、过度设计等缺口 |
| **执行（execution）** | 构建、测试、验证，在 Agent 自主性与人的监督之间取平衡 |
| **部署与监控（deployment and monitoring）** | 部署（可能由 CI/CD 或额外的人工关卡把守）；再用 Agent 盯日志、暴露问题、提出并执行改进 |

他对「主导」这项技能本身的定义是：

> "This involves deciding how much human and how much agent effort to spend on each and when to go back to an earlier step to iterate. It requires deeply understanding the tradeoffs of speed, cost, technical risk, and human effort..."
>
> 这包括决定每一步投入多少人力、多少 Agent 算力，以及什么时候退回上一步去迭代。它要求你深入理解速度、成本、技术风险与人力投入之间的取舍……

同时他明确说了两件事：**时长相依、步骤可省**——绿地（greenfield，从头新建）原型的 spec 可能就是一段随手写的提示词，而有很多用户的存量（brownfield）项目，光是把 spec 写出来并验证就够费劲；以及这套流程**高度迭代**——「熟练的开发者知道后一步的反馈什么时候应该把他们带回前一步」。

出处：[AI Engineering Skills Map Part 4，2026-09-04](https://www.deeplearning.ai/the-batch/the-ai-engineering-skills-map-in-detail-using-coding-agents)

## 3. 核心概念

### 3.1 规划产物的三档

规划要写到多细，是这项工作里最常见的一个误判。判断依据是**这件事错一次要付多少代价**——代价高就多写，代价低就少写。

| 档位 | 产物形态 | 适合什么 | 代价 |
|---|---|---|---|
| **一段提示词** | 直接在对话里说清要什么 | 绿地原型、一次性脚本、可丢弃的探索 | 错了重来，损失几分钟 |
| **spec** | 需求 + 技术设计 + 架构，写成文档 | 有真实用户的功能、要和既有代码融合的改动 | 错了要在代码里往回拆 |
| **spec + 执行计划** | 上面的 spec 再拆成有序、可验证的步骤 | 多人协作、需要评审、改动面大 | 错了会波及多个模块与他人 |

吴恩达对存量项目的判断是：spec 不仅要写，还要**验证**——因为存量系统的约束往往不在文档里，而在代码里。

### 3.2 计划复审要盯的三类缺口

他自己点了三个方向：**安全、过度设计、以及其他缺口**。其中过度设计最容易被忽略，因为它的表现是「代码看起来更专业了」。值得盯的具体问题：

- 有没有引入本不需要的抽象层、配置项、框架
- 有没有为了"以后可能要用"而提前建的扩展点
- 有没有把简单判断写成了策略模式
- 关键假设是什么？如果这个假设错了，整个设计会不会塌

### 3.3 拆解的判据：可验证

拆成多个步骤交给 Agent，判断一个步骤是不是好的单位，有一条很实用的标准：**你能不能写出它的检查方式**。写得出来，这一步就可以交给 Agent 自主跑；写不出来，这一步要么再拆，要么就得人在旁边看。

这条标准同时解释了为什么「把整个需求丢给 Agent 让它自己拆」通常不理想——它拆出来的步骤是按它自己理解的逻辑，而不是按你能验证的边界。

### 3.4 什么留在人手上

吴恩达用了一个说法：**「什么时候把关键工作保留为人类所有」**（when to retain human ownership over critical work）。判断的两个维度：

| 维度 | 留在人手的信号 |
|---|---|
| **不可逆性** | 数据迁移、删除、对外发布、涉及真实资金 |
| **不可验证性** | 结果对不对没有客观检查方法，只能靠判断 |

两项都低的时候，交给 Agent 是划算的；只要有一项高，就该保留人的决策权——不是由人写代码，而是由人对**结论**负责。

### 3.5 什么时候退回上一步

这是「主导」与「跟着走」的分界线。三种典型的回退触发：

| 现象 | 退回到哪 |
|---|---|
| 验证失败了，但失败原因是需求本身没想清楚 | 退回规划，重写 spec |
| 实现过程中发现某个架构假设不成立 | 退回规划，改设计 |
| 部署或监控暴露出问题 | 退回执行（或规划，取决于问题性质） |

**回退不是失败**。真正昂贵的是一直往前走、把错误放大。

## 4. 深入原理

### 4.1 一个实测出来的反直觉结果

2025 年 METR 做了一项随机对照试验，对象是 16 位长期维护大型开源项目的资深开发者（他们维护的项目平均超过 2.2 万颗星、人均写过 100 万行以上代码），任务来自他们自己代码库里的 246 个真实问题。

结果：**使用 AI 工具时，这些开发者完成同样的任务慢了 19%。**

而更值得注意的是感知：任务开始前，他们预测 AI 能让自己快 24%；任务结束后，即便面对变慢的实测结果，他们仍然认为 AI 让自己快了 20%。

慢在哪里，也被量出来了。研究者分析了 140 多个小时的录屏，发现 AI 确实节省了三类时间——**主动编码、测试与调试、阅读与搜索信息**——但这些节省被另外两类开销吃掉了，而且超出：

- **审查 AI 输出、提示 AI、等待生成**
- **空闲与切换开销**（录屏里无活动的时段）

同一份研究里还有一个数字：这些开发者**不经修改直接接受 AI 生成代码的比例不到 44%**；在「可用 AI」那一半任务里，**约 9% 的任务时间花在审查 AI 的输出上**。

出处：[METR, *Measuring the Impact of Early-2025 AI on Experienced Open-Source Developer Productivity*, 2025, arXiv:2507.09089](https://arxiv.org/abs/2507.09089)

### 4.2 为什么"更快"和"感觉更快"会分开

上面的数字不该被读成「AI 工具没用」。它在说明另一件事：**瓶颈的位置换了**。

METR 的解释是，编程基准测试为了可规模化，通常牺牲了现实性——任务是自包含的，不需要先前的上下文就能理解，而且用算法自动评判。这两点都会**高估** AI 的能力：真实任务需要读懂一个你并不熟悉的代码库，而正确与否的判断往往没有一个现成的判分器。

这也解释了这个悖论的核心：如果任务的瓶颈原本是「写」，AI 确实赢了；但如果瓶颈是「理解既有约束」和「判断结果对不对」，AI 省下的那点写代码时间，会被它带来的额外理解与审查成本抵消，甚至倒亏。**越是熟悉自己代码库的资深开发者，这两种成本越高**——因为他能看出来 AI 的解法和这个代码库的既有约定不一致，而这需要时间。

工程含义很直接：**把 Agent 用在瓶颈确实是「写」的地方**（从零起、约定明确的模块、大量重复性改写），而不是用在瓶颈是「理解」的地方（改动一个自己也不熟的子系统）。

### 4.3 可以委托多长的任务，取决于你能验证多长

METR 另一项研究提出了一个衡量方式：**任务时长视野（time horizon）**——把 AI 能可靠完成的任务，换算成人类专家完成同样任务需要多少时间。他们测的是 **50% 时间视野**，即 AI 有 50% 成功率完成的任务长度。

两个结论值得记住：

- **增长是指数级的**：2019–2025 年间，前沿模型 agent 的 50% 时间视野大约**每 7 个月翻一倍**。论文发表时（2025 年 3 月），Claude 3.7 Sonnet 的 50% 时间视野约 **50 分钟**。
- **可靠性与任务长度是强取舍**：同一批模型的 **80% 时间视野**只有 50% 时间视野的**约五分之一**。

第二点是这项研究里最有工程价值的一条，但最少被引用。它意味着：如果你要的是「基本能成」，可委托的任务长度只有「一半能成」时的五分之一。换句话说，**把自主性往上调一档，可用的任务长度就要往下砍一档**。

METR 后来发布了更新版数据（Time Horizon 1.1），把任务集从 170 个扩到 228 个，并给出更细的拟合：2023 年之后的翻倍时间约为 131 天，只看 2024 年之后则约 89 天。同一版数据里，Claude Opus 4.5 的 50% 时间视野约为 4 小时 49 分。METR 同时提醒，**在当前任务集下，超过 16 小时的测量不可靠**——任务集在高难度端已接近饱和。

出处：[METR, *Measuring AI Ability to Complete Long Tasks*, 2025, arXiv:2503.14499](https://arxiv.org/abs/2503.14499)、[Time Horizons 追踪页](https://metr.org/time-horizons)

### 4.4 吴恩达本人对"长时间自主运行"的降温

这一点值得单独列出来，因为它来自原始文档本身，而且与舆论的调子相反：

> "For example, it is sometimes useful to get agents to run autonomously for hours and burn millions or tens of millions of tokens. But currently the practical utility of very long-horizon tasks — especially relative to their cost — has been amplified beyond reality."
>
> 举例来说，让 Agent 自主运行几个小时、烧掉数百万乃至数千万 token，有时是有用的。但目前超长时域任务的实用价值——尤其是相对于其成本而言——被放大到了超出真实水平的程度。

他的结论是，「大多数有效的编程 Agent 使用是一个复杂、高度迭代的过程，**能够带着高水平的判断介入，会带来好得多的结果**」。这与 §4.3 的数字是同一件事的两种说法：可以委托的长度，取决于你能多快发现它走偏了。

### 4.5 为什么规划在 Agent 时代反而更值钱

有一个机制上的理由，值得说清楚。

在过去，一个错误的规格会被**实现成本**限制住：想法错了，写到一半就会疼，人自然会停下来重新想。现在实现成本大幅下降了——**这个天然的刹车没有了**。一个错的规格仍然会被忠实、完整、快速地实现出来，而且因为代码质量看起来不错，它甚至更难被认出是错的。

这就是为什么规划环节（以及复审计划里的关键假设）在整条流程里的权重反而上升了。规划省下的不是写代码的时间，而是**在被忠实实现的错误方案上返工的时间**。

## 5. 能力检查点

1. 我能画出「规划 → 执行 → 部署与监控」三段流程，并说出每一段里人的具体动作是什么。
2. 我能针对一个具体任务，判断规划产物该停在哪一档（一段提示词 / spec / spec 加执行计划），并说明理由。
3. 我能拿到一份 Agent 生成的执行计划后，指出其中的关键假设、过度设计与安全缺口。
4. 我能把一个需求拆成多个步骤，并逐个说明每一步的检查方式，判断哪些步骤可以交给 Agent 自主跑。
5. 我能说出哪些工作应该保留人的决策权，并给出判断依据。
6. 我能举出至少三种「该退回上一步」的信号，并说明各自退回哪一步。
7. 我能解释为什么资深开发者在实测中反而变慢了，以及这对「该把 Agent 用在什么任务上」意味着什么。
8. 我能说明任务时长视野与可靠性之间的取舍关系，并据此为一个具体任务选择合理的委托长度。
