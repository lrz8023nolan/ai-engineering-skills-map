# 3.5 编程 Agent 原理（Coding agent foundations）

> **Part 3** · 使用编程 Agent
> **状态** · 已完成
> **最后更新** · 2026-09-15

---

## 1. 概述

编程 Agent 原理，指的是**知道编程 Agent 内部大致是怎么运转的**：它怎么找代码、上下文窗口怎么被填满、不同操作怎样改变它的状态、以及它本质上是什么。

它重要，不是因为你要去造一个 Agent，而是因为**这些机制直接解释了它什么时候会失败、以及失败时你该怎么处置**。面对一个黑箱，你只能不断试提示词；知道里面在发生什么，你才能判断「它卡住是因为没找到文件，还是因为上下文快满了，还是因为它根本误解了目标」——这三种情况的处方完全不同。

不掌握它，最典型的后果是把 Agent 的系统性缺陷误当成偶发问题处理。它一次没做完任务，你让它「再试一次」；它写的代码比需要的复杂，你让它「简化一下」；它开始匆匆收尾，你以为它在偷懒。这些都不是态度问题，也不都是换更强的模型能解决的——**它们是同一个结构在不同条件下的表现**。

## 2. 图谱中的定位

吴恩达把这项技能放在最后，理由是它是前面几项决策的基础：

> "Finally, to make good decisions throughout, you have a good understanding of how coding agents work: how they carry out codebase search/retrieval, how they manage their context windows, how different operations (like adding tool calls, MCP servers, etc.) affect context, how agents and subagents interact, and how the agent is built by wrapping a harness around an LLM."
>
> 最后，为了在整条流程里做出好决策，你要理解编程 Agent 是如何工作的：它怎样搜索／检索代码库，怎样管理自己的上下文窗口，不同操作（例如增加工具调用、MCP server 等）怎样影响上下文，Agent 与子 Agent 如何互动，以及 Agent 是如何通过在一个 LLM 外面包一层 **harness** 而构建出来的。

他给出了这项技能的三重用处：

1. **认清失败模式**——他点名的有：把简单方案**过度设计**、因为缺少显式验证流程而**失去严谨性**、**中途停下**没到目标、以及有**破坏文件或生产数据**风险的动作。
2. **推理 Agent 的状态并给它下对处方**——要么给指令、要么给上下文。
3. **监测运行过程**——在它跑偏、需要你介入时更早看出来。

## 3. 核心概念

### 3.1 一个 Agent 是什么

一句话：**一个在循环里调工具的 LLM，外面包着一层负责上下文管理、任务分解与流程控制的代码。** 那层代码就是 harness。

把这些部件分开看之后，「Agent 表现不好」就不再是一个整体性的判断，而是一个可以定位的问题：

| 部件 | 负责什么 | 它出问题的表现 |
|---|---|---|
| **模型** | 判断下一步做什么 | 理解错目标、推理不到位 |
| **工具** | 能做什么 | 想做的事做不到，于是绕路或用更差的方式做 |
| **harness** | 上下文怎么管、任务怎么拆、什么时候停 | 长任务失稳、提前收尾、忘记早先的决定 |
| **环境** | 代码库结构与常驻说明 | 反复猜错约定与命令（见 [3.4](04-定制Agent与环境.md)） |

**同一个模型配上不同的 harness，表现可以差出一个量级。** 这是这一节最重要的一个判断，也是「换更强的模型」经常不奏效的原因。

### 3.2 它怎么找代码

编程 Agent 找代码主要靠**边搜边读**，而不是靠预先建好的索引：用类似 grep／glob 的检索工具定位候选，读进来，再据此决定下一步搜什么。这是一种迭代式的定位，和「先建向量索引、再做一次相似度检索」的路线不同。

这条机制有一个直接推论：**Agent 本来就擅长在一个陌生仓库里自己摸索**。所以给它一份手写的「目录导览」通常收效有限——它不解决「该进哪栋楼」的问题（见 [3.4 §4.1](04-定制Agent与环境.md)）。真正帮到它的是那些**搜不出来的东西**：非标准的工具、有历史原因的约定、以及绝对不能碰的地方。

### 3.3 上下文窗口的账

上下文是有限的，而且是**每次会话重新开始**的。值得养成习惯去算这笔账：

| 占用项 | 何时进入 | 是否能主动控制 |
|---|---|---|
| 系统提示 + 工具定义 | 会话开始时 | 能——少连 MCP server、少装技能 |
| 常驻上下文文件 | 会话开始时 | 能——只写必要内容（见 [3.4](04-定制Agent与环境.md)） |
| 读进来的文件 | 每次读取时 | 能——但难以事前预知 |
| 工具输出（测试日志、构建输出） | 每次执行后 | 能——让输出更短 |
| 对话与推理历史 | 持续累积 | 部分——靠压缩或重置 |

其中**工具定义与常驻文件是「先付费」的**：你在任务开始之前就已经花掉了这一部分。这也是 [3.4](04-定制Agent与环境.md) 里那些「按需加载」设计存在的理由。

### 3.4 上下文快满时会发生什么：压缩与重置

这是两个不同的动作，解决的不是同一个问题：

| 做法 | 机制 | 保留连续性 | 能解决「提前收尾」吗 |
|---|---|---|---|
| **压缩（compaction）** | 把早先的对话就地摘要，同一个 Agent 带着缩短的历史继续 | 是 | **不能** |
| **上下文重置（context reset）** | 清空窗口、起一个全新的 Agent，用结构化交接件传递状态 | 否 | **能** |

原因在于模型会感知到自己接近上下文上限，并因此在还没做完时就开始收尾。摘要过的历史仍然是「很长的历史」，这个感知不会消失；换一个干净的窗口才会。代价是重置需要一份足够完整的交接件，否则下一个 Agent 接不上。

### 3.5 子 Agent 与父 Agent 怎么互动

子 Agent 的价值在于**窗口隔离**：它用自己的上下文去啃一块任务（比如搜遍一个大仓库），只把结论带回父 Agent。父 Agent 不需要看到那一大堆中间过程。

代价也在这里：**父 Agent 只拿到摘要，而摘要是会丢信息的**。所以「子 Agent 说的」和「实际发生的」之间的差距，是一个需要留意的地方——需要精确信息时，宁可让父 Agent 直接读原始内容。

（多 Agent 的失败模式与分工取舍，已在 [1.3 构建 Agentic 系统](../part-1-ai-applications/03-构建Agentic系统.md) 展开，这里不重复。）

### 3.6 失败模式的清单与可观测信号

把 Ng 的四种失败模式补上实测中观察到的形态，可以得到一张可用于诊断的表：

| 失败模式 | 表现 | 通常的原因 |
|---|---|---|
| **过度设计** | 一个简单改动引入了抽象层、配置项、扩展点 | 它在按「完整方案」的模板产出，而不是按你的最小需求 |
| **缺少验证而失去严谨** | 改了代码、跑了单元测试，但从没验证端到端能用 | 你没把「怎么算完成」给它，它就按最省事的标准收尾 |
| **中途停下** | 做了一部分就宣布任务完成 | 上下文焦虑；或它认为已满足你给的（过弱）判据 |
| **破坏性动作** | 删文件、改生产数据、强推分支 | 权限过宽（见 [3.2](02-赋予Agent自主性.md)） |
| **自信地自评** | 交付一份平庸的东西并说做得很好 | 自评不可靠，这是结构性的（见 §4.2） |

最后一条不属于 Ng 的四项，但同样常见，而且它和其他几条相互作用：**如果「完成」由 Agent 自己判定，那它上面列的每一条都会更容易发生。**

## 4. 深入原理

### 4.1 长任务的两个失败模式，有官方实测

Anthropic 在公开的 harness 研究里，把长时运行 Agent 的问题归到两个根因，两个都很具体：

**一、上下文焦虑（context anxiety）。**

> "Some models also exhibit 'context anxiety,' in which they begin wrapping up work prematurely as they approach what they believe is their context limit."
>
> 一些模型还会表现出「上下文焦虑」——当它们接近自己所认为的上下文上限时，就开始提前把工作收尾。

这个描述值得细读：它说的是模型**自己认为**的上限。也就是说，行为由模型对剩余空间的感知驱动，而不是由实际还剩多少空间驱动。Anthropic 明确说了实测强度：Sonnet 4.5 上这个现象强到**单靠压缩不够用**，必须引入上下文重置。

顺带解释了 §3.4 里那张表的结论为什么成立：**压缩保留的是连续性，不是干净的状态。**

**二、自评偏差（self-evaluation bias）。**

> "When asked to evaluate work they've produced, agents tend to respond by confidently praising the work — even when, to a human observer, the quality is obviously mediocre."
>
> 当被要求评价自己产出的工作时，Agent 倾向于自信地称赞它——即便在人类观察者看来，质量显然平庸。

这一条在主观任务上最严重（设计、文案），但 Anthropic 指出**在有可验证结果的任务上它同样会干扰表现**。他们的解法是把做事的 Agent 和判事的 Agent 分开，并且诚实地说明了局限与收益：

> 分离开「并不能立刻消除那种宽容」——评审者仍是 LLM，仍然倾向于对 LLM 的产出给出好评。但**把一个独立评审者调教成爱挑刺，比让生成者批判自己容易得多**；而且一旦有了外部反馈，生成者就有了可以对照迭代的具体东西。

出处：Anthropic Engineering, [*Harness design for long-running application development*](https://www.anthropic.com/engineering/harness-design-long-running-apps) 与 [*Effective harnesses for long-running agents*](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

### 4.2 harness 决定上限，不是模型

Anthropic 的第一句结论就是这个：

> "Harness design is key to performance at the frontier of agentic coding."
>
> 在 agentic 编程的前沿，harness 设计是性能的关键。

他们的做法里，最可迁移的不是多 Agent 架构，而是**把状态从模型里搬出去、放进文件**。具体形态：一个初始化的 Agent 把规格拆成一份结构化的**功能清单**（每一项初始标为「未通过」）、建好仓库并写下启动脚本与进度日志；之后的编码 Agent 每次会话只做一件事，并且**每次会话都从同一个固定流程开始**——读 git 日志与进度文件、挑一个未完成的功能、把开发环境跑起来、先做一次基本冒烟测试，然后再动代码。

两个细节值得单独记住：

- **功能清单用 JSON 而不是 Markdown**。理由是模型更不容易去不当修改结构化数据——**它对自己写的散文更宽容**。这不是格式偏好，是在给「自评偏差」上枷锁。
- **不明确要求，它就不会端到端验证**。Anthropic 的观察是：不额外提示时，模型会改代码、甚至跑单元测试，但**不会去验证功能是否真的可用**；给它可以操作浏览器的工具、并明确要求「像真实用户那样测」，效果显著变好。

以及一条他们自己留白的地方，值得引用，因为它精确地说明了这部分的现状：**目前仍不清楚在各类场景下是单个通用编程 Agent 表现最好，还是多 Agent 架构更好。** 这与 1.3 里 Anthropic 与 Cognition 的分歧是同一个悬而未决的问题。

### 4.3 为什么「自评」不可靠，而换个评审者就可行

这里可以把两条线接起来。

[3.3](03-审阅产出.md) 里 OpenAI 的那个案例——Agent 发现测试只检查某个函数，于是把 `verify` 改成永远返回 `true`——说明的是同一件事的另一面：**你给的判据就是它的目标**。自评之所以不可靠，不只是因为它偏乐观，还因为它有动机（或被训练成）把「我做完了」这个判断做得对自己有利。

把评审者换成另一个实例，收益来自两点：**判据被外化成了具体反馈**（生成者有了可迭代的对象，而不是一个笼统的「再检查一下」），以及**宽容度是可调的**——调教一个独立评审者去挑刺，是可优化的问题；让生成者对自己苛刻，几乎不是。

### 4.4 为什么「过度设计」是高频失败

Ng 把它列在失败模式的第一位。机制上它有一个很清楚的理由。

模型产出代码时可用的最强线索是**它读到的代码**（见 [3.4 §4.3](04-定制Agent与环境.md)）。当需求描述得笼统时，它要去补全那些没被说出口的部分，而补全的方向是「一个完整的、看起来专业的实现」——抽象层、配置项、扩展点都属于这个方向的产物。

**这正好与 [3.4 §4.1](04-定制Agent与环境.md) 的实验结果互为印证**：上下文文件里每一条不必要的要求都会被认真执行。过度设计可以理解为「模型自己给自己写了一堆不必要的要求」，而没有人告诉它哪些是不必要的。

因此处方不在 prompt 里劝它「简单一点」，而在两处：**把最小需求说清楚**，以及**让代码库里没有可模仿的过度设计**。

## 5. 能力检查点

1. 我能说明一个 Agent 由哪四个部件构成，并把一次具体的失败定位到其中某一个部件。
2. 我能描述 Agent 找代码的方式，并解释为什么手写的目录导览收益有限。
3. 我能列出占用上下文窗口的主要几项，并指出哪几项是任务开始前就已付出的成本。
4. 我能区分压缩与上下文重置，并说明哪一个能解决「提前收尾」、为什么。
5. 我能说明子 Agent 的窗口隔离带来什么收益、付出什么代价。
6. 我能解释「上下文焦虑」为什么是模型对剩余空间的**感知**问题，而不是真实容量问题。
7. 我能说明为什么高强度的模型自评不可靠，并解释把评审者独立出来为什么是可行的修法。
8. 我能说出把功能清单做成结构化数据而不是散文的理由。
9. 我能解释「过度设计」的成因，并说明为什么在提示词里劝它简化不是有效处方。
10. 我能针对一次失败的运行，判断该给的是指令还是上下文，并说明依据。
