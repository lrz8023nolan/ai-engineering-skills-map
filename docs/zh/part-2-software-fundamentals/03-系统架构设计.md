# 2.3 系统架构设计（Designing system architectures）

> **Part 2** · 软件工程基础
> **状态** · 已完成
> **最后更新** · 2026-09-14

---

## 1. 概述

系统架构设计，指的是决定**一个系统由哪些部分组成、边界划在哪里、状态放在哪一层、以及每一块的粒度多大**。

它不是画图，而是一连串取舍。而且这些取舍的前提会变——用户量变了、延迟要求变了、成本约束变了，原本对的架构就可能变成错的。所以这项技能的核心不是记住某种「正确答案」，而是**知道每种选择在换什么**，以及**什么时候该重新评估**。

不掌握它，最典型的后果有两种。一种是**在还不需要的时候引入复杂度**：一个内部工具被拆成八个微服务，运维成本远超业务价值。另一种更隐蔽、也更常见——**把架构当成可以「以后再说」的事**。事实上架构是系统里最难事后调整的一层：数据边界、服务边界、状态归属，这些一旦被大量代码依赖，改动成本就呈指数上升。Ng 说编程 Agent 能帮上忙，但工具解决的是"改得快不快"，不是"知道该改成什么"。

## 2. 图谱中的定位

这是 Part 2 五个子技能中的第三个。吴恩达先说明了它的前置条件——你得先理解全栈和数据，才有资格判断怎么拼：

> "When you understand the major components of the full stack of software and data, you are then better positioned to decide how to put the pieces together."
>
> 当你理解了软件与数据的全栈主要组件之后，你才更有能力判断该如何把这些部分拼在一起。

他列出的架构决策清单：

| 决策 | 要回答的问题 |
|---|---|
| 应用平台 | 跑在什么之上？自建、云主机还是托管服务？ |
| 前后端边界 | 哪些逻辑放前端、哪些放后端？ |
| 系统拆分 | 分成几个部分？边界划在哪？ |
| 状态放置 | 状态存在哪一层？ |
| 架构粒度 | 单体还是微服务？ |
| 技术栈 | 语言、运行时、框架、数据技术 |

他强调这些判断的前提是**先理解软件要做什么**——「有多少用户？延迟有多重要？成本有多重要？」——然后才谈得上选择。

而这一节最关键的一句是：

> "Further, the right architecture is a moving target, depending on the phase of the project."
>
> 而且，正确的架构是一个移动的目标，取决于项目所处的阶段。

出处：[AI Engineering Skills Map Part 3，2026-08-28](https://www.deeplearning.ai/the-batch/the-ai-engineering-skills-map-in-detail-software-engineering-fundamentals)

## 3. 核心概念

### 3.1 先问需求，再谈架构

架构选择的第一性问题不是技术，而是**这套软件要达成什么**：

| 问题 | 影响的选择 |
|---|---|
| 有多少用户？增长率多少？ | 要不要为规模提前设计 |
| 延迟有多重要？ | 缓存层、就近部署、同步 vs 异步 |
| 成本有多敏感？ | 自建 vs 托管、单机 vs 分布式 |
| 团队多大？ | 服务拆分的粒度上限（见 §4.2） |
| 数据一致性要求多强？ | 能不能接受最终一致 |
| 预期寿命多长？ | 值得投入多少前期设计 |

**没有这些答案，任何架构讨论都只是偏好之争。**

### 3.2 单体与微服务

| | 单体 | 微服务 |
|---|---|---|
| **部署** | 一个单元 | 各自独立部署 |
| **团队** | 一个团队协作 | 每个服务可由独立团队负责 |
| **跨模块调用** | 进程内函数调用 | 网络调用（会失败、有延迟） |
| **事务** | 数据库事务即可 | 需要分布式事务或补偿 |
| **调试** | 一个进程，栈清晰 | 跨多个服务，需要链路追踪 |
| **早期速度** | 快 | 慢（要先搭基础设施） |
| **规模化** | 整体扩容 | 按需扩容热点服务 |

**关键认识：微服务的代价不是"多写几个服务"，而是把进程内调用换成了网络调用。** 后者会失败、有延迟、有部分成功，因此需要重试、超时、幂等、链路追踪、服务发现——这一整套基础设施是微服务的隐含成本。

### 3.3 拆分的依据：按什么划线

这是架构设计里最难也最重要的一步。几种常见的划线方式：

| 依据 | 例子 | 问题 |
|---|---|---|
| 按技术层次 | 前端服务 / 业务服务 / 数据服务 | 一次需求变更往往横跨所有层，耦合反而更强 |
| 按业务流程步骤 | 接单 → 处理 → 通知 | 步骤之间的数据依赖会强制同步调用 |
| **按可能变化的决策** | 把"价格怎么算"、"用户怎么存"分别封起来 | 需要一个模块承担变化的主要冲击（见 §4.1） |
| 按团队边界 | 每个团队负责端到端的一块 | 与康威定律一致（见 §4.2），但可能牺牲技术合理性 |

### 3.4 状态放在哪里

| 位置 | 优点 | 缺点 |
|---|---|---|
| **数据库** | 持久、可查询、可备份 | 每次访问有延迟 |
| **服务进程内** | 极快 | 无法水平扩展；重启就丢 |
| **分布式缓存** | 快、可共享 | 有失效问题（见 [2.1 §4.2](01-全栈应用构建.md)） |
| **客户端** | 完全不占服务端资源 | 不可信；可能被篡改 |

**一条实用的规则：能让服务无状态就无状态。** 无状态的服务可以随意增删实例，这是水平扩展的前提。状态集中到数据库或缓存，代价是引入一次网络访问。

### 3.5 技术栈的选择方法

Ng 提到一个容易被忽略的做法：**「有时通过跑实验来评估选项，然后再定下来」**。

这值得单独说——技术栈选择经常被当成信仰之争（哪种语言更好、哪个框架更先进），而它其实**可以是一个可测量的实验**：拿真实的一个关键场景，用两个候选方案各实现一遍，比较开发和运行的实际表现。这比任何基准测试都更贴近你的真实情况。

### 3.6 架构随阶段演进

| 阶段 | 合适的架构 | 原因 |
|---|---|---|
| **原型** | 最简单能跑的方式，通常单机单体 | 目标是验证可行性，不是承载规模 |
| **首个生产系统** | 加上部署、监控、备份、基础隔离 | 开始有真实用户，需要可用性 |
| **规模化** | 拆分热点、引入缓存与副本、可能拆服务 | 瓶颈出现，需要针对性扩展 |

**这里有一个需要警惕的反模式：为第三个阶段设计第一个阶段。** 在还不知道瓶颈在哪的时候就做拆分，成本是确定的、收益是假想的。反过来也有风险：**假设"以后可以重构"**——如果数据边界被大量代码依赖，重构的成本可能高到永远做不了（见 §4.5）。

### 3.7 分布式计算的八条谬误

这些是新手最容易默认成立、而在分布式系统里全都不成立的假设：

| 谬误 | 现实 |
|---|---|
| 网络是可靠的 | 会丢包、会超时、会部分成功 |
| 延迟是零 | 跨机房往返可能几百毫秒 |
| 带宽是无限的 | 大对象传输会成为瓶颈 |
| 网络是安全的 | 内网也会被攻破 |
| 拓扑不会变 | 节点增删、扩缩容是常态 |
| 只有一个管理员 | 多人多团队会同时改配置 |
| 传输成本是零 | 跨区流量是真实账单 |
| 网络是同构的 | 不同机房、不同云、不同协议 |

（这组表述源自 Waldo 等人 1994 年的 *A Note on Distributed Computing* 与后续整理）

## 4. 深入原理

### 4.1 Parnas 1972：按信息隐藏拆分，而不是按流程图

这是软件架构史上最重要的一篇论文，只有五页：

> Parnas, *On the Criteria To Be Used in Decomposing Systems into Modules*, Communications of the ACM 15(12), 1972

他做了一个看似平凡的演示：拿一个 KWIC 索引生成器（输入若干行，输出所有循环移位并排序），**用两种方式各拆一遍**。

| 拆法 | 依据 | 模块 |
|---|---|---|
| **方式一（流程图）** | 按处理步骤 | 输入、循环移位、字母排序、输出、主控 |
| **方式二（信息隐藏）** | 按**可能变化的设计决策** | 行存储（隐藏数据怎么存）、循环移位（隐藏移位怎么表示）等 |

两种拆法**模块数量相同、名字相似、表面看起来一样干净**。区别只在面对变更时：

- 把行的存储方式从数组改成链表：方式一要改几乎所有模块（因为它们都直接操作共享数组）；方式二**只改行存储模块**。
- 把排序算法换掉：方式一改排序模块，还要改所有依赖排序结果索引的模块；方式二只改一个。

Parnas 的原话是：

> "It is almost always incorrect to begin the decomposition of a system into modules on the basis of a flowchart."

**为什么这条至今仍是反直觉的**：流程图描述的是**执行顺序**，而执行顺序恰恰不是变化发生的地方。人们在画架构图时仍然习惯按「请求进来 → 处理 → 存储 → 返回」切分，而这正是 Parnas 指出会出问题的切法。

**怎么用**：划模块边界前先问一句——**「哪一部分最可能变？」** 把最容易变的那件事封进一个模块，让它的变化不外溢。五十年前的 KWIC 和今天的微服务在这一点上完全同构：每个服务独享自己的数据库、拒绝外部直连，就是在跑 Parnas 那个实验。

> 一个值得知道的后续：Fred Brooks 在《人月神话》第一版里对信息隐藏持怀疑态度，后来公开纠正——「Parnas 是对的，我在信息隐藏这一点上错了。」

### 4.2 康威定律：架构会反映组织

> "organisations which design systems are constrained to produce designs which are copies of the communication structures of these organisations."
>
> 设计系统的组织，其产出会被约束为这些组织沟通结构的复制品。

> Conway, *How Do Committees Invent?*, Datamation 14(4), 1968

这条定律的含义是：**架构不只是技术决策，也是组织决策。** 如果两个模块必须紧密协作，但负责它们的团队几乎不沟通，那么无论架构图上怎么画，这两个模块之间的接口都会退化成"扔过去就不管"。

由此得出一条实用推论：**要么让团队边界与你想得到的架构边界一致，要么接受得到的架构会向组织边界收敛。** 这也是「按团队边界拆分服务」这种做法的合理性来源——它是顺着康威定律走，而不是对抗它。

反过来说，如果技术上有明确的拆分理由（比如某块的计算特性完全不同），却不调整团队结构，那这个拆分大概率会失败。

### 4.3 微服务不是默认答案：一个公开的回归案例

微服务常被当作"更先进"的做法，但公开的工程案例显示它可以反过来走。

2023 年，AWS 官方博客发布了一篇被广泛讨论的文章：Amazon Prime Video 的音频/视频监控服务在从微服务架构**改回单体**之后，成本降低了约 90%。

值得注意的不是"单体更好"，而是**他们改回去的理由**：那个服务的负载特点是大量组件之间存在高度耦合的通信，拆成微服务后，每一步编排、每一次跨服务调用的数据量都被放大了。**在这种访问模式下水，微服务的抽象没有带来任何收益，只带来了开销。**

**这条对架构判断的实际价值**：微服务的收益来自"各部分的伸缩需求和控制频率不同"，代价是"把进程内调用换成网络调用"（见 §3.2）。如果几个组件**总是同时伸缩、总是需要一起改**，那拆分就是在只付代价不拿收益。

### 4.4 「分布式单体」：最坏的组合

一个需要专门记住的反模式：**拆成了一堆服务，但它们之间高度耦合，必须同时部署、同时修改。**

结果是你同时得到了两边的缺点：

| 来源 | 得到的缺点 |
|---|---|
| 微服务 | 网络调用的不可靠、分布式调试、运维复杂度 |
| 单体 | 紧耦合、改一处要动多处、无法独立部署 |

**判据很简单**：如果你改一个需求需要同时改三个服务并一起部署，那你实际上没有微服务，只有"部署起来更麻烦的单体"。这种状态往往不是有意设计的，而是拆分依据选错（见 §3.3）之后自然演化出来的。

### 4.5 「以后可以重构」是一个危险的假设

Ng 说正确的架构是**移动的目标**，这句话隐含了一个常见误解：既然架构会变，那先随便搭、以后再调就行了。

问题在于**架构的改动成本不是线性的，而是随依赖数量系统性上升的**：

| 依赖程度 | 改动成本 |
|---|---|
| 只有代码依赖 | 改代码、测试、发布 |
| 数据边界被依赖 | 需要数据迁移（见 [2.2 §4.6](02-数据管理.md)） |
| 接口被外部系统依赖 | 需要版本演进、双写、灰度 |
| 被大量第三方依赖 | 实际上不可改 |

**所以"以后再说"的合理范围，只限于那些还没有外部依赖的部分。** 一旦某个边界被发布出去（对外 API、被写入的数据、被别的服务消费的消息），它就从"可重构"变成了"不可逆"。

实践上的推论是：**在还不确定的地方，优先选择最难改的那一层做得保守一些。** 具体说，数据边界和对外接口值得多花时间想清楚，而内部实现、框架选型、部署方式都可以后调——因为前者不可逆，后者可以。

### 4.6 分布式计算的八条谬误

§3.7 那张表值得当作一份检查清单来用，因为**每一条谬误都对应一类只在分布式下出现的 bug**：

| 谬误 | 对应的真实故障 |
|---|---|
| 网络可靠 | 没有超时和重试逻辑，请求挂死 |
| 延迟为零 | 同步调用串起来，延迟累加 |
| 带宽无限 | 大响应体拖垮下游 |
| 网络安全 | 内网明文传输被窃听 |
| 拓扑不变 | 硬编码 IP，扩容后失效 |
| 一个管理员 | 配置冲突 |
| 传输成本为零 | 跨区流量账单失控 |
| 网络同构 | 假设了某个云的特性，换环境就崩 |

**这八条的价值在于它解释了为什么"本地跑得好、上线就出问题"。** 单机环境下这八条全部成立，所以单机测试无法暴露它们——这也是 §4.1 里那个实证结论（大多数严重故障来自没被测过的代码路径）的前提。

### 4.7 让架构决策可追溯

架构决策的特点是：**理由会随时间流失，而结论会留下。** 三个月后没人记得为什么当初选了这个数据库，于是新来的人要么盲目沿用，要么推翻重来。

一个不做作的解决办法是把决策记录下来，每条包含：决策是什么、当时考虑了哪些选项、为什么选它、什么条件下应该重新评估。这种做法通常叫架构决策记录（ADR）。

它的价值不在形式，而在**「什么条件下应该重新评估」这一项**——它把 Ng 说的"移动的目标"变成了可操作的东西：不是等感觉不对了再改，而是事先写明触发条件。

## 5. 能力检查点

1. 我能说明架构选择必须以软件要达成的目标为前提，并列出至少四个会影响架构的需求维度。
2. 我能比较单体与微服务在部署、团队、跨模块调用、事务和调试上的差异，并指出微服务的隐含成本是什么。
3. 我能说明按技术层次、按业务流程、按变化点、按团队四种拆分依据各自的风险。
4. 我能解释为什么"能让服务无状态就无状态"，并说出状态集中在数据库或缓存的代价。
5. 我能复述 Parnas 关于模块拆分的核心结论，并解释为什么按流程图拆分是错的。
6. 我能用康威定律解释为什么架构不只是技术决策，并说明它的实用推论。
7. 我能给出一个微服务不如单体的公开案例，并说明判断拆分是否划算的依据。
8. 我能识别"分布式单体"的形态，并说明它为什么同时具备两边的缺点。
9. 我能区分架构中哪些部分是可逆的、哪些是不可逆的，并说明这个区分对决策顺序的影响。
10. 我能列出分布式计算的八条谬误，并说明它们如何解释"本地跑得好、上线出问题"。
