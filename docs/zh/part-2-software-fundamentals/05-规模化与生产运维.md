# 2.5 规模化与生产运维（Scaling and operating in production）

> **Part 2** · 软件工程基础
> **状态** · 已完成
> **最后更新** · 2026-09-14

---

## 1. 概述

规模化与生产运维，指的是**把软件真正交付给用户，并让它在负载增长时继续可用**——包括部署、发布、观测、扩容，以及让代码库在多年之后仍然可维护。

**先说与 [1.5 生产环境运维](../part-1-ai-applications/05-operating-in-production.md) 的分工**，这两节容易混：

| | 1.5 | 2.5（本节） |
|---|---|---|
| 视角 | **AI 系统特有的**运维 | **通用软件工程**的运维 |
| 核心问题 | 输出不可预测、成本随用量放大、质量会漂移 | 部署、发布、承载负载、长期维护 |
| 典型内容 | eval 接入 CI、漂移检测、模型路由、推理成本优化 | SDLC、发布策略、错误预算、扩容、代码审查、依赖维护 |

两者是同心圆：本节是外圈（任何软件都适用），1.5 是内圈（AI 特有的增量）。已经交叉引用的部分不再重复。

不掌握它，最典型的后果是**系统能上线但撑不住规模**——这不是因为某处代码写得不好，而是因为交付方式和运维方式从没被当作设计的一部分。比如：每次发布都要停机、出故障只能靠用户反馈发现、流量涨了只能整体加机器、或者三年后没人敢改代码因为不知道会崩哪里。

## 2. 图谱中的定位

这是 Part 2 五个子技能中的最后一个。吴恩达把它分成三块：

**第一块，交付**。要能执行完整的软件开发生命周期（SDLC）——除了构建和测试，还包括**配置部署环境、决定发布策略、应用部署自动化（CI/CD），以及理解基础设施即服务（IaaS）**。

**第二块，运维**。需要有可观测性工具、告警设置和事故管理。

**第三块，扩容**，这是他对技术细节写得最具体的一句：

> "to scale your application, you should understand the real load and know how to scale servers, load-balance, and adapt your data infrastructure (via sharding, indexing, replication) or make architecture changes to allow your system to adapt to scale."
>
> 要让应用扩展，你需要理解真实负载，并知道如何扩展服务器、做负载均衡、调整数据基础设施（通过分片、索引、复制），或者做架构变更让系统能适应规模。

最后他还点了一组容易被当成"软技能"而忽略的长期实践：**版本控制、代码审查、依赖维护，以及如何管理技术债**——「帮助你让系统随时间持续演进」。

出处：[AI Engineering Skills Map Part 3，2026-08-28](https://www.deeplearning.ai/the-batch/the-ai-engineering-skills-map-in-detail-software-engineering-fundamentals)

## 3. 核心概念

### 3.1 SDLC 的完整范围

| 阶段 | 包含什么 |
|---|---|
| 规划 | 需求、技术方案、风险评估 |
| 构建 | 编码、代码审查 |
| 测试 | 单元、集成、端到端（见 [2.4 §3.2](04-安全与可靠性.md)） |
| 配置环境 | 开发/预发/生产的差异管理；配置与代码分离 |
| 发布 | 发布策略、回滚方案、变更审批 |
| 自动化 | CI/CD 流水线 |
| 运行 | 监控、告警、值班、事故响应 |

**最容易被忽略的是"配置部署环境"**：开发环境能跑但生产跑不起来，绝大多数原因是环境差异——依赖版本、环境变量、网络策略、权限。**配置应该与代码分离并且可版本化**，这样"生产上到底跑的是哪套配置"才是一个能回答的问题。

### 3.2 发布策略

已在 [2.1 §3.5](01-全栈应用构建.md) 展开，这里只强调与本节的关联：**发布策略决定了失败的影响半径。** 金丝雀发布的价值不只是"稳"，而是把一次错误发布的影响范围限制在一小部分流量内——这与 [2.4 §4.6](04-安全与可靠性.md) 讲的影响半径是同一个思路，只是发生在时间维度上。

### 3.3 可观测、告警与事故管理

可观测性的技术细节见 [1.5 §3.1–3.2](../part-1-ai-applications/05-operating-in-production.md)。本节只补通用软件视角下必须知道的两条原则，见 §4.2（错误预算）和 §4.4（按症状告警）。

### 3.4 扩容之前先测量真实负载

吴恩达那句「理解真实负载」值得单独强调。扩容易犯的第一类错误是**没测准**：

| 要测量的 | 为什么 |
|---|---|
| 请求到达速率与峰值形态 | 平均值会掩盖峰值；容量是按峰值设计的 |
| 每次请求的资源消耗分布 | 不是所有请求一样重；少数重请求可能主导负载 |
| 延迟的尾部（p95/p99） | 平均值掩盖尾部的糟糕体验 |
| 瓶颈在哪一环 | 加错地方的机器是纯粹的浪费 |
| 增长的驱动因素 | 是用户数、数据量，还是某个特定功能？ |

**最后一条最关键**。不同的增长驱动因素对应完全不同的扩容方式：用户数增长靠加实例，数据量增长靠分片，某个功能变重靠优化那个功能。**没弄清是哪种，扩容就是在猜。**

### 3.5 负载均衡与水平扩容

水平扩容的前提是**实例之间可以互相替代**，而这要求服务无状态或把状态外置（见 [2.3 §3.4](03-系统架构设计.md)）。

| 机制 | 作用 |
|---|---|
| 负载均衡算法 | 轮询、最少连接、一致性哈希（同一用户/键固定到同一实例） |
| 健康检查 | 自动把坏掉的实例摘出流量 |
| 优雅关闭 | 实例退出前处理完在途请求 |
| 自动扩缩容 | 按指标自动增减实例 |
| 限流与队列 | 保护自己不被突发流量打垮 |

### 3.6 数据层的扩展

数据层比无状态服务难扩展得多，因为数据不能随意复制或丢弃。三种基本手段（细节见 [2.2](02-数据管理.md)）：

| 手段 | 解决什么 | 代价 |
|---|---|---|
| **索引** | 查询慢 | 写入变慢、占空间 |
| **复制** | 读扩展、容灾 | 复制延迟导致读到旧数据 |
| **分片** | 单机放不下、写扩展 | 跨片查询变复杂；重新分片是重活 |

**顺序通常是：先加索引，再加读副本，最后才分片。** 分片是这三种里成本最高、最难回退的，只有在前面两条都用尽时才该动。

### 3.7 让代码库可以长期维护

Ng 点到的这一组实践经常被当成"流程琐事"，但它们决定了三年后这个系统还能不能改：

| 实践 | 解决什么 |
|---|---|
| 版本控制 | 能回退、能追溯、能并行开发 |
| 代码审查 | 在合并前发现问题；同时是知识传递的主要渠道 |
| 依赖维护 | 依赖会腐化：有漏洞、有破坏性变更、有停止维护的 |
| 技术债管理 | 债会复利（见 [1.5 §4.1](../part-1-ai-applications/05-operating-in-production.md)） |

**依赖维护值得单独说**：依赖是**唯一一类你会被动获得新风险的东西**——你的代码没改，但你依赖的库被发现了一个漏洞。所以"更新依赖"不是可选动作，而是持续的维护成本。

## 4. 深入原理

### 4.1 速度与稳定性不是取舍，而是互相强化

这是整节最有反直觉价值的一条结论，而且有大规模的实证支撑。

> [Forsgren, Humble & Kim, *Accelerate: The Science of Lean Software and DevOps*, 2018](https://dl.acm.org/doi/10.5555/3235404)（基于 DORA 的多年研究）

DORA 研究用四个指标衡量软件交付性能：

| 指标 | 含义 |
|---|---|
| **部署频率** | 多久部署一次 |
| **变更前置时间** | 从提交代码到它在生产运行的时间 |
| **变更失败率** | 多大比例的部署导致了需要修复的问题 |
| **恢复时间（MTTR）** | 出故障后恢复要多久 |

精英团队与低绩效团队的差距非常具体：

| | 精英团队 | 低绩效团队 |
|---|---|---|
| 部署频率 | 按需，每天多次 | 每月或更低 |
| 变更前置时间 | 小于 1 小时 | 1–6 个月 |
| 变更失败率 | 0–15% | 46–60% |
| 恢复时间 | 小于 1 小时 | 一周到一个月 |

**关键发现是这四个指标彼此正相关。** 「部署更频繁」的团队，**同时**有更低的失败率和更快的恢复。直觉上这说不通——「发布多了当然更容易出错」——但数据是反过来的。

机制其实好理解：

| 环节 | 为什么 |
|---|---|
| 变更更小 | 一次部署只含 3 个提交 vs 300 个提交，出问题时知道去哪找 |
| 反馈更快 | 频繁部署意味着问题在几分钟内暴露，而不是几周后 |
| 定位更容易 | 问题出现在刚部署的小改动里，范围明确 |
| 回退更简单 | 回退一个小变更比回退一个大版本安全得多 |

**所以「为了稳一点，我们少发几次」是一个自我实现的失败策略**：更少的发布意味着更大的变更批量，更大的批量意味着更难定位的失败和更危险的回退。

### 4.2 错误预算：可靠性的正确目标不是 100%

一个常见的默认假设是"可靠性越高越好"。但 100% 可用意味着**任何变更都不能带来风险**，也就是不能变更——这在业务上不可接受。

> [Google, *Site Reliability Engineering*](https://sre.google/)

SRE 的做法是用**错误预算（error budget）**把这个矛盾变成可量化的决策：

**错误预算 = 1 − SLO**

例如 SLO 定在 99.9%，错误预算就是 0.1%，大约每月 43 分钟不可用。

| 预算状态 | 该做什么 |
|---|---|
| 预算充足 | 快速发布新功能 |
| 预算接近耗尽 | 暂停功能发布，转向可靠性工作 |

**这个机制的价值在于它把"开发想要速度、运维想要稳定"的对立，变成了一个共享的目标。** 不再是两个部门吵，而是"预算还剩多少"决定下一步做什么。同时它也承认了「100% 不是正确目标」——追求 100% 的成本远超用户能感知到的收益。

### 4.3 Toil 与 50% 上限

SRE 有个概念叫 **toil（苦役）**：手工的、重复的、可以被自动化但还没被自动化的运维工作。它的判定标准是：手工、重复、可自动化、战术性、不产生持久价值、且**随系统规模线性增长**。

Google 给的纪律是：**SRE 团队花在 toil 上的时间不应超过 50%。** 超过这个比例说明团队人手不足或自动化不足。

**这条判据的实用价值**在于它把"自动化"从"有空再说"变成了有阈值触发的硬要求。因为 toil 的特征就是它会在你忙的时候更容易堆积，而越堆积你越没空去自动化它——这是一个需要外部阈值才能打破的循环。

### 4.4 告警要基于症状，而不是原因

一条会显著影响你睡眠质量的原则：

| 告警对象 | 结果 |
|---|---|
| **原因**（CPU 高、磁盘用了 80%、某个进程重启了） | 你会被用户根本没察觉的事情叫醒，同时错过用户真正在意的事情 |
| **症状**（错误率上升、延迟超标、请求失败） | 只在用户真的受影响时被叫醒 |

原因是**原因与影响之间不是一一对应的**：CPU 跑到 90% 可能完全不影响服务；而 CPU 只有 40% 时错误率可能已经飙升（比如某个依赖挂了）。基于原因的告警看起来"更专业"，实际上制造了大量噪音，而噪音会让人开始忽略告警——那时真正的告警也就失效了。

**正确做法是：对症状告警，用原因去诊断。** 监控面板和日志留给排查阶段用，不要拿来触发呼叫。

### 4.5 负载均衡的两个隐藏陷阱

这两条不会在测试环境暴露，因为测试环境既没有真实流量，也没有实例上下线。

**陷阱一：健康检查 + 没有优雅关闭 = 请求被丢**

实例被摘出流量和实例停止服务之间，如果代码没有"处理完在途请求再退出"的能力，那么正在处理中的请求会被直接切断。用户看到的是随机的失败——而且只在部署或扩缩容时出现，所以极难复现。

**陷阱二：重试会放大故障**

这是级联故障最经典的成因：某个依赖变慢 → 调用方超时 → 调用方重试 → 依赖收到两倍请求 → 更慢 → 更多人超时重试……

```
正常：100 请求 → 依赖
变慢后：100 请求，其中 40 个超时重试 → 依赖收到 140
再慢一点：140 都变慢，70 个重试 → 210
...
```

**防御手段有两个组合起来才有效**：

- **重试要有上限和随机抖动（jitter）**——没有抖动的重试会让所有客户端在同一时刻再次冲击。
- **熔断器（circuit breaker）**：当下游连续失败到一定比例，直接停止调用它一段时间，快速失败而不是继续堆积。这既保护下游，也让调用方不用白白等超时。

### 4.6 自动扩缩容不能修复慢查询

一个容易走错的排查路径：看到延迟升高 → 看 CPU 高 → 加实例。

问题在于**扩容解决的是"并发量超过处理能力"，不解决"单个请求变慢了"**：

| 症状 | 正确的排查方向 |
|---|---|
| 并发量涨了，延迟涨了，CPU 也涨了 | 扩容有效 |
| 并发量没变，延迟涨了，CPU 涨了 | **单个请求变重了**——去查慢查询、N+1、锁竞争 |
| 并发量没变，延迟涨了，CPU 没变 | 瓶颈在 IO 或外部依赖——扩容无用 |

**第二种情况下加机器只会摊薄同样的问题**，成本上升而用户感受不变。这又回到了 §3.4 的第一条：**先测量真实负载，再决定扩什么。**

### 4.7 依赖维护是持续成本，不是一次性任务

依赖是软件里一个特殊的存在：**它是唯一一类你会被动获得新风险的东西。**

| 事实 | 含义 |
|---|---|
| 你的代码没改，但你依赖的库被发现漏洞 | 风险是外部注入的 |
| 依赖会发布破坏性变更 | 不升级也会被生态抛下 |
| 依赖会停止维护 | 今天能用的库，三年后可能没人修了 |
| 依赖的依赖也算你的风险 | 供应链的深度通常是几十层 |

**实践上要做三件事**：

1. **锁定版本**（用锁文件），保证构建可复现——否则"昨天还能构建"会变成一句无法解释的话。
2. **持续扫描**已知漏洞，并明确修复的时限。
3. **定期主动升级**，而不是攒到必须升的那天一次性跳几个大版本——后者是最危险的升级方式。

## 5. 能力检查点

1. 我能说明通用的生产运维与 AI 特有的运维各自关注什么，以及为什么不能混为一谈。
2. 我能列出 SDLC 的完整阶段，说明「配置部署环境」为什么最容易被忽略，并说明发布策略与影响半径的关系。
3. 我能列出扩容前必须测量的至少四项内容，并说明为什么"增长由什么驱动"最关键。
4. 我能说明水平扩容的前提条件，以及负载均衡、健康检查、优雅关闭各自的作用。
5. 我能说出数据层扩展三种手段的代价，并说明它们的合理应用顺序。
6. 我能复述 DORA 的四个指标及其精英团队的基准，并解释为什么速度与稳定性是互相强化的。
7. 我能解释错误预算如何把开发与运维的对立变成共享目标，并算出 99.9% SLO 对应的月度不可用时间。
8. 我能举例说明为什么告警应该基于症状而不是原因。
9. 我能说明重试为什么会导致级联故障，以及需要哪两个手段配合才能防御。
10. 我能区分"并发量超载"与"单个请求变慢"两种情况，并说明为什么后者扩容无效。
