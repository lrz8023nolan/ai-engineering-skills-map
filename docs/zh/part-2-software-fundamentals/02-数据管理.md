> **状态** · 已完成

---

## 1. 概述

数据管理，指的是**决定存什么、存多久、存在什么结构里、以及怎么保证它一直是干净且一致可用的**。

它值得单独拎出来讲，原因很朴素：**数据是整个系统里最难改的一层。** 代码可以重写，界面可以重做，架构可以逐步演进——但数据结构和数据本身一旦积累起来，改动就变成了迁移，而迁移是有风险的、需要停机或双写的、并且往往无法完全自动化。哪怕是编程 Agent 也帮不了多少：它能写出迁移脚本，但**"这个字段当初为什么这么设计"这种上下文，只存在于人的脑子里。**

不掌握它，最典型的后果是**早期的一个数据模型决策，把后面所有的功能都锁死了**。想加一个新查询，发现现有结构根本支持不了，只能写一堆拼凑的代码；想扩规模，发现当初选的存储类型在并发下退化成串行。这类问题的特征是：**它们不会在开发阶段暴露**，因为开发环境的数据量和并发量都小到可以掩盖任何结构缺陷。

## 2. 图谱中的定位

这是 Part 2 五个子技能中的第二个。吴恩达在这一节给了一个完整的清单：

- 想清**访问模式**，据此决定存什么、存多久
- 识别正确的**数据模型**，选择合适的**存储类型**（关系表、文档、键值、图）与基础设施——这反过来影响速度、可扩展性、可用性、可靠性与成本
- 理解**事务与并发**，保证数据干净、一致、新鲜
- 在需要时保证**隐私、治理与合规**
- 管理**数据生命周期**
- 随着应用演进，**让数据架构跟着演进**

而这一节最值得记住的是他指出的 AI 特定后果：

> "Your AI systems will get their own input context from your data source, so if data architecture is chosen poorly, the AI doesn't know what it doesn't know."
>
> 你的 AI 系统会从你的数据源里取得它自己的输入上下文；所以如果数据架构选得不好，AI 不知道它自己不知道什么。

出处：[AI Engineering Skills Map Part 3，2026-08-28](https://www.deeplearning.ai/the-batch/the-ai-engineering-skills-map-in-detail-software-engineering-fundamentals)

## 3. 核心概念

### 3.1 先想访问模式，再选存储

这是全篇最重要的顺序。**不要先问"我要用哪种数据库"，要先问"数据会被怎么读写"。**

| 要回答的问题 | 影响 |
|---|---|
| 谁读、谁写？读写比例如何？ | 决定要不要反规范化、要不要读副本 |
| 每次读的时候，**在什么维度上做筛选**？ | 决定索引与分区键 |
| 单条记录会被频繁更新吗？ | 决定存储类型的适配度 |
| 需要跨实体查询吗？ | 决定要不要关系型、要不要图 |
| 数据量增长曲线是什么样？ | 决定分片策略与成本模型 |
| 一致性要求有多强？ | 决定能不能接受最终一致 |

**访问模式决定数据模型，而不是反过来。** 反过来做（先定表结构，再想办法满足查询）是绝大部分性能事故的根源。

### 3.2 四种存储类型与判据

| 类型 | 数据形状 | 强项 | 弱项 |
|---|---|---|---|
| **关系型** | 表、行、列，带约束与连接 | 跨实体查询、事务、约束与数据完整性 | 水平扩展较难；模式变更需要迁移 |
| **文档型** | 自包含的文档（JSON 类） | 单文档读写快；模式灵活 | 跨文档查询与多文档事务较弱 |
| **键值型** | 键 → 值 | 极快、极易扩展 | 只能按主键访问；无法做范围查询与关系查询 |
| **图型** | 节点 + 边 | 多跳关系查询 | 生态与工具相对少；不适合简单访问模式 |

**这四类不是代际替代关系，而是适配不同访问模式的工具。** 一个系统里完全可以同时用多种——比如核心业务数据放关系型、会话放键值、推荐关系放图。

### 3.3 数据模型：规范化与反规范化

| | 规范化 | 反规范化 |
|---|---|---|
| **做法** | 每份数据只存一处，通过引用关联 | 故意重复存储，减少连接 |
| **好处** | 更新一致；不容易出现矛盾 | 读取快；查询简单 |
| **代价** | 读取需要连接，复杂查询变慢 | 更新要同步多处，容易不一致 |

**反规范化是有意的交易，不是设计失误。** 判断依据是读写比例：读多写少且对延迟敏感时，反规范化的收益明确；写多或对一致性要求高时，它带来的同步负担会超过收益。

需要留意的是：**反规范化把"保证一致"的责任从数据库转移到了应用代码上。** 数据库不再能帮你防止矛盾，你得自己保证。

### 3.4 事务与并发

**事务**是一组操作要么全做、要么全不做的单位。它的四个保证通常合称 ACID：原子性、一致性、隔离性、持久性。

**隔离性是最微妙的一个**，因为它不是一个开关，而是一组级别，每个级别允许某些并发异常存在：

| 隔离级别 | 允许出现的异常 |
|---|---|
| 读未提交 | 脏读、不可重复读、幻读 |
| 读已提交 | 不可重复读、幻读 |
| 可重复读 | 幻读（在标准定义下） |
| 可串行化 | 无（代价是并发性能最低） |

选择级别本质上是**在"正确性"与"并发吞吐"之间做交易**。级别越高越安全，但锁竞争越多、吞吐越低。

### 3.5 一致性、可用性与分区

这是分布式数据系统的经典三角形，**但它被广泛误读**（详见 §4.1）。正确的读法是：

- 三个性质是**一致性（C）、可用性（A）、分区容忍性（P）**
- **P 不是可以放弃的选项**——网络分区在分布式系统里必然会发生
- 因此真正的取舍发生在 **C 和 A 之间，且只在分区发生期间**
- 没有分区的时候，你完全可以同时拥有 C 和 A

### 3.6 数据质量：三件事

吴恩达用了三个词：**干净（clean）、一致（consistent）、新鲜（fresh）**。可以拆成三组具体的工程动作：

| 维度 | 要处理的问题 | 手段 |
|---|---|---|
| **干净** | 缺失值、格式不一、单位混乱、明显错误的取值、重复记录 | 入库校验、约束、清洗管线、去重 |
| **一致** | 同一事实在两处不同、跨表引用失效、时序矛盾 | 事务、外键约束、单一写入路径 |
| **新鲜** | 上游更新了但下游没跟上、缓存比源数据旧 | 变更捕获、增量同步、新鲜度监控 |

**一个容易被忽略的原则：质量要在源头保证，而不是在下游修补。** 下游清洗永远在猜上游的意图，而猜错的成本会一路传导到最终结果。

### 3.7 数据生命周期

数据不是只有"存"和"删"两种状态。完整生命周期包括：创建 → 活跃使用 → 冷存 → 归档 → 销毁。

| 阶段 | 要做的决策 |
|---|---|
| 创建 | 校验规则、必填字段、默认值 |
| 活跃 | 索引策略、访问控制、备份频率 |
| 冷存 | 何时降级到更便宜的存储 |
| 归档 | 是否需要保留查询能力；保留多久 |
| 销毁 | 如何确保真的删掉了（含备份与副本） |

**"保留多久"是一个必须显式回答的问题**，因为它同时受业务需求和合规要求约束（见 §3.8）。

### 3.8 隐私、治理与合规

| 关注点 | 具体内容 |
|---|---|
| **数据分类** | 哪些是个人数据、敏感数据、可公开数据 |
| **访问控制** | 谁能读、谁能写、谁只能聚合查看；是否要字段级权限 |
| **可删除性** | 用户要求删除时，能否真正删干净（含衍生数据、备份、日志） |
| **可导出性** | 用户要求导出自己数据的权利 |
| **最小化** | 只收集确实需要的字段 |
| **审计** | 谁在什么时候访问了什么 |
| **合规** | 按目标市场遵守相应法规（如欧盟 GDPR、中国《个人信息保护法》） |

**"可删除性"是最容易被低估的一项。** 如果数据被复制到了缓存、搜索索引、数据仓库、日志里，那么"删除"就变成了一次跨系统的协同作业——而且必须在设计阶段就想好，事后补不上。

### 3.9 让数据架构跟着应用演进

应用会变，数据架构必须能跟着变。三种演进方式：

| 方式 | 做法 | 风险 |
|---|---|---|
| **渐进式迁移** | 新旧结构并存，逐步切换读写路径 | 周期长，期间两套逻辑并存 |
| **双写 + 回填** | 同时写新旧两处，历史数据回填 | 双写期间的失败处理复杂 |
| **一次性迁移** | 停机迁移 | 简单，但要求可停机 |

**共同点是：迁移是数据管理里最难的一部分，而且它的难度随数据量增长而非线性增长。** 这也是为什么"当初的选择"如此重要——你选择的不是今天的成本，而是未来所有迁移的难度上限。

### 3.10 为 Agent 建数据基础设施

这是吴恩达单独点出的、仍在快速演化的领域。传统数据架构假设的消费者是**人和应用代码**，两者都不太在意数据组织得是否"对模型友好"。而 Agent 是第三种消费者：

| 维度 | 对人/代码 | 对 Agent |
|---|---|---|
| 数据组织 | 表结构、接口 | 语义化的文档切块、可检索的表示（见 [1.2 用数据锚定模型](../part-1-ai-applications/02-用数据锚定模型.md)） |
| 访问方式 | 明确的查询 | 模糊的自然语言意图 |
| 失败表现 | 报错或空结果 | **给出看似合理的错误答案** |

最后一行是关键：**传统消费者在数据缺失时会失败得很明显，Agent 不会。** 它会用同样的自信语气，基于不完整的数据给出一个答案。这就是吴恩达那句"AI 不知道它自己不知道什么"的具体含义。

## 4. 深入原理

### 4.1 CAP 被误读了十年，原作者自己出来纠正

"三选二"这个说法流传极广，**而它是错的**。Brewer 本人在 2012 年专门写了文章纠正这一点：

> Brewer, *CAP Twelve Years Later: How the "Rules" Have Changed*, IEEE Computer 45(2), 2012 — [DOI](https://doi.org/10.1109/mc.2012.37)

原定理（Brewer 2000 年提出猜想，Gilbert 与 Lynch 2002 年给出证明）说的是：**在出现网络分区的情况下**，一个分布式系统无法同时保证强一致性和可用性。

被误读成"三选二"之后，产生了三个具体错误：

| 误读 | 事实 |
|---|---|
| "可以从 P 里选掉一个" | P 不是选项——分布式系统里分区必然发生 |
| "必须永久放弃 C 或 A" | 取舍**只在分区发生期间**存在；正常情况下可以两者兼得 |
| "这个取舍定义了数据库的类型" | 现代系统在分区恢复后可以同时恢复一致性，所以不能用 CAP 给数据库贴"CP"或"AP"标签 |

**这条对工程的实际含义**：不要在选型时用"我们选 AP 所以允许不一致"来合理化设计，因为这句话本身是基于误读的。真正需要回答的问题是更具体的——**在分区期间，这个具体操作应该拒绝服务还是返回可能过期的数据**；以及分区恢复后，如何修补不一致。

> 相关：Kleppmann, *Please stop calling databases CP or AP*, 2015 对这一点有更细的论述。

### 4.2 隔离级别：标准定义本身是模糊的

关于"读已提交""可重复读"这些名字，一个容易被忽略的事实是：**SQL 标准对它们的定义是有歧义的，而且实践中各数据库的实现并不一致。**

这一点由一篇影响深远的论文指出：

> Berenson, Bernstein, Gray, Melton, O'Neil & O'Neil, *A Critique of ANSI SQL Isolation Levels*, SIGMOD 1995

该论文做了两件事：一是证明标准中用自然语言描述的隔离级别定义存在歧义（同一条定义可以解读出不同的实现），二是**提出了"快照隔离"（snapshot isolation）这一当时标准里不存在、但已被商业数据库广泛使用的隔离级别**。

**对工程的含义有两条**：

1. **不要假设"可重复读"在不同数据库里行为相同。** 同一个级别名，不同实现的语义可能有实质差别。选型或迁移时必须查具体数据库的文档。
2. **不要只按级别名判断安全性。** 你需要知道的是"在这个数据库的这个级别下，哪些具体的并发异常是可能的"，而不是一个笼统的级别名。

这类问题的危险在于它**不会报错**：你的代码在高并发下偶尔产生一次错误的余额或库存，而任何单次测试都通不过不了复现。

### 4.3 关系模型的真正贡献不是"表格"，而是数据独立性

1970 年那篇论文常被记成"提出了用表格存数据"。表格当然不是新东西。它真正的贡献在开篇第一句：

> "Future users of large data banks must be protected from having to know how the data is organized in the machine."
>
> 未来的大型数据库用户必须被保护起来，不必知道数据在机器内部是如何组织的。

> Codd, *A Relational Model of Data for Large Shared Data Banks*, Communications of the ACM, 1970

这就是**数据独立性**：物理独立性（应用不必知道数据怎么存）与逻辑独立性（应用不必知道逻辑结构怎么变）。在此之前，层次模型和网状模型要求程序员知道数据的物理位置和导航路径——**改一个字段的结构就可能要改大量程序**。

**这条对今天的意义**：当你评估一个数据方案时，真正要问的不是"它快不快"，而是**"它把多少结构细节暴露给了调用方"**。暴露得越多，未来改结构时你要改的代码就越多。这也是为什么 ORM、API 抽象层、语义层这类东西有价值——它们买的不是性能，是**可演进性**。

### 4.4 索引不是免费的

一个经典的取舍，但值得明确说出来：**每一个索引都会让写入变慢。**

| 加索引 | 不加索引 |
|---|---|
| 按该字段的查询变快 | 该查询退化为全表扫描 |
| 每次写入都要更新索引结构 | 写入更快 |
| 占用额外存储 | 节省空间 |

判断依据是读写比例与查询的临界性。**不要"觉得可能有用"就加索引**——在写密集的系统里，多余的索引会直接压低写入吞吐，而且这个代价不像查询那么直观可见。

### 4.5 写时模式 vs 读时模式

| | 写时模式（schema-on-write） | 读时模式（schema-on-read） |
|---|---|---|
| **校验时机** | 写入时 | 读取时 |
| **好处** | 数据质量在入口就有保证；结构明确 | 写入灵活，适合演进中的需求 |
| **代价** | 结构变更需要迁移 | 质量问题推迟到读取时才暴露 |

**这也不是优劣问题，而是把校验成本放在哪一端的取舍。** 一个实用的组合是：核心业务数据用写时模式保证质量，探索性/日志类数据用读时模式保持灵活。

### 4.6 迁移无法完全自动化：expand-contract

Ng 说数据"相对难以修改，**即使 Agent 能帮忙做迁移**"。这句话的分量在于：迁移的难点通常不在写脚本，而在**在不中断服务的前提下切换**。

一个被广泛采用的模式是 **expand-contract**：

| 阶段 | 动作 |
|---|---|
| **Expand** | 新增结构（新列/新表），同时保留旧的；代码同时兼容两者 |
| **Migrate** | 回填历史数据；逐步把读写切到新结构 |
| **Contract** | 确认没有代码再依赖旧结构后，删除它 |

关键在于**每一阶段都是可回滚的**，而且系统在整个过程中持续可用。代价是周期长，且中间状态需要维护两套兼容逻辑。

**把这个模式记住的实际价值是**：它让你在每次需要改数据结构时，有一个"不用停机"的默认方案，而不是被迫在"停机"和"凑合不改"之间二选一。

### 4.7 数据架构决定了 AI 能知道什么

回到吴恩达那句最关键的话。把它展开成工程含义，有三层：

1. **AI 的输入上下文来自你的数据源。** 如果相关信息散落在无法关联的角落、或者字段含义需要口头传承才能理解，那检索再先进也取不到它。
2. **缺失的信息不会表现为报错，而会表现为自信的错误答案。** 1.1 里讲过模型不知道自己知识的边界；这里的情况更糟——**它连"数据里没有"这件事都不知道**。
3. **所以数据架构的选择实际上决定了 AI 的能力上限。** 这跟 Part 1 讲的"检索质量是系统的上限"是同一条原则，只是层次更低一层。

**最实际的推论**：如果你要做一个基于自有数据的 AI 系统，**先把数据整理好，比先调检索参数回报大得多。** 这也是机器学习里"以数据为中心"那套思路在数据基础设施层面的对应物。

## 5. 能力检查点

1. 我能解释为什么必须先确定访问模式再选存储类型，并说出访问模式至少影响哪些决策。
2. 我能比较关系型、文档型、键值型、图型四种存储在数据形状、强项与弱项上的差异，并为给定访问模式做出选择。
3. 我能说明规范化与反规范化各自的代价，并指出反规范化把一致性责任转移到了哪里。
4. 我能列出四个标准隔离级别及其允许的并发异常，并说明选级别本质上是在交易什么。
5. 我能说明 CAP 定理的正确表述，并指出"三选二"这一流行说法错在哪里。
6. 我能给出数据质量三个维度（干净、一致、新鲜）各自的具体工程手段。
7. 我能列出数据生命周期的各个阶段，并说明为什么"保留多久"必须显式回答。
8. 我能说明"可删除性"为什么在设计阶段就要考虑，事后补不上。
9. 我能解释 expand-contract 迁移模式各阶段的动作，并说明它解决的核心问题是什么。
10. 我能解释数据架构如何决定 AI 系统的能力上限，并说明"AI 不知道它不知道什么"在工程上的具体含义。
