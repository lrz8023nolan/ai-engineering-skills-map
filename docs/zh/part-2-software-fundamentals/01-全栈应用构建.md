# 2.1 全栈应用构建（Building full-stack applications）

> **Part 2** · 软件工程基础
> **状态** · 已完成
> **最后更新** · 2026-09-14

---

## 1. 概述

全栈应用构建，指的是理解**一个网络应用从用户点击到数据落库，中间到底经过了哪些环节**——以及每个环节上存在哪些取舍。

这个技能的价值在 AI 时代反而上升了。编程 Agent 让原本只做前端的、只做移动端的人，能够承担更宽的职责；但它同时制造了一个陷阱：**你不知道该给 Agent 什么约束，因为你不知道有哪些取舍存在。** 一个不懂缓存的人不会意识到"这个接口该不该缓存"是个需要决策的问题，于是 Agent 替他做了一个他看不见的选择——而且往往是代价更高的那个。

不掌握它，典型的后果不是"跑不起来"，而是**跑起来了但结构性错误**：把该放服务端的状态放在了客户端、给不该缓存的响应加了缓存、在认证和授权之间留了一个洞、或者用 ORM 写出一个在开发环境毫秒级、在生产环境秒级的查询。这些都不会报错，只会以"慢"和"偶尔的数据错乱"的形式出现。

## 2. 图谱中的定位

这是 Part 2 五个子技能中的第一个。吴恩达在这一节点出了这个技能的核心张力：

> "A coding agent can help with parts of the development process that you might be less familiar with. However, understanding how the full stack actually works is important."
>
> 编程 Agent 能在你不那么熟悉的环节上帮上忙。但是，理解全栈实际是如何运作的，很重要。

他列出的"关键组件与概念"覆盖了整个栈：

| 层面 | 要理解的内容 |
|---|---|
| 前端 | UI 组件、页面渲染 |
| 数据流 | 缓存、异步处理、数据持久化 |
| 接口 | API 的选择与设计 |
| 身份 | 认证（authentication） |
| 状态 | 状态管理与会话管理 |
| 质量 | 测试、安全、无障碍（accessibility） |

## 3. 核心概念

### 3.1 前后端的分界

| 端 | 跑在哪里 | 可以信任吗 |
|---|---|---|
| **前端** | 用户设备上 | **不可以。** 用户完全控制它，所有校验都必须重做 |
| **后端** | 你的服务器上 | 可以，这是唯一可以放置信任的地方 |

这条是后面一切安全讨论的基础：**前端的任何校验都只是体验优化，不是安全措施。**

### 3.2 页面渲染的四种策略

| 策略 | 何时生成 HTML | 优点 | 代价 |
|---|---|---|---|
| **CSR**（客户端渲染） | 浏览器拿到 JS 后 | 交互流畅，服务端轻 | 首屏慢；SEO 差 |
| **SSR**（服务端渲染） | 每个请求 | 首屏快；SEO 好 | 服务端要承担渲染成本 |
| **SSG**（静态生成） | 构建时 | 最快、最容易缓存 | 内容变了要重新构建 |
| **ISR**（增量静态再生成） | 构建时 + 后台按需更新 | 兼顾速度与新鲜度 | 复杂度上升 |

这四种可以混用。判断的关键是**内容变化频率**与**是否需要为每个用户定制**：几乎不变的内容用 SSG，每次请求都不同的用 SSR，交互密集的局部用 CSR。

### 3.3 缓存是分层的

缓存不是一个按钮，是贯穿整个链路的多层结构：

| 层 | 位置 | 控制方式 |
|---|---|---|
| 浏览器缓存 | 用户设备 | HTTP 响应头 |
| CDN / 边缘缓存 | 离用户最近的节点 | HTTP 响应头 + CDN 配置 |
| 应用层缓存 | 你的服务进程内 | 代码 |
| 分布式缓存 | 独立服务（如 Redis） | 代码 |
| 数据库缓存 | 数据库内部 | 查询与索引设计 |

**前两层的语义已经标准化在 HTTP 里**（RFC 9111 定义了 `Cache-Control`、`Age`、`Vary` 等字段的准确含义）。这意味着你不应该自己发明缓存语义，而是使用标准头——不然中间的任何一层代理都不知道该怎么处理你的响应。

### 3.4 API 的选择与设计

| 风格 | 特点 | 适合 |
|---|---|---|
| **REST** | 以资源为中心，用 HTTP 方法表达动作，依托 HTTP 语义（含缓存、幂等性） | 面向资源的公开接口 |
| **RPC 风格** | 以动作为中心（如 `POST /doThing`） | 内部服务之间的明确动作 |
| **GraphQL** | 客户端声明要什么字段，单一端点 | 客户端需求差异大、避免过度获取 |

选哪种不如**把三件事做对**重要：

1. **幂等性**——GET、PUT、DELETE 按 HTTP 语义应当是幂等的，POST 不是。这决定了客户端能不能安全重试。
2. **错误的结构**——错误应该机器可读而不只是一句话。已有标准格式（RFC 9457 的 problem details），不需要自己发明。
3. **版本演进**——接口一定会变，事先想好怎么变。

### 3.5 认证与授权是两件事

这是最常被混淆、也最贵的一组概念：

| | 回答的问题 | 例子 |
|---|---|---|
| **认证**（authentication） | 你是谁？ | 登录、验证密码或 token |
| **授权**（authorization） | 你能做什么？ | 这个用户能不能删这条记录 |

**只做认证不做授权，就是"I 类漏洞"（越权）的经典形态**：用户确实登录了，但他能访问别人的数据。OWASP 的十大风险清单把访问控制失效长期列在首位附近，原因就在这里。

行业标准的授权框架是 OAuth 2.0（RFC 6749），它定义了四种授权类型——授权码、隐式、资源所有者密码、客户端凭证。**其中隐式授权已被普遍认为不应再用于新系统**（token 会暴露在浏览器地址与历史里），取而代之的是授权码 + PKCE。

### 3.6 状态与会话管理的两种形态

| 形态 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **有状态（服务端会话）** | 会话数据存在服务端，客户端只拿一个不透明 ID | 可以随时失效；数据不暴露 | 需要共享存储；水平扩展要额外处理 |
| **无状态（token）** | 会话数据编码在 token 里，服务端验签即可 | 无需共享存储，扩展容易 | **无法在到期前撤销**（除非维护黑名单，那又变回有状态） |

**这个取舍的核心矛盾是"撤销能力"与"扩展性"的交换。** 需要即时踢人的场景（改密码后失效、风控封禁）必须认真对待这一点。

### 3.7 异步处理与数据持久化

- **异步处理**：把耗时操作从请求路径里移出去（队列、后台任务），让接口快速返回。代价是**最终一致性**——用户看到"已提交"时，事情可能还没做完，所以必须能查询进度。
- **数据持久化**：不只是"存进去"，还包括数据放在哪一层、谁能访问、备份与恢复策略。细节见 [2.2 数据管理](02-数据管理.md)。

### 3.8 测试的层次

| 层次 | 测什么 | 特点 |
|---|---|---|
| **单元测试** | 单个函数或组件 | 极快、极稳定，但离真实使用远 |
| **集成测试** | 多个组件一起 | 覆盖真实交互，速度中等 |
| **端到端测试** | 从用户视角走完整流程 | 最接近真实，但慢且脆弱 |

**比例怎么定是有争议的**（见 §4.7），但"只写单元测试"和"只写端到端"都是已知的坏做法。

### 3.9 安全的最低清单

| 项 | 要求 |
|---|---|
| 输入校验 | 在服务端重做一遍 |
| 认证 | 用成熟方案，不要自己造 |
| 授权 | 每个受保护资源都要检查，且要检查到对象级 |
| 依赖 | 持续扫描已知漏洞 |
| 机密 | 放环境变量或密钥服务，不进代码库 |
| 传输 | 全站 HTTPS |
| 输出转义 | 防注入（SQL、XSS 等） |

### 3.10 无障碍（accessibility）

无障碍不是"给少数人做的额外工作"。它要求的是：语义化的 HTML、键盘可达、足够的对比度、给图片和非文本内容提供替代文本、以及正确的表单标签。

标准是 W3C 的 WCAG，分 A / AA / AAA 三级，**实践中通常以 AA 为合规目标**。

## 4. 深入原理

### 4.1 渲染策略不是偏好，是取舍矩阵

关于"该用 SSR 还是 CSR"的讨论经常变成站队，但它其实是一张可以算的账。要权衡的量至少四个：

| 策略 | 首字节时间（TTFB） | 可交互时间 | 服务端成本 | 内容新鲜度 |
|---|---|---|---|---|
| CSR | 快（空壳） | 慢 | 低 | 每次请求都是最新 |
| SSR | 慢（要渲染） | 中 | 高（每次请求都渲染） | 最新 |
| SSG | 极快 | 快 | 几乎为零 | 构建时的时间点 |
| ISR | 极快 | 快 | 低 | 延迟的 |

**关键洞察：服务端渲染把成本从用户设备转移到了你的服务器上。** 流量大而内容变化慢时，这是纯粹的浪费——同样的 HTML 被渲染了上百万次。反过来，高度个性化的页面无法被静态化，SSR 或 CSR 就没有替代方案。

这也是为什么"不要过早优化"在这里不适用：**渲染策略是一个改变成本结构的决策，而不是一个可以事后调优的参数。** 选错了，后面所有的性能优化都在为这个选择付利息。

### 4.2 缓存的难点在失效，而且分层缓存最容易出事

缓存的收益是显然的，风险是隐蔽的。真正的问题几乎从来不是"要不要缓存"，而是**"什么时候让它失效"**。

一旦你在浏览器、CDN、应用进程、分布式缓存、数据库五层里都放了缓存，同一份数据的**不同副本就处在不同的新鲜度上**。一个经典的事故形态是：

1. 用户更新了资料，应用层缓存被正确清除。
2. 但 CDN 上还留着旧版本的响应，`Cache-Control` 写的是 `max-age=3600`。
3. 于是接下来一小时里，一部分用户看到旧数据，另一部分看到新数据——**取决于他们命中了哪一层缓存。**

这类问题极难复现，因为它依赖缓存命中路径。防御手段是：**明确每一层的新鲜度要求，并用标准头把语义表达清楚**，而不是靠"记得手动清缓存"。

相关的一个实用模式是 **stale-while-revalidate**：先返回可能略旧的内容以保证速度，同时在后台刷新。它把"一致性"换成了"延迟一致性"，对大多数内容型场景是划算的交易——但**对"我刚改完必须立刻看到"的场景是灾难**，所以必须按场景区分。

### 4.3 把认证和授权混为一谈是最贵的 bug

从漏洞数量看，这一条比任何技术细节都更值得记住。**"用户已登录"和"用户有权做这件事"是两个独立的判断，而开发者经常只做了第一个。**

最典型的是**对象级越权**：接口路径是 `/api/orders/{id}`，服务端检查了"请求者有有效会话"，但没有检查"这个订单属于请求者"。攻击者只需把 id 换成别人的，就能读到别人的订单——而这**不会有任何报错**，因为从系统视角看，这个请求完全合法。

防御纪律很朴素：**每一个涉及具体资源的接口，都必须显式地检查"当前用户是否有权访问这个具体资源"**，而且这个检查应该在数据访问层统一实现，不能指望每个接口作者都记得写。

### 4.4 无状态 token 的可撤销性困境

JWT 类 token 的吸引力在于服务端不需要存储——验签即可，扩展性极好。但这里有一个**结构性的矛盾**：

**一个已经签发且未过期的 token，在被服务端遗忘之前一直是有效的。** 而服务端本来就不知道它——这正是无状态的含义。

于是下列场景都成了问题：用户改了密码要踢掉所有旧会话、发现账号被盗要立即封禁、员工离职要立刻收回权限。

常见的缓解手段及其代价：

| 手段 | 代价 |
|---|---|
| 缩短有效期 + 用 refresh token | 缩短了暴露窗口，但没有解决"立刻失效" |
| 维护一个已撤销 token 的黑名单 | 又变回有状态，失去无状态的核心优势 |
| 在 token 里加版本号，用户表存当前版本 | 需要每次请求查一次存储，同样是状态 |

**这不是一个能被"选对方案"解决的问题，而是一个必须按业务需求做取舍的问题。** 如果业务上确实需要即时撤销（金融、医疗、企业权限系统），那就应该承认"纯无状态"不适用，老实接受一次存储查询的代价。

### 4.5 幂等性：重试的前提

网络是不可靠的：超时不代表请求没到达，只代表你没收到响应。**如果接口不幂等，一次"超时后重试"就可能变成两次扣款。**

这解释了为什么 HTTP 协议要区分方法的幂等性：

| 方法 | 幂等？ | 含义 |
|---|---|---|
| GET / HEAD | 是 | 天然安全，可任意重试 |
| PUT / DELETE | 是 | 重复执行结果相同 |
| **POST** | **否** | 重复执行会产生多个资源 |

对于"必须用 POST 但需要可重试"的场景（创建订单、发起支付），标准解法是**幂等键（idempotency key）**：客户端为这次操作生成一个唯一键并随请求发送，服务端遇到同一个键就返回首次的结果而不重复执行。

这条设计的价值在于它把"网络层的不确定性"隔离在业务逻辑之外——**没有它，任何自动重试机制都是危险的。**

### 4.6 N+1 查询：ORM 最容易埋的坑

使用 ORM 时最常见的性能陷阱：查一个列表（1 次查询），然后对列表里每一项去查关联数据（N 次查询）。**开发环境数据量小，毫秒级；生产环境 N 是几百几千，于是变成秒级。**

它之所以危险，是因为**代码看起来完全正常**——没有循环里的原始 SQL，只有一句自然的属性访问。ORM 把性能问题隐藏在语法糖后面。

预防手段：了解你所用 ORM 的预加载（eager loading）机制、在开发环境打印实际执行的查询、以及在代码审查时特别留意"循环体内访问关联对象"的写法。

### 4.7 测试金字塔 vs 测试奖杯

关于各层测试的比例，存在一个值得知道的观点分歧：

| | 主张 | 依据 |
|---|---|---|
| **测试金字塔**（Mike Cohn 提出） | 大量单元测试 + 少量集成 + 更少端到端 | 越往下越快越稳定，成本越低 |
| **测试奖杯**（Kent C. Dodds 提出） | 集成测试是主体，单元和端到端都少 | 单元测试容易测"实现细节"而非"行为"，导致重构时大量无意义失败；集成测试的置信度/成本比最高 |

**双方的共识比分歧更重要**：端到端不应该成为主要手段（太慢太脆），而只测单元也不够（通不过集成）。分歧点在于**中间那一层该占多大比重**，而答案取决于你的系统里"组件间的契约"有多容易出错。

### 4.8 无障碍的"路缘坡效应"

一个反直觉但被反复验证的事实：**为残障用户做的设计改进，最终让所有人都受益。**

路缘坡（curb cut）原本是为轮椅使用者设计的，结果推婴儿车的人、拉行李箱的人、送快递的人都用上了。同样的模式在软件里反复出现：字幕原本为听障用户，结果被在嘈杂环境里的人大量使用；语义化 HTML 原本为了屏幕阅读器，结果让搜索引擎和 AI Agent 也更容易理解页面结构。

**对 AI 应用来说这一点尤其重要**：一个语义化、结构清晰的应用，不只是对人更友好，也更容易被 Agent 正确操作。无障碍做得好，等于顺带把你的应用变成了对 Agent 友好的接口。

### 4.9 为什么这些"过时"的基础在 Agent 时代更重要

一个合理的疑问是：Agent 都能写代码了，学这些还有意义吗？

**有，而且恰恰是因为 Agent 能写代码。** 编程 Agent 的默认行为是"实现需求"，它不会主动告诉你：

- 这个接口加缓存会引入一致性问题
- 这里缺了对象级的权限检查
- 这个查询在生产数据量下会退化成 N+1
- 这个页面选 SSR 会让服务端成本翻十倍

这些都不是"写得对不对"的问题，而是**"要什么"的问题**。Agent 只能在被给定的目标下优化，而**识别并定义这些目标，正是全栈知识的作用**。你不需要比 Agent 写得更快，但你需要知道该让它做什么。

## 5. 能力检查点

1. 我能说明前端与后端在信任模型上的根本区别，并解释为什么前端校验不能替代服务端校验。
2. 我能比较 CSR、SSR、SSG、ISR 四种渲染策略在首字节时间、可交互时间、服务端成本和内容新鲜度上的取舍，并为给定场景做出选择。
3. 我能说出缓存分布在哪些层，并说明为什么应使用标准 HTTP 缓存头而不是自创语义。
4. 我能区分认证与授权，并给出一个对象级越权的具体例子。
5. 我能说明有状态会话与无状态 token 在撤销能力上的取舍，并指出为什么"纯无状态"在某些业务下不适用。
6. 我能解释幂等性的含义，说明哪些 HTTP 方法幂等，并解释幂等键解决什么问题。
7. 我能识别 N+1 查询的代码形态，并说出至少两种预防手段。
8. 我能描述测试金字塔与测试奖杯的分歧点，并说明两者的共识是什么。
9. 我能列出无障碍的最低要求，并解释"路缘坡效应"为什么对 AI 应用尤其重要。
10. 我能解释为什么全栈基础在编程 Agent 普及后反而更重要，并举出至少两个 Agent 不会主动提醒你的风险。
