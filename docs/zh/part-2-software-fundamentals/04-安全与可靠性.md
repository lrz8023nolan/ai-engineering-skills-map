# 2.4 安全与可靠性（Making systems secure and reliable）

> **Part 2** · 软件工程基础
> **状态** · 已完成
> **最后更新** · 2026-09-14

---

## 1. 概述

安全与可靠性，指的是**让系统在会出错的世界里持续做对的事**——既不出安全漏洞，也不在故障面前整体倒下。

这两件事经常被分开讨论，但它们共享同一个前提：**假设一定会出问题。** 安全假设会有人试图攻破你，可靠性假设组件一定会坏。所以两者的工作方式都是"不指望不出错，而是让出错的后果可控"。

不掌握它，最典型的后果是**把安全当成上线前的最后一道关卡**：功能都写完了，最后找工具扫一遍，修掉报出来的问题就发布。这种做法的问题在于，很多安全问题无法在代码扫出来——它藏在设计里（权限边界怎么划、状态放在哪、谁能访问什么）。等代码写完再发现，改动成本已经很高了。可靠性同理：在系统已经跑起来之后才补容错，往往意味着要重构核心路径。

## 2. 图谱中的定位

这是 Part 2 五个子技能中的第四个。吴恩达把这项技能拆成两块：

**可靠性**，分两层：

| 层次 | 内容 |
|---|---|
| **测试策略** | 单元测试与集成测试各占多少、用什么框架、覆盖到什么程度 |
| **按失败设计** | 如何处理失败（比如 API 撞上限流）、优雅降级、**缩小失败的影响半径（blast radius）** |

**安全**，核心是一个时机问题——他称之为「安全左移（shift left）」：

> "You can now use AI tools to scan your code for vulnerabilities, check dependencies for supply chain injections, and examine your cloud configuration for attack surfaces. But doing this well still requires some knowledge of security."
>
> 现在你可以用 AI 工具扫描代码里的漏洞、检查依赖有没有被注入（供应链攻击）、检查云配置里的攻击面。但要把这件事做好，仍然需要一些安全知识。

他还指出一个角色层面的变化：正如所有开发者都在向全栈靠拢，**很多开发者现在也部分地成为了安全工程师**。

出处：[AI Engineering Skills Map Part 3，2026-08-28](https://www.deeplearning.ai/the-batch/the-ai-engineering-skills-map-in-detail-software-engineering-fundamentals)

## 3. 核心概念

### 3.1 可靠性的三条腿

| 支柱 | 作用 | 缺了会怎样 |
|---|---|---|
| **测试** | 提前发现逻辑错误 | 缺陷直接进生产 |
| **容错设计** | 假设组件会坏，让失败可承受 | 单点故障导致整体不可用 |
| **可观测** | 出问题时能快速定位 | 故障时间被排查时间放大 |

三者缺一不可：只有测试没有容错，测试覆盖不到的路径出问题就整体挂掉；只有容错没有可观测，故障会反复发生而找不到原因。

### 3.2 测试策略

| 层次 | 覆盖什么 | 速度 |
|---|---|---|
| 单元测试 | 单个函数/组件 | 毫秒级 |
| 集成测试 | 多个组件协作 | 秒级 |
| 端到端测试 | 完整用户流程 | 分钟级，脆弱 |

关于**覆盖率**（coverage）一个必须知道的判断：**它是一个有用的诊断指标，但是一个糟糕的目标指标。**

原因在于覆盖率衡量的是"这行代码被执行过"，而不是"这行代码被验证过"。一段代码可以 100% 被覆盖而完全没有断言，或者断言了错误的东西。把覆盖率当作 KPI，最直接的效果是 incentivize 写没有断言的测试来刷数字——这正是 §4.2 要展开的问题。

### 3.3 按失败设计

不要问"如果不出错会怎样"，要问"出错时会怎样"：

| 失败场景 | 应对手段 |
|---|---|
| 下游 API 撞上限流 | 退避重试（带随机抖动）、熔断、排队 |
| 依赖服务不可用 | **优雅降级**——提供降级结果而不是报错 |
| 某个实例坏掉 | 健康检查 + 自动摘除 + 冗余实例 |
| 一个区域的故障影响全局 | **缩小影响半径**——把系统切成互不影响的单元 |
| 请求量突增 | 限流、队列、背压（backpressure） |

**「影响半径」这个概念值得单独记**：它指的是**一次故障能波及多大范围**。同样是"某个实例挂了"，如果所有用户共享一个实例，影响半径就是全部用户；如果系统被切成若干互不依赖的单元、每个单元服务一部分用户，影响半径就只有一个单元。**这是架构层面的可靠性设计，不是代码层面能补的。**

### 3.4 安全左移（shift left）

"左"指的是传统项目时间轴上更早的位置。安全工作的位置从"发布前"往左移，含义是：

| 阶段 | 左移后做什么 |
|---|---|
| 设计 | 威胁建模：这个系统会被怎么攻击？权限边界在哪？ |
| 编码 | 安全编码规范、密钥不进代码库、输入校验 |
| 提交 | 密钥扫描、静态分析（SAST）、依赖漏洞扫描 |
| 构建 | 生成软件物料清单（SBOM）、制品签名 |
| 测试 | 动态分析（DAST）、模糊测试 |
| 部署 | 配置校验、最小权限、灰度 |
| 运行 | 运行时监控、异常检测、应急响应 |

**为什么左移有效**：越早发现，修复成本越低。一个设计层面的权限缺陷在编码前改是十分钟的事，上线后改可能要动数据模型。

### 3.5 供应链安全

现代应用里**自己写的代码通常只占一小部分**，其余是依赖。所以攻击者的目标也在往上游移。

| 概念 | 含义 |
|---|---|
| **SBOM**（软件物料清单） | 软件的"成分表"——列出所有组件及版本。有了它，新漏洞公布时能立刻判断自己受不受影响 |
| **SLSA** | 一套保证构建过程完整性、防篡改的等级框架 |
| **制品签名** | 证明这个二进制确实是你构建的、且没被改过 |
| **来源证明（provenance）** | 记录"这个制品是谁、何时、用什么过程构建的" |

**一个具体的动机**：真实发生过的供应链攻击（如 2024 年的 xz-utils 事件）显示，攻击者可以不碰你的代码，只在你的某个依赖里植入后门，通过正常的依赖更新流程进入你的系统。

### 3.6 AI 工具能做什么、不能做什么

吴恩达提到可以用 AI 扫代码漏洞、查依赖注入、看云配置攻击面。这项能力的边界值得说清楚：

| 能做 | 不能做 |
|---|---|
| 快速扫出已知模式的漏洞（注入、硬编码密钥等） | 判断权限边界设计得对不对 |
| 依赖版本与已知 CVE 的比对 | 判断某个操作该不该允许 |
| 云配置的偏离检测 | 识别业务逻辑层面的越权 |
| 大量代码的初筛 | 替代对安全模型的理解 |

**一句话概括**：AI 工具让"发现已知类型的问题"变得便宜，但**"知道哪些问题是问题"仍然是人的工作**。这也是吴恩达那句"要把这件事做好，仍然需要一些安全知识"的意思。

## 4. 深入原理

### 4.1 大多数严重故障，来自从没被测过的错误处理代码

这是一条有实证支撑的结论，应该改变你对"该写什么测试"的判断：

> [Yuan et al., *Simple Testing Can Prevent Most Critical Failures: An Analysis of Production Failures in Distributed Data-Intensive Systems*, OSDI 2014](https://www.usenix.org/conference/osdi14/technical-sessions/presentation/yuan)

研究者分析了多个主流分布式存储系统（Cassandra、HBase、HDFS、MapReduce、Redis、ZooKeeper）在生产中的严重故障，主要发现有两个：

| 发现 | 具体数字 |
|---|---|
| 故障的可复现门槛很低 | **77% 的生产故障可以用三个或更少的节点复现** |
| 故障的触发位置高度集中 | 大多数故障由**错误处理代码**触发 |

第二点是关键。**错误处理代码是平时永远不会被执行到的代码**——正常路径下那些 `catch`、`if error` 分支根本不运行。而恰恰是这些从未被验证过的代码，在生产出问题的那一刻被调用，然后以没预料到的方式失败。

**这条结论解释了为什么"测试覆盖率不错"和"生产可靠"是两件事**：覆盖率统计的是执行过的代码，而错误处理分支恰恰是最不容易被测试执行到的部分。

**它也直接给出了应对方式**：故障注入（fault injection）——**主动制造错误**，让那些平时沉睡的代码路径跑起来。这正是混沌工程（chaos engineering）的理论基础：不是随机搞破坏，而是专门去打那些从没被打过的地方。

### 4.2 覆盖率是激励错位的指标

续上一条，覆盖率作为目标指标会出三个具体问题：

| 问题 | 机制 |
|---|---|
| 奖励无断言的测试 | 执行一行代码就算"覆盖"，不检查结果是 0 成本的达标方式 |
| 奖励测实现细节 | 为了让某行分支被执行，测试会紧贴实现写，重构时大量假失败 |
| 不区分重要程度 | 核心支付逻辑和日志格式化的每行权重相同 |

一个更好的信号是**变异测试**（mutation testing）：工具故意修改你的源代码（把 `>` 改成 `>=`、把常量改掉），然后看测试能不能发现。**发现不了的变异，说明那块代码其实没被真正验证过。**

### 4.3 「按失败设计」为什么必须显式做

一个容易忽略的点：**失败处理代码不会被正常开发流程自然写出来。**

开发时你走的都是成功路径——接口返回了、数据存进去了、页面渲染了。失败路径只有在出事时才被走到，而那时你已经在灭火了，没有余力重新设计。

所以"按失败设计"必须是**主动的、在开发阶段就做的动作**，具体形式是问一组假设性问题：

- 这个下游调用超时 30 秒，用户体验是什么？
- 这个队列堆积了十万条，系统会怎样？
- 这个缓存全丢了，数据库扛得住吗？
- 这个依赖整体挂掉，哪些功能还能用？

**最后一问最重要**——它决定的是"降级后还剩什么"。一个设计良好的系统在依赖挂掉时应该退化成"功能变少但核心可用"，而不是"整体不可用"。

### 4.4 安全左移不是口号，已经有可执行的标准

「越早发现越便宜」是常识，难的是**知道具体该做什么、做到什么程度**。这一块已有成熟框架，不需要自己发明。

> [NIST, *Secure Software Development Framework (SSDF)*, SP 800-218](https://csrc.nist.gov/pubs/sp/800/218/final)
它把安全工作组织成四组实践：

| 组 | 内容 |
|---|---|
| **Prepare the Organization（PO）** | 政策、流程、人员准备：谁负责安全、用什么工具 |
| **Protect the Software（PS）** | 保护软件各组件不被篡改：分支保护、签名提交、仓库权限 |
| **Produce Well-Secured Software（PW）** | 在设计、编码、测试、构建阶段产出安全的软件 |
| **Respond to Vulnerabilities（RV）** | 发布后持续识别与修复漏洞 |

**一个现实信号**：这份框架已成为美国联邦软件采购的强制要求（源于行政令 EO 14028），也就是说它不只是"推荐做法"，而是被当作合同条件在用的。

配套的还有 **SLSA**（Supply-chain Levels for Software Artifacts，由 Google 与 OpenSSF 推动），用等级化的方式约束构建过程：

| 等级 | 要求 |
|---|---|
| L1 | 构建过程有文档、可追溯 |
| L2 | 构建发生在托管服务上，且由该服务签名生成来源证明 |
| L3 | 构建环境强化、隔离，防止构建之间互相干扰 |

**这套等级设计的意义在于它承认了"不是所有人都要一步到位"**：L1 很便宜（记录构建过程），L3 很贵（需要隔离的构建基础设施）。你可以按风险和成本决定停在哪一级。

### 4.5 供应链：把「信任依赖」改成「验证依赖」

传统上我们对依赖的态度是信任：装了就用了。供应链安全的转变是**从信任转向验证**。

具体可操作的三件事：

| 动作 | 解决的问题 |
|---|---|
| 生成 SBOM | 新漏洞公布时，能在几分钟内判断自己是否受影响（而不是几周） |
| 锁定并审查依赖变更 | 依赖的更新也会引入风险，需要被审查而不是自动合并 |
| 验证制品来源 | 确认线上跑的确实是你的构建流水线产出的，而不是被替换过的 |

**一个值得留意的现实**：SBOM 有国际标准格式（SPDX 已成为 ISO/IEC 5962:2021，CycloneDX 由 OWASP 维护），这意味着这不再是各做各的，而是可以互通的规范。

### 4.6 影响半径是架构层面的可靠性

前面说过影响半径，这里展开它的具体做法。

核心思路是**把系统切成互不影响的单元（cell）**：每个单元服务一部分用户、拥有自己完整的依赖栈，单元之间不共享故障域。这样一次故障最多影响一个单元的用户。

| 手段 | 效果 |
|---|---|
| **单元化架构** | 按用户分片到独立单元，故障被限制在一个单元内 |
| **洗牌分片**（shuffle sharding） | 让每个用户的资源组合尽量不重叠，把重叠故障的概率降到极低 |
| **请求隔离** | 一个租户的异常流量不影响其他租户 |
| **降级开关** | 出问题时能主动关掉非核心功能，保住核心路径 |

**为什么这比"把单个组件做可靠"更有效**：单个组件的可靠性有上限，而系统的可靠性是各组件可靠性的乘积——组件越多，整体越不可靠。影响半径的思路不是提高单个组件的可靠性，而是**让单个组件的失败不传播**。

这个思路的早期理论表述来自：

> [Fox & Brewer, *Harvest, Yield, and Scalable Tolerant Systems*, HotOS 1999](https://ieeexplore.ieee.org/document/798396)

该文提出用 **harvest**（返回的数据占应有数据的比例）和 **yield**（被成功响应的请求占请求总数的比例）两条轴来描述系统的退化状态——**而不是二值的"在线/离线"**。这是"优雅降级"的量化基础：一个系统可以在 harvest 下降的情况下保持 yield 不变，也就是"给出的结果不完整，但没有拒绝服务"。

### 4.7 AI 扫代码替代不了什么

回到吴恩达那句提醒。把 AI 在安全上的能力边界说清楚，有一条清晰的判据：

**AI 工具擅长的是"模式匹配"，人负责的是"意图判断"。**

| 类型 | 例子 | 谁来做 |
|---|---|---|
| 模式匹配 | 这段代码有 SQL 拼接、这个密钥被硬编码、这个依赖版本有已知 CVE | **工具，且 AI 让这件事更便宜** |
| 意图判断 | 这个接口应该允许谁访问、这个数据该不该存、这个操作是否需要人工审批 | **人** |

**越权漏洞是最好的例子**：代码本身完全"正确"——它检查了用户已登录、参数合法、类型匹配。工具扫不出任何问题。缺失的是"这个用户是否有权访问这条记录"这个业务判断（见 [2.1 §4.3](01-全栈应用构建.md)）。**这类问题的唯一防线是在数据访问层统一实现权限检查，而不是指望扫描工具。**

## 5. 能力检查点

1. 我能说出可靠性的三个支柱，并解释缺任何一个会出什么问题。
2. 我能说明覆盖率为什么是有用的诊断指标、但糟糕的目标指标，并举出至少两个具体的激励扭曲。
3. 我能解释"影响半径"的含义，并说明为什么它是架构层面的问题而不是代码层面的。
4. 我能说出"安全左移"在设计和编码阶段分别要求什么。
5. 我能解释 SBOM 和 SLSA 各解决什么问题，并说出 SLSA 三个等级的大致要求。
6. 我能说明 AI 工具在安全上的能力边界，并给出一个工具扫不出、必须靠人判断的例子。
7. 我能复述 Yuan 等人关于生产故障的实证结论，并解释它为什么意味着错误处理代码需要专门测试。
8. 我能说明故障注入与混沌工程的理论依据。
9. 我能用 harvest 与 yield 两条轴描述系统的降级状态，并解释为什么"在线/离线"是过于粗糙的描述。
10. 我能为给定系统列出至少四种主动缩小影响半径的手段。
