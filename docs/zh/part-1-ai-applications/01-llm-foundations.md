> **状态** · 已完成

## 1. 概述

LLM 基础，指的是理解大语言模型**把输入切成什么单位**、**如何一步步生成输出**，以及这套机制决定了它在哪些事情上可靠、在哪些事情上会以可预料的方式出错。

它重要，是因为几乎所有关于模型的工程决策都挂在这上面：这个任务该用多大的模型？上下文里能塞多少东西？为什么换个措辞结果就变了？为什么它对某些语言更贵？为什么明明把资料放进上下文了它还是答错？这些问题没有一个是靠"多试几次"能稳定解决的，它们的答案都在机制里。

不掌握它，最典型的后果是两个方向的误判。一是**在不该指望的地方反复碰壁**：让模型数一句话里有几个字母、做精确的算术、或者从十万字的长文档中间取出一个数字，然后归因于"模型不够聪明"，换更大的模型再试一遍。二是**在模型本来就胜任的地方过度工程**：为一个简单的判断任务搭一套检索管线、或者一上来就微调，成本和复杂度都花在了不需要的地方。

## 2. 图谱中的定位

这是 Part 1 六个子技能中的第一个，也是吴恩达在展开 Part 1 时列在最前的一项。他对这个技能要求的覆盖面很广，包括：

- 理解模型如何 tokenize 输入、如何生成输出
- 借此判断**什么时候可以信赖它、什么时候它可能会失败**
- 判断**什么时候该用多模态模型**
- 在上下文窗口里放什么、不放什么，如何做取舍
- 推理关于**缓存命中（cache hit）、知识截止（knowledge cutoff）、推理强度（reasoning effort）、采样参数**，以及什么时候该用工具调用这类特殊功能
- 据此**选出合适的模型或模型组合**
- 在需要时应用专门的技术，例如**微调或自托管模型**

吴恩达把这项技能的价值说得很直接：

> "Understanding how large language models tokenize input and generate output allows you to understand when to count on them and when they may fail."
>
> 理解大语言模型如何将输入分词、如何生成输出，能让你判断什么时候可以依赖它们、什么时候它们可能会失败。

## 3. 核心概念

### 3.1 一次生成发生什么：自回归（autoregressive）

大语言模型不是"想好整段话再一次说出"，而是一次只预测**下一个 token**，然后把预测出的 token 拼回输入，再预测下一个，如此循环。

| 步骤 | 发生什么 |
|---|---|
| 1. 分词 | 输入文本被切成 token 序列 |
| 2. 前向计算 | 模型对每个 token 计算内部表示，产出对整个词表的原始分数（logits） |
| 3. 采样 | 按采样参数把 logits 转成概率分布，并从中选出一个 token |
| 4. 追加 | 选中的 token 被接到序列末尾 |
| 5. 循环 | 回到第 2 步，直到遇到停止条件或达到长度上限 |

这个结构引出两个必须记住的推论：

- **模型对"整段输出"没有全局规划。** 它每一步只优化下一个 token。所以局部看起来通顺、整体却跑偏，是机制内的正常现象，不是 bug。
- **重复计算量很大。** 每生成一个 token 都要把前面全部内容重新过一遍（除非用了缓存，见 §3.5）。这是长上下文既慢又贵的原因。

### 3.2 分词（tokenization）

模型不直接处理字符，也不直接处理单词，而是处理 **token**——由分词器（tokenizer）按词表切出的子词单位。主流做法是 **BPE（字节对编码，byte-pair encoding）**：从字节或字符出发，反复把出现频率最高的相邻片段合并成一个新单位，直到达到预设词表大小。

要记住的是 **token ≠ 字符 ≠ 单词**，三者的换算关系因语言而异：

| 输入 | 大致 token 数 | 说明 |
|---|---|---|
| 英文常见词 `the` | 1 | 高频词往往独占一个 token |
| 英文生僻词 `tokenization` | 2–3 | 低频词被拆成多个片段 |
| 中文一句话 | 接近字数，有时更多 | 中文在多数以英文为主的词表里效率较低 |
| 一串随机数字 `84930517` | 多个 | 数字常被切成不规则的片段 |

### 3.3 上下文窗口（context window）

上下文窗口是模型单次能处理的最大 token 数，输入和输出**共享**这个额度。

| 要理解的点 | 含义 |
|---|---|
| 输入与输出共享额度 | 输出越长，能放进去的输入越少 |
| 注意力代价是二次的 | 序列长度翻倍，注意力部分的计算量约翻四倍（[Vaswani et al., 2017](https://arxiv.org/abs/1706.03762)） |
| 装得下 ≠ 用得好 | 见 §4.2「迷失在中间」 |
| 窗口大小是选模型的硬约束 | 但更大的窗口并不自动意味着更好的结果 |

### 3.4 采样参数

模型输出的是一个概率分布；采样参数决定**从这个分布里怎么挑**。

| 参数 | 作用 | 实际影响 |
|---|---|---|
| **温度（temperature）** | 缩放 logits，控制分布的陡峭程度 | 调低 → 更确定、更保守；调高 → 更多样、更容易跑偏 |
| **top-p（核采样，nucleus sampling）** | 只在累积概率达到 p 的最小 token 集合内采样 | 候选集大小随模型置信度动态变化 |
| **top-k** | 只在概率最高的 k 个 token 内采样 | 候选集大小固定，不随分布形状调整 |
| **贪心解码（greedy decoding）** | 每步直接取概率最高的 token | 确定、快，但容易陷入重复 |
| **seed** | 固定随机数种子 | 提升可复现性，但不保证跨版本一致 |

`top-p` 的提出动机值得记：Holtzman 等人发现，同样一个训练得很好的模型，**仅仅换掉解码策略**，生成质量就会剧烈变化——用似然最大化（贪心、束搜索）解码会产出乏味且重复的文本。人类写作并不走在最大似然的轨迹上。

### 3.5 提示缓存（prompt caching）与上下文经济学

既然每生成一个 token 都要重算前面全部内容，重复的前缀就是纯粹的浪费。提示缓存的做法是：**把前缀的计算状态（KV cache，即注意力机制中的键值状态）存下来**，下次请求如果前缀完全一致，直接复用。

关键机制是**前缀精确匹配**：

| 要点 | 说明 |
|---|---|
| 匹配的是前缀 | 从开头开始逐 token 比对，一旦不同即失效 |
| 静态内容必须放前面 | 系统指令、工具定义、长文档放开头；用户输入、时间戳放最后 |
| 有最小长度门槛 | OpenAI 的实现要求提示达到 1,024 token 才启用自动缓存（[官方文档](https://platform.openai.com/docs/guides/prompt-caching)） |
| 缓存有寿命 | 通常是分钟级；长会话后段可能已经冷掉 |
| 各家配置方式不同 | OpenAI 自动生效，按 `cached_tokens` 计量；Anthropic 需要显式打 `cache_control` 标记 |

### 3.6 知识截止（knowledge cutoff）与外部信息

模型只在训练数据的时间范围内有知识，此后的世界对它不存在。这不是可以通过"问得更清楚"来绕过的限制。

因此，凡是**时效性事实**——今天的价格、当前的版本号、最新的政策——都必须走外部信息注入（检索，或由应用直接提供），而不能指望模型自己知道。同时要意识到：模型不知道自己的知识边界在哪里，它会用同样自信的语气回答截止之后的问题。

### 3.7 推理强度（reasoning effort）

较新的模型提供可调的推理强度：在给出答案前先生成一段内部推理（thinking token），用更多的计算换更高的准确率。

| 场景 | 建议 |
|---|---|
| 多步数学、复杂逻辑、代码调试 | 调高，收益明显 |
| 简单抽取、格式转换、分类 | 调低，高推理强度只增加延迟和成本 |

这条也是选模型和设置参数的常见杠杆：不是所有请求都值得用最高强度。

### 3.8 多模态与工具调用

这两者都是"特殊功能"，使用前提是判断任务是否真的需要。

- **多模态**：当信息本身存在于图像、音频或视频里时使用（读图表、看截图、听语音）。代价是 token 消耗通常远高于等量文本，且不同模型对视觉细节的可靠性差异很大。
- **工具调用（tool calling）**：当模型需要**外部动作或实时数据**时使用。它的意义不只是"取数据"，更是把模型从"必须自己知道"变成"可以去查"，这也是抑制幻觉的主要手段之一。

### 3.9 选模型、改造模型的判据

按顺序判断，不要跳步：

| 决策 | 先问的问题 |
|---|---|
| 选哪个模型 | 任务需要多强的推理？延迟预算多少？成本能承受多少？上下文要多大？ |
| 混合模型 | 简单请求路由到小模型、复杂请求路由到大模型，通常是最直接的降本手段 |
| 加检索还是加工具 | 需要的是"更多上下文"还是"外部动作/实时数据"？ |
| 该不该微调 | 提示、上下文、工具都用尽了还是不够吗？ |
| 该不该自托管 | 有硬性的数据合规要求，或有量大到能摊平运维成本的场景吗？ |

## 4. 深入原理

### 4.1 分词是很多"诡异失败"的根源

模型的推理建立在 token 之上，而人习惯的很多操作建立在字符或单词之上。两者不对齐，就产生了看起来莫名其妙的失败：

| 现象 | 机制上的原因 |
|---|---|
| 数不清单词里有几个字母、数不清句子有几个字 | 模型看到的是 token，不是字符；`strawberry` 里的字母不构成独立的可数单位 |
| 拼写、字母级变换不可靠 | 同上；字母不是模型的原子单位 |
| 精确算术容易出错 | 数字被切成不规则片段，`1234` 可能不是"一千二百三十四"这个数，而是几个无语义的片段 |
| 非英语语言更贵 | 同一段意思，中文、日文在英文主导的词表下往往需要更多 token，成本和延迟同步上升 |
| 同样的提示换个空格结果不同 | 切分边界变了，token 序列就变了 |

这些不是"能力不足"，而是**表示层面**的限制。知道这一点，你就知道该绕开（让对方自己拆字符、用工具算数、用代码执行）而不是换更强的模型硬扛。

### 4.2 迷失在中间（lost in the middle）

一个被反复验证的现象：把同一段相关资料放在上下文的不同位置，模型的表现会系统性变化。

> Liu et al., *Lost in the Middle: How Language Models Use Long Contexts*, [arXiv:2307.03172](https://arxiv.org/abs/2307.03172)（发表于 TACL 2024）

| 发现 | 细节 |
|---|---|
| 性能呈 **U 型曲线** | 信息放在上下文**最开头或最末尾**时表现最好，放在**中间**时显著退化 |
| 退化幅度可以很大 | 极端情况下，GPT-3.5-Turbo 配 20–30 篇检索文档的表现，**低于完全不给文档**（闭卷）的表现 |
| 换成长上下文模型也没解决 | 当输入同时能塞进长、短两个变体时，两者的位置曲线几乎重合——**窗口变大不等于会用** |
| 不是纯语义问题 | 在去掉语义的随机 UUID 键值查找任务上，同样的中段凹陷依然出现，说明部分原因在检索而非推理 |

工程含义很直接：**检索到的资料不要一股脑塞进去。** 要么精选，要么把最关键的放在开头或结尾，要么减少干扰项的数量——多加文档不一定有帮助，可能反而有害。

### 4.3 采样：为什么"温度设成 0"也不保证可复现

即使把温度设为 0（等价于贪心解码），同一个请求也可能在不同时间返回不同结果。原因包括：并行计算带来的浮点累加顺序不固定、服务端批处理与硬件差异、模型版本静默更新、以及某些实现中存在的随机性。

实践结论：**不要把可复现性建立在解码参数上。** 需要稳定的地方，用固定的评估集在不同条件下反复测量，看分布而不是看单次结果。

顺带一个反直觉点：贪心解码虽然"最确定"，却最容易产生重复循环和乏味输出——这正是核采样被提出来的原因（Holtzman et al., *The Curious Case of Neural Text Degeneration*, [arXiv:1904.09751](https://arxiv.org/abs/1904.09751)，ICLR 2020，实验中主用 p = 0.95）。

### 4.4 缓存命中率为什么是 0

这是提示缓存最常见、也最容易踩的坑，值得单列：

**只要提示的前缀有一个 token 不同，后面全部失效。**

所以下面这些看起来很合理的写法，会把缓存命中率直接打到 0：

- 在系统提示的**最开头**插入当前日期或时间
- 在开头注入用户名、会话 ID、请求 ID
- 把一个会随请求变化的配置项放在靠前的位置
- 每轮对话都把工具调用结果无限追加，导致前缀持续变化

修法是结构上的：把提示分成三层，**按"变化频率递增"排列**——长期不变的静态指令放最前，半静态的文档与工具定义居中，本次请求的动态输入放最后。这个顺序在 OpenAI 和 Anthropic 上是通用的（OpenAI 官方文档明确要求 "place static content like instructions and examples at the beginning of your prompt, and put variable content, such as user-specific information, at the end"）。

### 4.5 微调通常是最后手段，不是第一手段

微调看起来最"硬核"，但在多数项目里顺序应该是：**提示 → 上下文/检索 → 工具 → 评估并定位失败 → 最后才是微调**。

原因是微调的成本不只在前向：你要构造成对的训练数据、要维护一条训练管线、要在每次基础模型更新后重新验证、还要承担能力退化（灾难性遗忘）的风险。而如果失败模式其实来自"没有给对上下文"，微调不会解决它。

真要用，参数高效的做法（如 LoRA，[Hu et al., 2021](https://arxiv.org/abs/2106.09685)）比全量微调更常见。

### 4.6 幻觉与校准

模型在不知道答案时，往往不会说"我不知道"，而是给出一个形式上完整、内容上错误的回答。这是训练目标的产物：模型被优化为生成**看起来合理的续写**，而"我不知道"在很多语境下并不是最可能的续写。

研究表明模型内部其实**编码了关于自身正确性的信息**，只是默认不表达出来：

> Kadavath et al., *Language Models (Mostly) Know What They Know*, [arXiv:2205.14334](https://arxiv.org/abs/2205.14334)

工程上有三条常用手段：一是**让模型有据可依**（检索、给参考材料、要求引用来源）；二是**给模型一个退出通道**（明确允许并示范"无法确定"的回答格式，例如要求输出结构化的置信度字段）；三是**外部校验**（用工具或代码去验证模型给出的结论，而不是直接采用）。

## 5. 能力检查点

1. 我能描述自回归生成的一次完整循环，并说明为什么"局部通顺、整体跑偏"是机制内的正常现象而非异常。
2. 我能解释 token、字符、单词三者的区别，并据此说明模型为什么在字母计数、拼写和精确算术上不可靠。
3. 我能说出上下文窗口的额度在输入和输出之间共享，并解释为什么"窗口更大"不等于"用得更准"。
4. 我能说明 `temperature`、`top-p`、`top-k`、贪心解码各自的取舍，并为给定任务选一组采样参数。
5. 我能解释提示缓存的前缀匹配机制，并指出至少三种会让缓存命中率归零的写法。
6. 我能复述"迷失在中间"的核心结论，并说明它对检索系统设计的具体含义。
7. 我能按顺序说明"提示 → 上下文 → 工具 → 评估 → 微调"这个决策链，并解释为什么微调不该排在前面。
8. 我能给出至少三种抑制幻觉的工程手段，并说明各自依赖的机制。
