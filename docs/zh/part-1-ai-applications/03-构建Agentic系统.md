# 1.3 构建 Agentic 系统（Building agentic systems）

> **Part 1** · 构建与部署 AI 应用
> **状态** · 已完成
> **最后更新** · 2026-09-14

---

## 1. 概述

构建 Agentic 系统，指的是把「一次模型调用」扩展成一个**有步骤、有工具、有状态、并且能自己决定下一步做什么**的系统。

它解决的问题是：很多任务不是一次调用能完成的。需要先去查数据、根据结果判断、执行一个动作、再验证动作有没有生效——中间每一步的走向都取决于上一步的产出。单次问答做不到这件事。

不掌握它，会有两种相反的失败。一种是**停在单轮问答**，凡是需要取数、判断、动作的任务都做不了。另一种更常见也更容易吃亏：**一上来就上多智能体**。这个方向的诱惑很大，演示效果也好，但已有测量数据表明，多智能体系统在常见基准上的收益往往远小于预期，失败率却高达 41%–86.7%（见表 §4.3）。付出几倍的 token 和延迟，换来更差、更难调试的结果。

而吴恩达在这个技能上的措辞值得注意：他先说架构选择（什么串联、什么并行、什么时候用代码而不是用模型），然后才是 agent loop 的设计。**顺序本身就是重点——先把流程想清楚，再决定要不要放手让模型自主。**

## 2. 图谱中的定位

这是 Part 1 六个子技能中的第三个。吴恩达给出的定义把它放在一条光谱上：

> "Agentic systems range from workflows that execute a predefined sequence of LLM calls to ones based on an agent harness that lets an LLM repeatedly decide its own next step."
>
> Agentic 系统覆盖一条光谱：一端是执行预先定义好的 LLM 调用序列的 workflow，另一端是基于 agent harness、让模型反复自行决定下一步的系统。

他在这一节里要求的判断包括：

- **架构选择**：哪些步骤串联、哪些并行、什么时候用代码、什么时候用模型
- **工程化实现** workflow 或 harness，并**带 fallback**（失败时的退路）
- **agent loop 的设计**：模型可以调用哪些工具（含 MCP、CLI 与沙箱执行环境）、用什么记忆架构、**长会话中如何管理上下文**、以及什么时候任务需要多智能体编排而不是单智能体
- **从原型走向生产**：护栏、对抗性输入，以及识别并规避关键风险（例如数据外泄）与治理
- **前沿形态**：语音 Agent、computer-use Agent、生成式 UI

出处：[AI Engineering Skills Map Part 2，2026-08-21](https://www.deeplearning.ai/the-batch/he-ai-engineering-skills-map-in-detail-building-and-deploying-ai-applications)

## 3. 核心概念

### 3.1 光谱的两端：workflow 与 agent

关键区分不在"用不用模型"，而在**执行路径由谁决定**。

| | Workflow | Agent |
|---|---|---|
| **执行路径** | 由代码预先编排好 | 由模型在运行时决定 |
| **可预测性** | 高，步骤固定 | 低，路径不固定 |
| **适合** | 任务明确、步骤能事先分解 | 开放式问题，事先说不清要几步 |
| **代价** | 延迟和成本较低 | 延迟和成本更高，换取灵活性 |

Anthropic 的工程指南给出的建议是：**从最简单的方案开始，只在被证明必要时才增加复杂度。** 很多任务根本不需要 agent——一次带检索的模型调用就够了。

### 3.2 五种可组合的 workflow 模式

这是最实用的一张菜单，来自 Anthropic 对数十个团队实践的系统化：

| 模式 | 做法 | 适用 |
|---|---|---|
| **提示链**（prompt chaining） | 把任务拆成固定的顺序步骤，前一步输出喂给后一步，步骤之间可插入程序化检查点 | 任务能干净地顺序分解，如先列大纲、审查、再成文 |
| **路由**（routing） | 先用分类器判断输入类型，再分派给专门的处理路径 | 输入可明确分类，且不同类别需要不同处理；也用于把小模型路由给简单请求 |
| **并行化**（parallelization） | 分段式（不同子任务并行后聚合）或投票式（同一任务多次运行取共识） | 独立的多个维度要同时评估；或需要提高鲁棒性 |
| **编排者-工作者**（orchestrator-workers） | 中心模型在运行时动态拆解任务、分派给工作者、再综合结果 | 子任务无法事先确定，如改动文件数未知的编程任务 |
| **评估者-优化者**（evaluator-optimizer） | 一个模型生成、另一个模型按标准评判，循环到达标 | 有明确的评价标准，且迭代确实能改进，如翻译精修 |

**编排者-工作者与并行化的区别**在于：子任务的集合是运行时才决定的，不是预先固定的。这一点决定了成本和确定性。

### 3.3 架构选择的判据

| 问题 | 指向 |
|---|---|
| 步骤能事先列出来吗？ | 能 → workflow；不能 → agent |
| 路径需要根据中间结果改变吗？ | 需要 → 更靠近 agent 一端 |
| 错误的代价高吗？ | 高 → 保留人在环中或程序化检查点 |
| 延迟预算紧吗？ | 紧 → 偏 workflow，减少往返 |
| 任务能干净分解成互不依赖的子任务吗？ | 能 → 并行；不能 → 不要并行（见 §4.4） |
| 有明确的成功判据吗？ | 有 → 可以加评估者-优化者循环 |

### 3.4 代码还是模型

一条实用的分工原则：

- **用代码**做确定性的部分——数据转换、格式校验、算术、条件分支、权限判定。
- **用模型**做需要判断的部分——理解模糊的意图、决定下一步、生成自然语言、处理例外。

最容易犯的错是把本该用代码做的事交给模型：让模型做算术、让模型判断权限、让模型做格式转换。这些用代码做更快、更便宜、更可靠。

### 3.5 工具层的三种执行环境

| 类型 | 用途 | 需要注意 |
|---|---|---|
| **MCP（模型上下文协议）** | 以标准化方式接入外部工具与数据源 | 工具的授权范围与数据边界 |
| **CLI** | 让模型调用命令行工具 | 命令注入；需要限制可执行的命令集 |
| **沙箱执行环境** | 让模型写并运行代码 | 必须有隔离与资源限制，否则代码是任意执行 |

**工具设计本身是一项技能。** Anthropic 的经验是：花在打磨工具（参数名、描述、示例、边界情况）上的时间，回报超过花在优化提示词上的时间。评判标准应该向"为人类设计界面"看齐。

### 3.6 记忆与长会话的上下文

agent loop 跑起来之后，上下文会持续增长，直到撞上窗口上限。要处理的问题有三类：

| 问题 | 常见做法 |
|---|---|
| 上下文太长 | 摘要压缩、把大块中间产物外置到文件或存储、只保留关键结论 |
| 跨会话丢失 | 把状态持久化，新会话开始时读回 |
| 状态不一致 | 明确哪些是"已知事实"、哪些是"仍需验证" |

**一个必须记住的边界：权限和状态判定不应该由模型持有。** 模型可以被"告知"某个权限，但"被告诉"不等于"被约束"。凡是决定"下一步允不允许做某事"的开关，必须落在代码里、由控制循环显式读取。

### 3.7 单智能体还是多智能体

默认答案应该是**单智能体**。多智能体只在特定条件下才划算，判断依据见 §4.2。

### 3.8 生产化的四件事

| 事项 | 具体内容 |
|---|---|
| **护栏（guardrails）** | 输入输出过滤、权限边界、高风险动作的人工审批 |
| **对抗性输入** | 间接提示注入（见 §4.8）、恶意工具返回值、越权诱导 |
| **关键风险** | 数据外泄、误删生产数据、无限循环导致的成本失控 |
| **治理** | 审计留痕、可回溯的决策链、责任归属 |

## 4. 深入原理

### 4.1 「从简单开始」不是口号，是有测量支撑的

Anthropic 的结论是：大多数任务不需要 agent，增强型 LLM（模型 + 检索 + 工具 + 记忆）就够了；只有当简单方案确实不够用时，才沿着 workflow → agent 的光谱逐步增加复杂度。

这个建议在数据上得到了印证。Cemri 等人对当前最先进的多智能体框架做过一次系统测量：

> Cemri et al., *Why Do Multi-Agent LLM Systems Fail?*, [arXiv:2503.13657](https://arxiv.org/abs/2503.13657)，NeurIPS 2025

他们在 7 个流行的开源多智能体框架上测到 **41%–86.7% 的失败率**，并明确指出：「尽管多智能体系统受到热捧，它们在常见基准上的性能提升相对于单智能体框架、或相对于 best-of-N 采样这样的简单基线，往往很有限。」

换句话说，**增加智能体数量不等于增加能力。** 复杂度必须被证据说服才值得引入。

### 4.2 多智能体：它什么时候真的有效

多智能体并非一无是处，它的有效场景有很明确的特征。Anthropic 报告其多智能体研究系统在检索类任务上比单智能体高出 **90.2%**，但代价是 **token 消耗约为普通对话的 15 倍**；更有意思的一个数字是，**仅 token 用量一项就解释了约 80% 的性能方差**——也就是说，收益很大程度上来自"做得更多"，而不是"分工更聪明"。

关键在于适用边界：

| 适合 | 不适合 |
|---|---|
| 子任务**真正互相独立**、可并行展开（如多路检索、并行审查不同维度） | 子任务**紧耦合**、需要共享大量中间状态（如编程） |
| 上下文可以互相隔离而不损失信息 | 一个 agent 的产出必须精确接上另一个的假设 |

Anthropic 自己就说得很直白：这个模式**不适合编程这类紧耦合的工作**。

### 4.3 多智能体为什么会失败：MAST 的三类十四种

这是目前关于多智能体失败最有据可依的分类。MAST（Multi-Agent System Failure Taxonomy）基于 1,642 条标注过的执行 trace、覆盖 7 个框架构建，标注者间一致性达到 Cohen's κ = 0.88。共 **14 种失败模式，归为三类**：

| 类别 | 占比 | 主要失败模式 |
|---|---|---|
| **一、规格与系统设计** | 约 44.2% | **步骤重复（单一项就占 15.7%，是最常见的失败）**、违背任务规格（11.8%）、违背角色规格、丢失对话历史、不知道终止条件 |
| **二、智能体之间的错位** | 约 32.3% | 对话被重置、隐瞒信息、任务脱轨、忽略其他 agent 的输出、推理与行动不一致（13.2%） |
| **三、验证与终止** | 约 23.5% | 过早终止、没有验证、验证不正确 |

这张表的含义很值得琢磨：**占比最大的那一类（44.2%）根本不是在运行时出的问题，而是在设计时就注定的。** agent 没有坏，它只是忠实地执行了一个有缺陷的设定。这也解释了为什么"换个更强的模型"通常救不了——问题不在模型。

第二类则完全无法在单智能体系统中出现：它们是多智能体这个结构本身带来的。

### 4.4 为什么「再加一个 agent」经常不管用

Cognition 在一篇引起广泛讨论的文章里给出了机制性的解释：

> Walden Yan, *Don't Build Multi-Agents*, Cognition, 2025-06

核心论点是：**动作承载着隐含的决策，而相互冲突的决策会带来糟糕的结果。** 当每个 agent 只掌握部分上下文时，它们各自做出的隐含决策会以任何单个 agent 都看不见的方式互相冲突。

经典例子是让系统生成一个 Flappy Bird 的克隆：一个子 agent 负责背景，一个负责小鸟。第一个把需求理解错，产出了《超级马里奥》风格的背景；第二个产出的鸟既不像 Flappy Bird 的运动方式，画风也和它飞翔其上的背景对不上。**两个子 agent 在各自被告知的信息下都没有做错。**

要缓解这一点，需要共享**完整的 agent 执行 trace**，而不只是 agent 之间传递的消息。这是架构层面的要求，不是改个配置能解决的。

### 4.5 回报最高的单项干预：加一个验证步骤

在同一篇 MAST 研究里，作者做了直接干预实验，结果非常具体：

| 干预 | 任务成功率变化 |
|---|---|
| 增加一个高层验证步骤（在 ChatDev 上） | **+15.6 个百分点** |
| 收紧角色规格 | +9.4 个百分点 |

验证步骤是**最集中、最可测量、效应量最大**的单项改动，而且它不属于上面第一类（设计）问题——它是一个可以直接加的架构组件。如果要给多智能体系统排优先级，这件事应该排在最前面。

### 4.6 失败归因本身极难

一个容易被忽略的现实：即使你知道系统失败了，**自动定位是哪个 agent、在哪一步出问题，目前也做不好**。

Zhang 等人对 127 个多智能体系统做了自动化失败归因的基准测试（*Which Agent Causes Task Failures and When?*, [arXiv:2505.00212](https://arxiv.org/abs/2505.00212)，ICML 2025），最优方法识别**责任 agent** 的准确率为 53.5%，定位**责任步骤**的准确率仅 14.2%——而前沿推理模型在步骤归因上甚至低于自动化基线。

原因是失败通常以**级联**形式出现：早期的一个规格模糊，要到十步之后才以验证失败的形式暴露出来，而 trace 本身不会标记这条因果链。这就是为什么"看日志找原因"在多智能体系统里格外低效。

### 4.7 长会话的上下文管理

随着轮次增加，上下文单调增长，最终会撞上窗口上限；而即使没撞上，「迷失在中间」也会让远处信息的使用效率下降。三条处理路径：

1. **摘要（summarize）**——把早期轮次压缩成结论，丢掉原始细节。
2. **外置（externalize）**——把大块中间产物写到文件或存储，需要时再取回，而不是常驻上下文。
3. **重放（replay）**——把关键状态持久化，让会话可以从中断处恢复，而不是从头重来。

需要警惕的是：**摘要会丢失信息，而且丢失方式不可控。** MAST 分类里"丢失对话历史"本身就是一个独立的失败模式。所以摘要策略要保守，关键约束（如任务规格、角色边界）应当作为常驻内容，而不是被压缩掉的部分。

> 相关早期工作：Packer et al., *MemGPT: Towards LLMs as Operating Systems*, 2023（本文按二手引用，未见原文）

### 4.8 安全：间接提示注入与数据外泄

一旦系统能读外部内容（网页、文档、邮件、工具返回值），这些内容就成了一条**指令通道**。

> Greshake et al., *Not what you've signed up for: Compromising Real-World LLM-Integrated Applications with Indirect Prompt Injection*, 2023（本文按二手引用，未见原文）

机制是：攻击者把指令藏在模型会读到的内容里，模型无法可靠地区分"我收到的数据"和"我收到的指令"。一旦触发，配合工具权限，可能导致数据外泄——把敏感内容发送到攻击者控制的位置。

防御的基本思路有三条：**最小权限**（工具能做的事严格限定）、**来源与指令的隔离**（把外部内容明确标注为数据而非指令）、以及**对不可逆动作设人工闸门**。要注意的是，这一类攻击目前没有被彻底解决，所以真正高风险的场景必须靠权限设计兜底，而不是靠提示词祈祷。

### 4.9 前沿形态

吴恩达点到的三个方向——语音 Agent、computer-use Agent、生成式 UI——共同的特点是：模型的输出不再只是文本，而是**进入一个需要实时交互和状态同步的环境**。它们会把上面所有问题（上下文管理、工具权限、验证、失败归因）都放大一层，因为环境的反馈更快、状态更复杂、出错代价更直接。

## 5. 能力检查点

1. 我能解释 workflow 与 agent 在"执行路径由谁决定"上的根本区别，并为一个任务判断该落在光谱的哪一端。
2. 我能说出五种 workflow 模式各自的机制与适用条件，并指出编排者-工作者与并行化的关键差别。
3. 我能按判据为给定任务选择架构，并说明为什么"更自主"不等于"更好"。
4. 我能划分哪些部分该用代码实现、哪些该交给模型，并说明理由。
5. 我能说明三类工具执行环境（MCP、CLI、沙箱）各自的风险点。
6. 我能复述多智能体在什么条件下有效、在什么条件下无效，并给出支持判断的数据。
7. 我能说出 MAST 三类失败模式的名称与大致占比，并解释为什么占比最大的一类难以靠换模型解决。
8. 我能解释为什么"多一个 agent"经常不奏效，以及缓解它需要什么样的架构改动。
9. 我能说明长会话上下文管理的三种做法，并指出摘要策略的风险。
10. 我能解释间接提示注入的机制，并说出至少三条防御思路。
