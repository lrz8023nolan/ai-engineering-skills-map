# 1.2 用数据锚定模型（Grounding models with data）

> **Part 1** · 构建与部署 AI 应用
> **状态** · 已完成
> **最后更新** · 2026-09-14

---

## 1. 概述

用数据锚定模型，指的是**在模型需要的时候，把相关的、干净的外部数据送到它的输入里**，让它的回答建立在真实材料上而不是参数的模糊记忆上。

它解决的问题很朴素：模型的参数里装着训练时压进去的知识，但这些知识既可能过时、也可能根本没有覆盖你的场景——你的内部文档、上周的会议纪要、客户数据库里的记录，它一概不知。而且它不知道自己不知道，会以同样的自信编造。

不掌握这项技能，最典型的后果是自己造了一堆没有用的东西：把整个知识库塞进提示导致成本和延迟失控、检索回来的资料和问题根本不相关、或者文档里的关键数字因为解析错误而丢失。更隐蔽的一种是**以为接了检索就万事大吉**——实际上检索质量决定了整个系统的上限，检索环节出了问题，后面再强的模型也救不回来。

## 2. 图谱中的定位

这是 Part 1 六个子技能中的第二个。吴恩达在这一节里把它写成一个"选项菜单"的问题——重点不是某个具体技术，而是**知道有哪些选择、以及按什么判据选**：

- 什么内容**直接放进提示**，什么内容**让模型通过工具按需取回**
- 数据的**表示形式**该选哪种：向量索引、知识图谱，还是架在结构化数据之上的语义层
- 把文档（文本、PDF、HTML、图片）**转换成模型可用的输入**
- 搭建数据管线以**保证数据干净且新鲜**

这一节的收尾句把它的价值说得很清楚：

> "When you understand the menu of techniques available to get data, you are better able to give your LLM relevant context."
>
> 当你理解了可用来获取数据的这套技术菜单，你就更有能力为你的大模型提供相关的上下文。

## 3. 核心概念

### 3.1 两条路径：塞进提示 vs 让模型按需取

| 路径 | 做法 | 适用 | 代价 |
|---|---|---|---|
| **塞进提示** | 预先检索，把内容拼进上下文 | 内容确定、每次都需要、体量可控 | 每次都付 token 费；内容变了缓存就失效 |
| **按需取回（工具）** | 给模型检索工具，让它自己决定何时查、查什么 | 内容取决于问题、体量大、需要多轮 | 需要模型判断准确；增加往返轮次和延迟 |

判断的关键是**内容是否每次都相同**。固定的写作规范、接口定义属于前者；用户问什么就查什么的知识库属于后者。两者也可以叠加：把稳定的部分放进提示并打上缓存标记，把变动的部分留给工具。

### 3.2 检索的三代演进

| 代际 | 方法 | 特点 | 代表工作 |
|---|---|---|---|
| **稀疏检索** | 词频统计（BM25 等） | 快、可解释、精确匹配强；不懂同义改写 | Robertson & Zaragoza, BM25（2009） |
| **密集检索** | 把查询和文档都编码成向量，比余弦相似度 | 抓语义，能处理同义替换和模糊表述 | DPR（Karpukhin et al., [arXiv:2004.04906](https://arxiv.org/abs/2004.04906)） |
| **混合检索** | 两路召回后融合 | 兼顾精确匹配和语义匹配，是当前主流 | HybridRAG 等 |

DPR 论文给出的量级感值得记住：仅靠密集表示，在 Top-20 段落检索准确率上比当时很强的 Lucene-BM25 高出 **9–19 个百分点**。

### 3.3 表示形式的选择

这是吴恩达点名的核心判断。四种表示，对应不同的查询类型：

| 表示形式 | 擅长回答 | 不擅长 |
|---|---|---|
| **直接全量塞入** | 小体量、整体相关的材料 | 体量大时成本失控 |
| **向量索引** | 「和这个问题语义相近的内容是什么」——局部事实型问题 | 需要跨文档聚合的全局问题 |
| **知识图谱** | 「这些实体之间的关系是什么」——需要多跳推理的问题 | 索引构建成本高 |
| **语义层（semantic layer）** | 架在结构化数据（如业务记录）之上的受控查询 | 只适用于本来就有结构的数据 |

前三者可以并存。混合检索加知识图谱在金融文档这类场景中已被证明优于单用任何一种。

### 3.4 一条完整的检索管线

```
文档 → 解析 → 切块 → 嵌入 → 索引
                              ↓
问题 → （查询改写）→ 检索 → 重排 → 上下文压缩 → 生成
```

| 环节 | 要做的判断 |
|---|---|
| 解析 | 扫描版 PDF 要不要 OCR？表格结构怎么保留？ |
| 切块（chunking） | 按固定长度还是按语义边界？块太小丢上下文，太大引入噪音 |
| 嵌入 | 选哪个嵌入模型？要不要针对领域微调？ |
| 查询改写 | 用户的问法往往不适合直接检索，需要改写或扩展 |
| 重排（rerank） | 用专门的重排模型对召回结果二次排序，通常回报明显 |
| 上下文压缩 | 把长块里真正相关的部分提取出来，减少噪音和 token |

### 3.5 文档转换

PDF、HTML、图片本身不是模型的输入，需要转成干净的文本或结构化数据。这一步经常被低估，而它的问题会一路传导到最终答案——**解析阶段丢掉的数字，检索阶段找不回来**。

需要留意的几类情况：双栏排版被读串行、表格被拍平成无法理解的文本、页眉页脚混进正文、图片里的信息完全没有被提取。

### 3.6 数据新鲜度

锚定的效果取决于数据有多新。索引不是一次性工作，需要一套机制处理：新增文档的增量索引、修订文档的失效与替换、以及定时重建。这里要判断的是**时效要求有多高**——政策文档可以按天更新，交易看板可能按秒。

### 3.7 决策顺序

遇到「模型答不好这个领域的问题」，按这个顺序排查：

1. 这个问题**需要外部信息**吗？模型本身会的话，检索只会引入噪音。
2. 需要的话，信息**每次都一样**吗？一样就放进提示，不一样就用工具。
3. 用工具的话，**查询类型**是什么？局部事实 → 向量；关系推理 → 图；结构化记录 → 语义层。
4. 检索结果**准不准**？先看检索指标，再怪生成。

## 4. 深入原理

### 4.1 检索质量是系统的上限

这是 RAG 领域最一致的经验：**如果检索没有把相关材料取回来，生成器再强也产不出正确答案。**

原始 RAG 论文（Lewis et al., *Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks*, [arXiv:2005.11401](https://arxiv.org/abs/2005.11401)，NeurIPS 2020）确立的正是这个双记忆范式：模型的知识分成参数化的部分（预训练权重）和非参数化的部分（可检索的外部索引），后者可以随时更新而不需要重新训练。这个设计同时解决了三个问题——知识无法更新、长尾知识覆盖不足、以及回答无法追溯来源。

论文里有一个容易被忽略的技术选择：检索器和生成器是**联合训练**的，而不是各自独立优化。这一点提醒我们一个至今成立的原则：**检索的目标不是"把语义相近的文档找出来"，而是"把生成器真正需要的那几段找出来"**。两者并不总是同一件事。

### 4.2 切块是最被低估的环节

切块决定了检索的最小单位，而它几乎总是一个**手工调参的取舍**：

| 切得小 | 切得大 |
|---|---|
| 检索更精确，噪音少 | 检索更模糊，容易引入无关内容 |
| 单块信息不完整，需要多块拼合 | 单块自足，但含大量无关内容 |
| 适合精确事实查找 | 适合需要上下文的解释性问题 |

实践中通常还需要给每块附加元数据（来源、标题、章节路径），否则检索到的块脱离语境后难以理解。**块的边界应该沿着语义结构走，而不是沿着字数走**——按章节、按段落切，通常优于按固定 token 数硬切。

### 4.3 长上下文不是检索的替代品

上下文窗口越来越大，一个常见的推论是"直接把整个知识库塞进去就行了"。RETRO 的研究给出了一个反向的数据点：

> Borgeaud et al., *Improving Language Models by Retrieving from Trillions of Tokens*, [arXiv:2112.04426](https://arxiv.org/abs/2112.04426)，NeurIPS 2022

该工作通过从 2 万亿 token 的语料中检索来增强自回归语言模型，在 Pile 基准上取得了与 GPT-3 和 Jurassic-1 相当的性能，而参数量只有后者的 **1/25**。这说明检索的价值不只是"补充知识"，还包括**用更小的模型达到同等效果**——这是成本结构上的优势，长上下文窗口替代不了。

反过来说，长上下文也有它不可替代的位置：需要在整篇文档上做全局推理时，检索的碎片化反而是障碍。两者是互补关系。

### 4.4 全局问题的困境与图索引的代价

向量检索的根本限制在这里暴露：它检索的是**独立的文本块**，所以擅长回答「X 是什么」，但回答不了「这批文档整体在讲什么主题」「这些团队之间的协作关系是什么」这类需要跨文档聚合的问题。

GraphRAG 的思路是先构建实体与关系的知识图谱、再做社区检测与分层摘要：

> Edge et al., *From Local to Global: A Graph RAG Approach to Query-Focused Summarization*, [arXiv:2404.16130](https://arxiv.org/abs/2404.16130)，Microsoft Research，2024

论文报告在全局性问题上相比朴素 RAG 的回答质量提升约 **30–70%**。但代价必须一起看：索引阶段需要大量 LLM 调用来抽取实体和关系，成本显著高于向量索引，而且文档更新时往往要重建图结构。**这不是一个"更好的 RAG"，而是一个针对特定查询类型的昂贵补充**。

### 4.5 检索到了，仍然可能答错

把相关材料取回来并放进上下文，并不保证模型会用对。1.1 里讲过的「迷失在中间」在这里直接生效：同一段材料放在上下文的最前面或最后面效果最好，放在中间显著退化；极端情况下，给了 20–30 篇文档的表现**低于完全不给文档**（Liu et al., [arXiv:2307.03172](https://arxiv.org/abs/2307.03172)）。

这条对检索系统的设计有直接含义：**召回数量不是越多越好**。给 20 篇质量参差的文档，很可能不如精选 3 篇。减少干扰项、把最关键的放在两端，比盲目扩大 top-k 更有效。

### 4.6 不是所有问题都该检索

一个反直觉但重要的发现：**对每个问题都执行检索是有害的**。有些问题模型本身就能回答，检索回来的内容反而是噪音，甚至会把模型从正确答案上带偏。

Self-RAG（Asai et al., [arXiv:2310.11511](https://arxiv.org/abs/2310.11511)）的做法是让模型学会输出反思标记，自己判断四件事：是否需要检索、检索到的文档是否相关、生成内容是否有文档支持、回答是否有用。CRAG（Yan et al., [arXiv:2401.15884](https://arxiv.org/abs/2401.15884)）则针对另一个痛点——检索质量差时怎么办——引入一个轻量的检索评估器，根据质量分档采取不同策略，包括降级到网络搜索。

两者的共同启示是：**检索应该是一个可以失败、并且能感知自己失败了的环节**，而不是管线的固定第一站。

### 4.7 检索和生成要分开评估

这是与 1.4 直接衔接的一点。一个 RAG 系统的失败可能出在两个完全不同的地方，混在一起看指标就永远定位不到：

| 层面 | 指标 | 回答的问题 |
|---|---|---|
| **检索** | 命中率（Hit Rate）、MRR、Recall@K | 相关材料有没有被取回来 |
| **生成** | 忠实度（Faithfulness）、答案相关性、上下文精确度/召回率 | 取回来的材料有没有被用对 |

Gao 等人的综述（*Retrieval-Augmented Generation for Large Language Models: A Survey*, [arXiv:2312.10997](https://arxiv.org/abs/2312.10997)）把 RAG 的架构演进归纳为三代——朴素 RAG、高级 RAG、模块化 RAG——并给出了这套分类。它同时是分开评估这一原则的常用出处。

## 5. 能力检查点

1. 我能判断某份内容应该放进提示还是交给工具按需取回，并说明判断依据。
2. 我能说出稀疏检索、密集检索、混合检索各自的取舍，并说明什么情况下密集检索的优势最明显。
3. 我能为给定任务在「向量索引 / 知识图谱 / 语义层 / 直接全量」之间做出选择，并说明理由。
4. 我能画出并解释一条完整检索管线的各个环节，说出每一环要做的判断。
5. 我能解释为什么切块策略是决定检索质量的关键变量，并说明块的边界应该按什么来切。
6. 我能说明为什么长上下文窗口不能替代检索，并举出支持这一点的证据。
7. 我能解释为什么"召回更多文档"可能让结果变差，并指出这与「迷失在中间」的关系。
8. 我能把 RAG 系统的故障分成检索层和生成层，并各举至少两个对应指标。
