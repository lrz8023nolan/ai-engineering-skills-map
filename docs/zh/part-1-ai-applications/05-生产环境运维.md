# 1.5 生产环境运维（Operating in production）

> **Part 1** · 构建与部署 AI 应用
> **状态** · 已完成
> **最后更新** · 2026-09-14

---

## 1. 概述

生产环境运维，指的是**让系统在真实用户、真实流量、真实故障面前持续可用**——而不只是在你的机器上跑通一次。

它和传统软件运维的区别来自三点：**输出不可预测**（你没法用一条断言确认"对了"）、**成本随用量线性放大**（每个请求都在花钱，而传统软件的边际成本接近于零）、**延迟直接变成体验**（用户不会等）。这三点使得"上线"不是一个终点，而是一段需要持续测量的状态。

不掌握它，最常见的三种崩法：系统悄悄变差而没人发现（输入分布漂移了，模型还是老样子）；账单突然失控（某个功能被反复调用，或者提示缓存全部失效）；以及出了事故之后无法定位——因为你没有留下足够的观测数据，只知道"用户说变差了"。

## 2. 图谱中的定位

这是 Part 1 六个子技能中的第五个。吴恩达把这项技能的特殊性直接归因于三点：

> "Operating AI software is different from traditional software because of its unpredictability, cost, and latency."
>
> 运维 AI 软件之所以不同于传统软件，是因为它的不可预测性、成本与延迟。

他列出的要求分三块：

| 要求 | 具体内容 |
|---|---|
| **建立可观测性** | 理解系统在真实使用中的表现；追踪性能、**检测漂移**、对模型故障与安全事件（如对抗性提示注入）快速响应 |
| **回归测试与 CI/CD** | 需要比传统软件**更多的统计评估**；测试投入应当**按犯错的代价来校准** |
| **成本与延迟优化** | 选对技术组合——模型选择优化、蒸馏与微调、Agentic 工作流简化——尤其在用户量大的时候 |

出处：[AI Engineering Skills Map Part 2，2026-08-21](https://www.deeplearning.ai/the-batch/he-ai-engineering-skills-map-in-detail-building-and-deploying-ai-applications)

## 3. 核心概念

### 3.1 可观测性要回答的三个问题

| 问题 | 需要的信号 |
|---|---|
| 发生了什么？ | **trace**——单次请求的完整链路，含各次 LLM 调用、工具调用、耗时、token 数 |
| 现在整体状况如何？ | **指标**——聚合的延迟、成本、成功率、质量分数 |
| 什么时候开始变坏的？ | **日志 + 版本标记**——模型版本、提示版本、代码版本的时间轴对齐 |

三者的关系是：指标告诉你**有异常**，trace 告诉你**异常长什么样**，版本标记告诉你**是哪次改动引入的**。缺任何一个，排查都会退化成猜测。行业已有跨厂商的标准（OpenTelemetry）来统一 trace、指标与日志的格式，不必自创一套。

### 3.2 要追踪什么

| 类别 | 关键指标 | 为什么 |
|---|---|---|
| **质量** | eval 分数（见 1.4）、用户反馈、任务完成率 | 这是 AI 系统唯一真正重要的指标 |
| **成本** | 每请求 token 数、缓存命中率、每用户成本 | 成本失控是 AI 系统特有的故障模式 |
| **延迟** | p50 / p95 / p99、**首 token 延迟**与总延迟分开看 | 平均值会掩盖尾部的糟糕体验；对话场景里首 token 延迟比总延迟更影响感知 |
| **业务** | 转化、留存、人工介入率 | 技术指标好但业务没变，说明测错了东西 |

**一个容易忽略的分层要求**：所有指标都应该能按切片查看——按用户群、按输入类型、按模型版本、按时段。聚合数字会掩盖某一类用户正在被系统性地伤害。

### 3.3 漂移的三种类型

| 类型 | 含义 | 典型信号 |
|---|---|---|
| **数据漂移**（输入分布变了） | 用户问的东西变了，或上游数据变了 | 输入长度分布、主题分布、语言分布偏移 |
| **概念漂移**（输入到输出的关系变了） | 同样的输入，正确答案变了 | 质量指标下降而输入分布未变 |
| **上游变更** | 数据源的 schema、语义或接口变了 | 解析失败率上升；字段突然为空 |

第三种最容易被忽略，也最容易被误诊为"模型坏了"。实践中大量的"模型退化"其实是**上游悄悄改了字段名或格式**。

### 3.4 为什么 CI/CD 需要统计评估

| | 传统软件 | AI 系统 |
|---|---|---|
| 判定方式 | 断言：等于 / 不等于 | 统计：分数是否显著变化 |
| 通过标准 | 确定的 | 需要阈值与容差 |
| 覆盖方式 | 单元 + 集成测试 | 加上 eval 集（见 1.4） |
| 成本敏感度 | 低 | 高——每次回归都要真金白银跑一遍 |

这就是吴恩达说"测试投入要按犯错代价校准"的意思。给一个内部工具做全套 LLM judge 回归是浪费；给一个高风险场景只跑几条断言是不够的。**校准的判据是：这个错误如果漏到线上，代价有多大。**

### 3.5 发布策略

| 策略 | 做法 | 适合 |
|---|---|---|
| **影子（shadow）** | 新模型并行接收真实流量，但结果不返回给用户，仅记录对比 | 上线前验证正确性与真实延迟表现 |
| **金丝雀（canary）** | 先放一小部分真实流量给新版本 | 渐进放量，发现问题代价小 |
| **灰度 / 灰度回滚** | 按用户或流量比例逐步切换，保留快速回退路径 | 常态化发布 |
| **功能开关** | 模型/提示版本可运行时切换 | 需要秒级回滚时 |

**关键前提：模型版本、提示版本都必须是可回滚的一等公民**，就像代码版本一样。如果回滚一次模型要重新部署整个应用，那你实际上没有回滚能力。

### 3.6 成本与延迟优化的四种手段

按"先做回报高的"排序：

| 手段 | 做法 | 收益来源 |
|---|---|---|
| **模型选择与路由** | 简单请求走小模型，复杂请求走大模型 | 直接减少高价模型的调用量 |
| **Agentic 工作流简化** | 去掉不必要的往返；能用代码的地方不要用模型 | 减少调用次数与 token 总量 |
| **服务层效率** | 提示缓存、continuous batching、量化、speculative decoding | 同等硬件服务更多请求 |
| **蒸馏与微调** | 把大模型的能力压到小模型 | 长期单位成本下降 |

前两项是**架构层面**的，通常回报最大而且不需要训练；后两项是**基础设施与模型层面**的，需要投入但上限更高。

### 3.7 事件响应

AI 系统新增了几类传统软件没有的事故：

| 事故类型 | 表现 | 应对 |
|---|---|---|
| **模型故障** | 上游模型 API 变更、限流、宕机 | 多供应商回退；请求队列与降级 |
| **对抗性输入** | 提示注入导致越权或数据外泄（见 1.3） | 最小权限；不可逆动作的人工闸门 |
| **成本失控** | 无限循环、异常重试、缓存全失效 | 预算硬上限与速率限制；缓存命中率告警 |
| **质量静默退化** | 指标缓慢下滑，无人察觉 | 线上质量抽样评估；漂移告警 |

共同点：**都必须能在不发布新版本的情况下止损。** 所以降级路径（关掉某个功能、切回旧模型、把请求拒掉）要事先建好，而不是出事时现做。

## 4. 深入原理

### 4.1 机器学习系统的技术债是系统级的

生产环境运维最难的部分，是那些**看不到的债**。

> Sculley et al., *Hidden Technical Debt in Machine Learning Systems*, NeurIPS 2015 — [论文页](https://papers.nips.cc/paper/5656-hidden-technical-debt-in-machine-learning-systems.pdf)

这篇论文的第一个观察就很有冲击力：真实 ML 系统里，**模型代码只占整体系统的很小一部分**，其余是数据管线、配置、监控、服务化与各种"胶水代码"。

它提出的原则至今适用，叫做 **CACE（Changing Anything Changes Everything）**——改变任何东西都会改变一切。改一个输入特征的分布，其余特征的权重和重要性会跟着变；改超参、采样方法、收敛阈值同样如此。因为**没有任何输入是真正独立的**。

论文列出的系统性反模式，每一条都对应运维里的一类麻烦：

| 反模式 | 表现 |
|---|---|
| 胶水代码 | 原型在一个代码库、上线在另一个，预处理逐步产生分歧 |
| 管线丛林 | 为不同模型版本各建一条数据管线，逻辑重复、结果不一致 |
| 未声明的下游依赖 | 别的系统悄悄依赖你的输出结构，你一改它就静默崩溃 |
| 隐藏的反馈回路 | 模型输出影响用户行为，用户行为又生成未来的训练数据 |
| 配置债 | 配置项散落各处，无法确认线上到底跑的哪套参数 |

**为什么这些债特别危险**：它们复利式累积，而且**silently**（无声地）。代码层面的债有 lint、有 review、有测试可以发现；系统层面的债没有对应的机制，只能靠主动设计。

### 4.2 训练-服务偏移

这是生产环境里最隐蔽、破坏力最大的问题之一：**推理时算出的特征，和训练时用的特征不是同一个东西。**

常见成因：训练用 Python 预处理、服务端用另一种语言重写；缺失值的处理逻辑两边不一致；时间窗口定义不同（训练用 7 天均值，服务用滚动 24 小时）；归一化统计量只在训练数据上算过，而线上分布已经漂移。

它的可怕之处在于**不报错**。系统正常运行、接口正常返回，只是准确率悄悄掉了。

检测手段是：在服务端记录模型的实际输入，定期与训练输入的分布做统计检验（KS 检验、PSI 等），超过阈值就告警。预防手段更根本——**训练与服务共用同一条特征计算代码路径**，而不是保留两套实现。

### 4.3 反馈回路会自我强化

Sculley 等人点出的一个系统级风险：当模型的输出会影响用户行为，而用户行为又成为未来的训练数据时，就形成了闭环。

典型是推荐系统：某个方向的内容因为点击率略高而被推得更多，于是产生更多该类行为数据，于是被推得更多。**系统会自我强化，而每一轮单独看都像是"数据支持这个方向"。** 这里没有 bug，只有设计缺失。

应对不是纯技术问题，而是要在系统设计时就意识到：**你的训练数据是被你自己的模型污染过的**，不能当作对真实偏好的无偏观测。

### 4.4 优化成本之前，先把成本拆开

一个常见的错误是看到账单高就想"换个便宜模型"。但成本由多个部分构成，哪一块占大头决定了该做什么：

| 构成 | 优化方向 |
|---|---|
| 输入 token（含重复的固定前缀） | 提示缓存、精简系统提示、检索结果压缩 |
| 输出 token | 限制输出长度、降低推理强度、避免冗长格式 |
| 调用次数 | 减少往返、合并步骤、能不用模型的地方用代码 |
| 并发与排队 | 服务层批处理、容量规划 |

**提示缓存命中率尤其值得单独监控**。1.1 里讲过：前缀有一个 token 不同，后面全部失效。把时间戳或会话 ID 放在系统提示开头，缓存命中率直接归零——这个错误极其常见，而它只体现在账单上，不体现在任何报错里。

### 4.5 路由：性价比最高的一步

如果只做一件事来降本，通常是**模型路由**——让简单请求走小模型。

> Ong et al., *RouteLLM: Learning to Route LLMs with Preference Data*, LMSYS / UC Berkeley, [arXiv:2406.18665](https://arxiv.org/abs/2406.18665)

这项工作的关键设计是**用人类偏好数据训练路由器**，而不是只判断"小模型答得对不对"。差别在于：同一道题两个模型都能算对，但大模型的解释更清楚，用户实际更满意——只看对错会把这些请求误判为"小模型够用"。

论文报告的结果有具体的量级意义：在 MT-Bench 上，全程用 GPT-4 得分 9.2，而**只有 50% 的请求走 GPT-4** 时得分 9.1（用 BERT 路由器加数据增强），即用户几乎感知不到差异，成本减半。论文另外引入了一个更实用的指标 **CPT(call-performance threshold)**：语料中的数字是 CPT(50%) = 37%——**只用 37% 的请求调用大模型，就能拿到 50% 的顶配体验增益**。

同一批实验还显示，路由器学的是"问题本身的难度"，因此换掉底层模型组合后性能只轻微下降（约 2–3 个百分点），不需要重训。这对会持续更换模型的团队很重要。

### 4.6 蒸馏：为什么软目标比硬标签信息更多

> Hinton, Vinyals & Dean, *Distilling the Knowledge in a Neural Network*, 2015 — [arXiv:1503.02531](https://arxiv.org/abs/1503.02531)

核心洞察是：**大模型输出的完整概率分布，比那个 argmax 标签携带着多得多的信息。** 当一个强分类器说"猫 0.92"时，剩下 0.08 分散在"猞猁""狐狸""狗"上——这个分布编码了教师学到的**类别间相似结构**。让学生模型去匹配这个"软目标"，而不只是匹配硬标签，转移过来的就是这层结构。

机制上是**温度缩放**：把教师和学生的 logits 都除以一个温度 T（常用 2–20）再 softmax，高温让分布变平、把小概率暴露出来。论文在 MNIST 上的效果值得记：教师网络测试错误 67，学生网络从 146 降到 74——学生逼近了教师。在语音识别上，把 10 个模型的集成蒸馏成单个模型，帧分类准确率从 58.9% 提到 60.8%，接近集成的 61.1%。

对工程的含义：蒸馏是**把"贵但好"变成"便宜且接近好"**的正规手段，但它的前提是你已经有一个稳定的教师——所以它排在模型路由和工作流简化之后。

### 4.7 服务层的效率提升是可量化的

如果自托管或用推理服务，最值得知道的优化是 KV cache 的内存管理。

> Kwon et al., *Efficient Memory Management for Large Language Model Serving with PagedAttention*, SOSP 2023（最佳论文）— [arXiv:2309.06180](https://arxiv.org/abs/2309.06180)

传统做法为每个请求预分配一段连续显存，长度按最大可能输出算。但输出长度无法预知，于是产生三类浪费：预留了却用不到、块内部未填满、请求结束后留下的碎片无法拼给新请求。论文测到的结果是：**已分配的 KV cache 内存里，只有 20.4%–38.2% 真正用来存了有效的 token 状态**——60% 到 80% 被浪费掉了。

PagedAttention 借用了操作系统虚拟内存的思路：把 KV cache 切成固定大小的 block，逻辑上连续、物理上不必连续，用 block table 做映射。结果是显存利用率从 20%–40% 提到 **96% 以上**，同等硬件下吞吐提升 **2–4 倍**。

这件事的意义不只是"更快"：**它把并发能力从"模型权重决定"变成了"KV cache 管理决定"**，改的是一个系统问题而不是模型问题。同一层的其他手段还有 continuous batching、prefix caching、speculative decoding。

### 4.8 统计评估的阈值该怎么定

CI 里的 eval 是统计量，所以"通过了"必须有明确定义。三个要点：

1. **区分噪声和信号**。样本量小的时候，1–2 个百分点的波动可能是随机噪声。要么扩大 eval 集，要么设一个大于噪声的阈值。
2. **报告置信区间而不是单点**。只报 0.83 和 0.85 无法判断差异是否真实。
3. **按切片设不同阈值**。整体指标可接受的退化，可能意味着某个小切片彻底坏掉了。

## 5. 能力检查点

1. 我能解释为什么 AI 系统的运维特殊性来自不可预测性、成本和延迟这三点，而不只是"模型会出错"。
2. 我能说明可观测性需要哪三类信号，以及它们在排查中各自的角色。
3. 我能区分数据漂移、概念漂移和上游变更，并说出各自的典型信号。
4. 我能解释为什么 AI 系统的 CI 需要统计评估，并说明测试投入该按什么校准。
5. 我能说出至少三种发布策略及各自适用场景，并说明为什么模型版本与提示版本必须可回滚。
6. 我能把成本拆成至少四个构成部分，并为每个部分说出对应的优化方向。
7. 我能复述 CACE 原则的含义，并说出至少三种 ML 系统特有的技术债反模式。
8. 我能解释训练-服务偏移的成因、为什么它不报错，以及怎么检测和预防。
9. 我能说明模型路由的收益量级与其关键设计（为什么用偏好数据而不是对错）。
10. 我能解释 PagedAttention 解决的问题及其量化收益。
